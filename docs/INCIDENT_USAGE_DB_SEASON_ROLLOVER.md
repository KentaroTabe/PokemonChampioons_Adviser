# インシデント記録: シーズン切替直後の空データ取得による使用率DB汚染

- **発生**: 2026-08-05 21:42 JST(使用率DBの更新実行時)
- **検知**: 2026-08-16(11日後、スナップショットの集計母数が3件と異常に小さいことに気付いて調査)
- **復旧**: 2026-08-16 19:41 JST
- **影響**: 自己対戦の学習分布(約半分が14種族に偏る)、選出モデルの埋め込み基底、
  アドバイザーの使用率順位。**実運用のアドバイスは停止中だったため対人影響なし**
- **失われた生データ**: なし(取得した生JSONは両シーズン分ともアーカイブに保全されていた)。
  壊れたのは生データから作る派生物と、その期間の学習の質

---

## 1. 前提: このデータが何に使われるか

本システムは外部の2ソースを統合して「使用率DB」(SQLite)を作り、更新のたびに
1スナップショットを追加する。

| ソース | 提供する情報 |
|---|---|
| championsbattledata.com API | ポケモンごとの技/持ち物/特性/性格/能力ポイントの**採用率%** |
| champs.pokedb.tokyo オープンデータ | 上位ランカーの**構築一覧**。ここから**ポケモン使用率%**(チーム採用頻度)と**チームメイト共起率**を集計 |

ゲーム側がポケモン自体の使用率を公開していないため、**使用率%は「上位構築に何%登場したか」で代用**している。
この使用率%が下流の3か所に流れる。

1. `meta_sets.weight`(= 使用率%)→ 自己対戦のチーム生成で**種族の抽選確率**になる
2. `teammate_usage` → 種族埋め込みの**共起基底**(選出モデルが使う座標系)
3. アドバイザーの相手種族推測・構築診断の**メタ順位**

## 2. 何が起きたか

ポケモンチャンピオンズはシーズン制で、オープンデータは
`/opendata/s{N}_single_ranked_teams.json` という**シーズン番号付きのURL**で公開される。
取得処理はシーズン番号を明示しない場合、**大きい番号から順に叩いて最初に見つかったものを採用**していた。

```python
candidates = list(range(12, 0, -1))
for n in candidates:
    resp = requests.get(f"{BASE_URL}/opendata/s{n}_{rule}_ranked_teams.json")
    if resp.status_code == 404:
        continue
    ...
    return payload, n      # ← 中身の件数を見ていない
```

2026-08-05、新シーズン M-4 のファイルが公開された。ただし公開直後で**登録は3構築のみ**
(順位も 1位 / 7位 / 8位 と歯抜け)。同日21:42に走った更新は、前日まで使っていた
**285構築の M-3 を捨てて、3構築の M-4 に乗り換えた**。

外形的なサインは記録されていた。スナップショットの集計母数が `285 → 3` に落ちている。
しかし誰も見ていなかったため、11日間気付かれなかった。

| snapshot | 取得日時 | 母数 | 使用率が付いた種族 | 共起行数 |
|---|---|---|---|---|
| 5 | 2026-07-17 | 285 | 115 / 234 | 847 |
| **6** | **2026-08-05** | **3** | **14 / 233** | **82** |
| 7(復旧) | 2026-08-16 | 222 | 109 / 233 | 799 |

## 3. 被害の内訳

### 3-1. 学習分布の崩壊(最も大きい)

使用率%はそのまま `meta_sets.weight` になり、自己対戦のチーム生成 `build_random_party` は
この重みで種族を抽選する。3構築から算出された使用率は「3構築中2件 = 66.67%」「1件 = 33.33%」の
14種族だけに付き、残り219種族は未掲載時のフロア値 0.1 のままになった。

| 指標 | 正常時(7/17) | 汚染時(8/5〜8/16) |
|---|---|---|
| 抽選シェア上位14種の合計 | 48.9% | **96.5%** |
| 抽選シェア90%に必要な種族数 | 59 | **13** |

学習チームは「上位構築の実物50% + メタ生成50%」の混合のため、
**11日間、学習分布のおよそ半分が実質14種族のミラー戦**になっていた。

一方、評価用のベンチマーク相手は別経路(アーカイブファイルを直接読み、ピン止め済み)で
守られていた。つまりこの期間、**訓練分布と評価分布がズレたまま学習していた**。

### 3-2. 種族埋め込みの基底縮小

日次の構築進化ジョブは毎回、共起行列から種族埋め込みを作り直す。
共起データが 847行 → 82行 に減った結果、**埋め込みの基底が118種族から14種族に縮小**した。
8/6以降のログで全日 `共起14種` を確認している。

これは 2026-08-06 に観測されていた「配布版の選出勝率 0.609 → 0.442 の崩落」と日付・原因が符合する。
当時は現象(基底が変わると座標の意味が変わる)への対処として埋め込みのピン止めが入ったが、
**基底が変わった理由**が本件だった。

### 3-3. 無傷だったもの

- **技/持ち物/特性/能力ポイント配分**: championsbattledata 由来のため影響なし
  (234種族、`move_usage` 2,330行を維持)
- **代表型 `meta_sets` の中身**: snapshot 6 → 7 で技構成・持ち物・特性が**234種族すべて不変**。
  ベンチマーク相手の中身は動いていないため、**評価基準は据え置きで過去のベンチ履歴と比較可能**
- **ベンチマークのチームプール**: 8/5当日に別途保護が入っていた(後述)

### 3-4. 失われたもの

生の観測データは失われていない。取得した生JSONは gzip でアーカイブされており、
285構築の M-3 も3構築の M-4 も残っていた(今回の原因特定もこのアーカイブで行った)。

取り返せないのは、**2026-08-05〜08-16 に費やした自己対戦の学習量の質**である。
この期間の学習の約半分は極端に狭い種族分布に対する最適化であり、
同期間のベンチ推移は「訓練分布と評価分布がズレた状態での測定」として読む必要がある。

## 4. 部分的な対策が既にあったのに、なぜ防げなかったか

同じ現象は**発生当日に一度検知されている**。8/5の時点で、ベンチマーク/学習用の
チームプール側には保護が入った。

- 最小チーム数(100)未満のアーカイブファイルは採用しない
- ピンファイルで基準ファイルを固定する

しかしこの保護は**アーカイブファイルを読む経路にしか入らなかった**。
同じ薄いデータを**DBに書き込む経路(ingest)は無防備のまま**で、
そちらから使用率%・共起率・埋め込みが汚染され続けた。

> 根が同じ不具合は複数の経路に出る。片方を塞いだら、同じデータが流れる別経路を必ず洗う。

## 5. 復旧手順(2026-08-16 実施)

M-4 は本日時点で222構築まで積み上がっていたため、再取得のみで復旧できた。

```bash
bash champions_agent/scripts/update_usage_db.sh   # snapshot 7 を作成
python -m tools.species_embedding --build         # 共起基底を作り直す
```

復旧の確認(実測):

- 使用率が付いた種族: 14 → **109**、共起行: 82 → **799**
- 埋め込みの共起基底: 14種 → **111種**
- 抽選シェア上位14種: 96.5% → **49.1%**(正常時48.9%)
- 100パーティを実生成して延べ600体中 **100種族**が出現、上位14種シェア47.5%

チーム生成はバトルごとにDBを引き直すため、**稼働中の学習プロセスの再起動は不要**だった。

## 6. 恒久対策

### 6-1. 取得側: 薄いシーズンは見送って前シーズンへ遡る

`champions_agent/data/sources/pokedb_opendata.py`

- 最新シーズンの構築数が `config.USAGE_MIN_RANKED_TEAMS`(=100)未満なら採用せず、前シーズンを探す
- どのシーズンも満たさない場合は**最も構築数が多かったもの**を採用する(安全側)
- シーズン番号を明示した場合は足切りしない(意図的な取得を妨げない)
- アーカイブに保存するのは実際に採用したペイロードのみ

### 6-2. ingest側: 薄い集計は補完に使わない

`champions_agent/data/sources/usage_scraper.py`

取得側をすり抜けた場合(シーズン明示時、全シーズンが薄い場合)の二重の足切り。
構築数が閾値未満なら使用率%/共起率の補完を行わず、スナップショットを
`source='championsbattledata'` として記録する。壊れた使用率が入るより、
使用率の情報が無い方が下流にとって安全である。

### 6-3. 閾値の一元化

チームプール側の最小チーム数(`env/ranked_teams.py` の `MIN_POOL_TEAMS`)を
同じ設定値の参照に変更し、二重管理をなくした。

### 6-4. 列名と実体の乖離を明記

`usage_snapshot.number_of_battles` は、champions 経路では**対戦数ではなく
pokedb の集計構築数**が入る(ゲーム側が対戦数を公開していないため)。
今回はこの列だけが唯一の異常サインだったので、スキーマコメントと
スナップショットの note に実体を明記した。

### 6-5. 回帰テスト

`tests/test_usage_season_guard.py`(5ケース)

```bash
scripts/run_test.sh test_usage_season_guard
```

- 最新シーズンが薄ければ前シーズンへ遡る(本件の再現)
- 全シーズンが薄ければ最大構築数のものを使う
- シーズン明示時は足切りしない
- 薄い集計が ingest に届いても使用率%/共起率に反映されない
- チームプールの閾値が設定値と一致している

## 7. 教訓

1. **「新シーズンに自動追従」は「空のデータにも追従する」と同義。**
   外部データを自動で切り替える処理には、必ず中身の量の下限を置く。
2. **派生物は毎日作り直されるため、上流の汚染は静かに広がる。**
   使用率% → 抽選重み → 学習分布、共起率 → 埋め込み基底 → 選出モデルと、
   1回の取得ミスが2系統の下流を11日間汚し続けた。
3. **異常のサインは記録されていたが、誰も見ていなかった。**
   集計母数 285 → 3 はDBに残っていた。取り込み量が前回比で大きく変動したら
   警告を出す仕組みが要る(未実装、次の課題)。
4. **同じ根の不具合を片側だけ塞がない。**
   発生当日にチームプール側は保護されたが、DB書き込み側は無防備のままだった。

## 8. 未対応の課題

- 取り込み量の急変(前スナップショット比)を検知して警告する仕組みは未実装
- 使用率DBの日次自動更新(launchd)は plist 同梱済みだが未ロード。
  現状は手動実行のみ(足切りが入ったため、有効化しても暴発しない状態にはなった)
