計画: [docs/ADVICE_ACCURACY_PLAN_1009.md](ADVICE_ACCURACY_PLAN_1009.md) §8.36 (10/19 の 7 提案への回答で「分布混合は別単位」)・§8.49 (② の後に ③。
予測対象と利用できる観測を先に確定し、持ち物・技・選出を一括で混ぜない)。関連: [docs/USEFULNESS_VERIFICATION_PLAN_1007.md](USEFULNESS_VERIFICATION_PLAN_1007.md) §5 (選出傾向の混合は C、時系列で分けた対数尤度)。

## 0. 要点

- 使用率 DB (型予測) と実戦バンクは**同じ分布を持っていない**。DB は種ごとの技・持ち物・特性の採用率 (と構築の採用率・順位) を持ち、選出率を持たない。
  助言が実戦バンクから読むのは**種ごとの選出率だけ** (`advisor/real_prior.py`)。バンクにも技・持ち物・特性の観測はあるが、助言の予測経路は使っていない。
- だから「1 つの式で混ぜる」のではなく、対象を 1 つ選び、同じ条件・同じ対象の分布を両側で作ってから混ぜる。
- 実戦で見えなかった技・持ち物を「持っていなかった」と数えない。バンクの技・持ち物の数は**発火の回数**で、対戦ごとの有無ではない (2.2)。
- 予備集計 (時系列で分けた 103 対戦、参考値): 今の選出率 (出現 3 以上) を `combo_prior` に入れると、**一様分布より対数尤度が低い** (差 −0.46、標準誤差 0.19)。
  選出率を全体の平均へ縮める (疑似件数 5〜10) と一様と同程度 (+0.02〜+0.05)。(3.3)
- 最初に取り組む対象の案: **選出予測** (4 章)。ただしこれは DB と混ぜる話ではなく、バンクの選出率の縮小 (混合比 = 縮小の強さ) の話になる。
  DB と実戦バンクを本当に混ぜる最初の対象を選ぶなら **技予測** (観測が最も多く、DB に同じ量がある)。持ち物は観測の偏りが大きく後回し。
- 「序盤は DB、終盤は実戦バンクが良い」は未検証の仮説として扱い、時系列で分けたデータで比べてから採用する (3.4)。

## 2. 対象ごとの観測と、混ぜられる条件

### 2.1 選出

- **予測したい量**: 相手の 6 体 (と判明した種) が与えられたときの、選出 3 体の分布 (と種ごとの選出確率)。
- **DB 側**: 同じ量が無い。pokemon_usage は構築の採用率 (pokedb) と使用率順位 (ゲーム内) で、「ロースターにいたとき選出される割合」ではない。
  championsbattledata に選出率があるかは未確認 (新しい取得はこの作業の範囲外)。
- **実戦バンク側**: 種ごとの出現・選出 (1.2)。選出 3 体が分かった対戦では、選ばれた 3 体と選ばれなかった個体の両方が観測になる (見えなかった問題が小さい)。
  ただし `opp_pick_status` の無い古いログは「場に出た = 選出」で数えているので、選出されたが出なかった個体を非選出に数えている可能性がある。
- **混ぜられる条件**: DB に同じ量が無いので、DB × バンクの混合は今の DB では成り立たない。成り立つのは「バンクの選出率」と「情報の少ない事前分布」(全体の平均、
  または一様) の混合 = 縮小。混合比は疑似件数 k (p̂ = (選出 + k × m) / (出現 + k)、m = 締切までのバンク全体の選出率) の 1 つ。
  DB の採用率・順位を事前分布にするなら、それが選出率と関係するという仮説を先に別に確かめる (未検証)。

### 2.2 技

- **予測したい量**: 種 s の個体が技 m を持っている確率 (と、判明技 R を条件にした残りの技)。応手の候補として使う。
- **DB 側**: 同じ量がある (種ごとの採用率、上位 10、合計 ≈ 4 技分)。ゲーム内のバトルデータ由来。
- **実戦バンク側**: 実際に使われた技だけが見える。見えるのは「持っていて、かつその対戦で使った」で、持っていたが使わなかった技は見えない。
  発火回数で数えているので、対戦ごとの有無に直す必要がある (予備集計の数え直し: (対戦, 種, 技) 974 件、(対戦, 種) 535 件、250 対戦)。
- **見えなかったものの扱い**: 「その対戦で見えなかった = 持っていない」としない。使える情報は「場に出た個体のうち、技 m が見えた割合」= P(持つ) × P(使う | 持つ, 場に出た) で、
  使う確率が技ごとに違う (まもる・積み技・決め技) ので、P(持つ) と同じ量ではない。
- **混ぜられる条件**: (a) 比べる量を「判明技 R の次に見える技」にそろえる (DB 側も R を条件にした残りの技の分布に直す)、または (b) バンク側の数を DB を事前分布とした
  尤度 (使う確率を含む) で扱う。(a) のほうが実装が小さく、評価 (3.2) と同じ量になる。
- 予備集計 (参考): 対戦時点の snapshot (fetched_at < 対戦開始、時刻帯は未確認) の上位 10 に入っていた技は 739 / 974、入っていない 226、種が DB に無い 9。
  入っていない 226 件には帰属の誤り (1.2) が含まれ得る (内訳は未確認)。

### 2.3 持ち物

- **予測したい量**: 種 s の個体の持ち物の分布 (特に こだわりスカーフ・きあいのタスキ。素早さと耐えで順位が変わる)。
- **DB 側**: 同じ量がある (上位 10)。
- **実戦バンク側**: 自分で表示が出る持ち物だけが見える (予備集計の (対戦, 種, 持ち物) 150 件: たべのこし 65、きあいのタスキ 31、オボンのみ 27、marble 10、いのちのたま 7、
  しろいハーブ 6、ほか 1 件ずつ)。こだわり系は表示が出ないので数に入らない (素早さの推定 `spe_est` は別経路で、バンクには入っていない)。メガ石はメガシンカの観測 (`mega`) で見える。
- **見えなかったものの扱い**: 表示の出ない持ち物を持っていた個体は「観測なし」になる。観測された持ち物の割合をそのまま P(持ち物) にすると、表示の出る持ち物を過大に見積もる。
- **混ぜられる条件**: 「表示が出る持ち物の集合 A の中での内訳」にそろえる (DB 側も A に制限して正規化)。A に入らない持ち物 (スカーフ等) と「A かどうか」はバンクから分からないので DB のまま。
  観測は 150 件 / 54 種で薄く、A の中の内訳を直せる種は限られる。対戦時点の snapshot の上位 10 に入っていた持ち物は 134 / 150 (入っていない 13、種が DB に無い 3)。

## 3. 評価の方法

### 3.1 共通の規則

- **時系列の分割**: 対戦 i の予測には、対戦 i の開始 (`t0`) より前に終わった対戦 (`t1 < t0`) だけで作ったバンクと、対戦 i の開始より前の snapshot だけを使う。
  評価する対戦を推定元に含めない (`docs/USEFULNESS_VERIFICATION_PLAN_1007.md` §5 の規則と同じ)。
- **指標**: 正解の対数尤度の平均 (主)、対戦ごとの差の平均と区間 (対応比較)。副指標は上位 k の命中 (技は応手の候補に入っていたか)。
- **層別**: 種の出現数 (締切時点)、締切時点のバンクの対戦数、日付 (週)。「序盤 / 終盤」の検証は 3.4。
- **パラメータの選び方**: 疑似件数・混合比は前半の期間で選び、後半の期間で 1 回だけ評価する (同じデータで選んで評価しない)。

### 3.2 対象ごとの評価

| 対象 | 正解 | 比べる予測 | 主指標 |
|---|---|---|---|
| 選出 | 選出 3 体が分かった対戦 (ロースター既知 4 体以上) の 3 体組 | 一様 / 今の `combo_prior` (出現 3 以上) / 縮小 (k 複数) | log q(正解の 3 体組) |
| 技 | 対戦ごとに、個体が初めて使った技 (判明技 R の次に見えた技) | DB の残りの技の分布 / バンクの残りの技の分布 / 混合 (混合比 α) | log P(m \| s, R)、と今の応手の候補 (残り枠 + 2) に入っていた割合 |
| 持ち物 | 表示が出た持ち物 (集合 A の中) | DB を A に制限 / バンク / 混合 | log P(item \| s, item ∈ A) |

- 技・持ち物の正解は帰属の誤りを含む (1.2)。評価の前に、帰属の確かな観測だけを使う規則 (例: 技の発火とその時点の場の個体の種が覚えられる技か、の照合) を決める。
- 選出の正解ラベルは `opp_pick_status` のある対戦 (10/7 以降) と、無い古い対戦 (場に出た 3 体) で質が違う。両方を使うなら層に分けて報告する。

### 3.4 「序盤は DB、終盤は実戦バンク」の検証

- 「序盤 / 終盤」がシーズンの時期を指すのか、1 対戦の中の時期を指すのかは未記載。前者として扱い、締切時点のバンクの対戦数 (と種ごとの出現数) で層に分けて、
  DB / バンク / 混合の対数尤度の差が層によって入れ替わるかを見る。シーズンの開始日 (snapshot の source_month は M1) は未確認。
- 採用の条件: 後半の期間の評価で、層ごとの差の区間が入れ替わりを支持したときだけ、混合比を層 (バンクの量) の関数にする。支持しなければ固定の混合比 (または混合なし)。

### 3.5 必要な件数の見積もり

- 対応差の検出に必要な対戦数: n ≈ ((z₁₋α/₂ + z₁₋β) × σ / δ)²。予備集計の σ ≈ 1.3〜1.9 (選出)、α = 0.05 (両側)、検出力 0.8 (z の和 ≈ 2.8) で、
  σ = 1.5 なら δ = 0.5 で約 71 対戦、δ = 0.25 で約 280 対戦、δ = 0.1 で約 1,760 対戦。比較が k 本なら α を 0.05 / k にする。
- 今ある選出の正解: 103 対戦 (予備集計の条件)。前半・後半に分けると後半は約 50 対戦で、δ = 0.5 前後の差しか判定できない。最近の対戦はロースターが 4 体そろわずバンクに入りにくい (1.2) ので、
  新しい正解の増え方は遅い (原因の確認が先)。
- 技は (対戦, 個体) 535 件・初出の技 974 件、持ち物は 150 件。σ は未測定 (選出と同じ手順で予備集計してから見積もる)。

## 4. 最初に取り組む対象の案

**案: 選出予測 (バンクの選出率の縮小)**。

- 正解のラベルがある (選出 3 体が分かれば、選ばれた個体と選ばれなかった個体の両方が観測になる)。技・持ち物のような「見えなかった」問題が小さい。
- 記録の土台がある (`selection_record` の `opp_pick_pred`: 全分布・バンクの版・締切時刻、10/7〜)。評価の規則も既にある (有用性検証の計画 §5)。
- 予備集計で今の方法が一様より悪く、改善の余地が具体的 (3.3)。変更の範囲は `combo_prior` の入力 (選出率の作り方) と設定値で小さい。
- 注意: DB と混ぜる話にはならない。DB と実戦バンクを混ぜる最初の対象としては、**技予測** (観測 974 件、DB に同じ量、応手の候補として legacy・transition の両方に効く) を次に置く。
  持ち物は観測が 150 件で、表示の出ない持ち物 (スカーフ) が見えないため後回し。

## 5. 混合比とデータの版の記録

- 設定: 混合比・疑似件数・最小出現数は `champions_agent/config.py` に置く (選出は既存の `SELECTION_REAL_PRIOR_*` の並びに `…_SHRINK_K` 等)。ハードコードしない。
- 記録 (advice / selection_record 行への欄の追加だけ。既存ログの読み取り互換を保つ):
  - `opp_pick_pred` に `prior` = {方式 (例 "shrink")、k、m (全体の選出率)、最小出現数} を足す。既にあるバンクの版 (sha・締切時刻・対戦数) はそのまま。
  - 技・持ち物を混ぜる段では、予測を使った advice 行に {使用率 snapshot id、バンクの sha16、混合比、対象 (技 / 持ち物)} を残す。version 行の `rules.usage_snapshot` とバンクの版 (計画書 §8.48) と照合できるようにする。
- 再生: `tools.real_accept` / `tools.advice_replay` の `--data-mode restore` で同じ snapshot・同じバンクを読めること (`advisor.data_pin`) を受入条件にする。

## 6. 変えないもの

- 使用率 DB の取得・スキーマ、バンクの集計の既存の欄 (欄を足すなら別の名前で。技・持ち物の対戦ごとの有無は新しい欄にする)。
- 正式群の版の固定 (snapshot 75、バンク 7e515273fc132860、計画書 §8.48・§8.49)。群の間は予測の方式を変えない。
- `slot_weights` の式 (選出予測の改善とは別に、選出の勝率で判断する)。
- 型予測 (`sets.predict`) の出力の形と、`opponent_move_pool` の 4 枠の規則 (技の混合の段で別に判断する)。
- 学習環境の相手プール (`tools/real_opponents.merge_set`) の挙動。

## 7. 残す論点

1. 選出の正解ラベル: `opp_pick_status` の無い古いログ (場に出た 3 体) を正解に含めるか、層に分けるか。
2. 最近の対戦がバンクに入らない (ロースター既知 4 体未満) 原因。ラベルの増え方と時系列の評価の両方に効く。
3. バンクの技・持ち物・特性の帰属の誤り (1.2) と `marble` の意味。混ぜる前に集計の規則を直す必要があるか。
4. バンクの技・持ち物を発火回数から対戦ごとの有無に変える (欄の追加)。
5. `sets.predict` が技の採用率を合計 100 に正規化している (「持っている確率」として使えない)。技の混合の段で直すかどうか。
6. 選出率の事前分布に DB (採用率・順位) を使う案は、関係があるという仮説を別に確かめてから。
7. 持ち物の点推定 (第一の持ち物を 1 つ入れる) を分布にするかは、混合とは別の判断 (transition の感度の欄と関係する)。
