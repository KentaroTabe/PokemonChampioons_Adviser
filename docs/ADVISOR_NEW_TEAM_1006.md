# 新しい傾向のチームで選出・操縦の精度が落ちたときの改善案 (2026-10-06)

接続テストで、これまで使っていなかった傾向のチームを登録して戦ったところ、選出と操縦の精度が低かった、という報告への返答。
対戦ログはこちらにはまだ無いので、**どの経路が働いていたか**をコードから特定し、原因の仮説と、確かめ方、改善案を優先順に書く。
前提は 10/5 の計画書と同じ (良構造の問題はルールと統計、悪構造の問題は LLM か人、較正は実戦)。

## 0. 結論 (先に)

1. 新しい 6 体では、選出の第一候補 (◎) は**学習モデルではなく相性の規則**になっている可能性が高い。学習モデルは「登録の 6 体が
   試用 Package の 6 体に含まれる」か「配布版の学習に使った 6 体の集合と一致する」ときだけ ◎ になる (`advisor.selection.choose_primary`、
   `selection_model.is_in_distribution` は 6 体の集合の完全一致)。それ以外は規則が ◎ で、モデルの推しは「※このチームは未学習のため参考値」。
   規則は 7 月の実測で 乱択 0.25 / 規則 0.29 / モデル 0.51 (当時の my_team、各 200 戦) と、乱択とほとんど変わらない強さしか無い。
2. 規則そのものに、傾向の違うチームで外れやすい弱点がある: 自分の個体を**攻撃全振り (252/252/252) の仮定**で評価する (登録の配分・性格・
   持ち物を見ない。技と特性だけ登録を使う)、トリックルーム・おいかぜ・壁・フィールドの構造を見ない (天候だけ)、「勝ち筋 1 体 + 補助 2 体」
   のような役割の構造が無い。耐久型・トリックルーム型・展開型のチームでは、対面の撃破ターン差で選ぶ規則は的を外す。
3. 操縦 (行動の助言) は、固定の価値表 (`engine.STATUS_MOVE_VALUE`: トリックルーム 15、おいかぜ 18、積み技 25、設置 25 …) と、RL 方策の
   ヒント (確率 × 25 点をスコアに足す。チームの分布を見ずに常に掛かる) が、これまでのチーム (攻め・対面操作) の作法で較正されている。
   探索 (択の利得行列) は表示だけ (`SEARCH_BLEND = 0`)。チームの傾向が変わると、価値表と RL ヒントの両方が外れる方向に働く。
4. 直し方は 3 段: (A) **診断を先に** (半日。どの経路が働き、何を外したかを記録から出す)、(B) **選出**: 登録チームの選出モデルの適応を
   運用の手順に組み込む + 規則に登録の型と速度計画を入れる、(C) **操縦**: RL ヒントに分布の門を付け、構築パイプラインが持つ役割・
   速度計画を「作戦書」として助言に渡す。いずれも、変更の前後をシム (`check_advisor_player`) と正解つき局面で測る。
5. 「チームが弱い」と「操縦が悪い」は分けて測る。登録チームをパイプラインの参照として 1 run (ふるい段だけでよい) 回し、助言プレイヤーで
   操縦したシムの勝率を見れば、同じ操縦者での期待値が出る。実戦との差 (参照チームでは シム 0.54〜0.61 vs 実戦 0.44) が操縦の差の目安になる。

## 1. まず確かめること (診断、半日)

接続テストの対戦ログ (`logs/battles/battle_*.jsonl`) に対して、既にあるツールで次を出す。結果は表にして PENDING に残す。

| 確認 | 方法 | 読むもの |
|---|---|---|
| 選出の ◎ が規則だったか、モデルの退避理由 | `python -m tools.advice_trace --last N` | version 行の `selection_model.fallback_reason` (`party_not_in_package` / `selection_model_missing`)、選出助言の `primary` (model / rule)、`model_pick.trained` |
| 選出が実際の選出と一致したか、間に合ったか | `tools/team_build/real_eval.selection_compliance_rows` (advice_trace の集計にも出る) | `members_match`、`timely`、`by_primary` |
| 行動の助言のどこが外れたか | `python -m tools.scene_eval extract --last N --out logs/scenes/newteam.jsonl` → ラベル付け → `evaluate --set …` | 局面ごとの「正しい状態 / 合法な行動 / 表示の期限」と、助言の分類 (consistent / stale / late / advice_stop) |
| RL ヒントがどちらに引いたか | 助言行の `rl_hint` (top 4 と局面価値) と、採用された行動の `reason` の `RL xx%` | RL が最終順位を変えた局面の数と、その局面の正誤 |
| 自分側の認識 | 対戦ログの自分の種・持ち物の解決 (`my_roster_resolution` の経路) | 新しい個体で未解決・誤解決が無いか (選出の評価対象から落ちると `選出評価に必要な情報が不足` になる) |

ここまでで「規則が ◎ だった割合」「規則の選出と人の選出の不一致」「操縦の失敗の分類」が数字になる。30 局面の誤り率は実戦の率ではない
(10/5 ③ の注意) ので、傾向を見るための標本として扱う。

## 2. 原因の仮説: 選出

| 仮説 | 根拠 (コード) | 当てはまるときの症状 |
|---|---|---|
| 分布外のため規則に落ちた | `choose_primary`: `model_pick.trained` が偽なら ◎ は規則。`trained` は Package の 6 体に含まれるか、`trained_teams()` に 6 体の集合があるかだけ | 選出表示が「◎ 推奨選出:」(学習モデル の文字なし) + 「🤖 学習モデルの推し … ※未学習」 |
| 規則が登録の型を見ていない | `_make_view` は `OFFENSIVE_EV` (攻撃・特攻・素早さ 252) で自分の個体を作る。登録から使うのは技 (`_own_registered_moves`) と特性 (`_own_ability`) だけ。耐久振りの受け役が「速くて脆い攻撃役」として評価される | 受け役・起点役が選ばれない、速い攻撃役ばかりが選ばれる |
| 速度計画を見ない | `duel_score` は実効素早さの先手権を足すが、トリックルーム・おいかぜ・ねばねばネットを前提にできない。`advise_selection` の構造の加点は天候シナジーとメガ枠だけ | トリックルーム型で遅い攻撃役が「先手を取られる」として外れる。始動役が選ばれない |
| 役割の構造が無い | 評価は Σ_相手 max_自分 (補完性) + 0.3 × 平均。「始動 → エース」「設置 → 交代の圧力」のような 2 体で 1 つの仕事を評価できない | 3 体がばらばらに「有利対面が多い」個体になる |
| 相手の推測は変わらない | 相手側はタイプ → 使用率の候補 (`advisor.infer`) + 実戦の選出率 (`real_prior`) で、自分のチームに依らない | この部分の精度は前のチームと同じはず (差が出るなら自分側) |

## 3. 原因の仮説: 操縦

| 仮説 | 根拠 (コード) | 当てはまるときの症状 |
|---|---|---|
| 固定の価値表が前のチームの作法 | `STATUS_MOVE_VALUE` は技ごとの定数 (トリックルーム 15 < おいかぜ 18 < まもる 18 < 積み技 25)。回復技は別の規則。チームの計画 (この並びはトリックルームで勝つ) を知らない | 始動技が攻撃や交代より下に出る。受け役の回復・状態異常が攻撃より下に出る |
| RL ヒントが分布の外でも同じ重みで掛かる | `policy_hint` の確率 × 25 点 (`RL_BLEND_WEIGHT`) を常に足す。行動方策は自己対戦の固定プール (チーム適応は off: 計画書 D3) で学習。観測は種族値・タイプ・技なので形式上はどのチームも入るが、見ていない作法 (トリックルーム下の行動、受け回し) では確率が外れる | 「RL 70%」の理由で、割引された手や受けの手が持ち上がる |
| 探索は表示だけ | `SEARCH_BLEND = 0`。2 手読みの推奨は出るが順位に効かない | 探索は正しいのに ◎ が違う局面がある |
| 作戦が無い | 助言は局面ごとの採点で、「このチームはこう勝つ」(勝ち筋・始動の順・温存) を持たない。`_run_endgame` の勝ち筋は終盤だけ | 序盤に始動役を消耗する、エースを早く出す |

## 4. 改善案 (優先順)

効果の見込みは診断 (§1) の数字で決まる。工数は目安。検証はすべて「変更の前後を同じ条件で測る」。

### 4.1 選出

| # | 案 | 中身 | 工数 | 検証 |
|---|---|---|---|---|
| S1 | **登録チームの選出モデルの適応を運用の手順に組み込む** | `config/my_team.json` の 6 体が変わったら (種の集合の sha)、S7 と同じ適応 (`tools/team_build/adapt.adapt_selection`: シムで助言プレイヤーが選出 → 戦闘 → 勝敗を集め、汎用モデルを微調整) を登録チーム向けに回し、`logs/registry/registered/<sha>/selection_model.pt` に置く。`selection_dispatch.advisor_model_path` は Package → 登録チーム向け → 配布版の順に引き、version 行に `selection_model.package = registered:<sha>` を残す。画面には「選出モデル: 適応済み / 未適応 (規則で助言中)」を出す。既存の手順 `scripts/refresh_selection_myteam.sh` (2 回 × 2500 戦) の自動化に当たる | 1〜2 日 (収集はシムで数時間) | 適応の前後で `check_advisor_player --team-file 登録 --pick-policy advisor` vs `--pick-policy rule` を同じ相手 split で 300 戦ずつ。実戦では `selection_compliance` の一致率と勝率を版で分けて見る |
| S2 | **規則に登録の型を入れる** | `_make_view` を登録の配分・性格・持ち物 (`my_team.get_my_build`) で作る (無ければ今の攻撃全振り)。受け役が受け役として評価される | 半日 | S1 と同じシムの比較 (rule の前後)。正解つき局面の選出版 (人の選出との一致) |
| S3 | **速度計画と構造の加点** | 並びにトリックルーム (始動技か、構築の `speed_plan = trick_room`) があれば、その 3 体の `duel_score` を遅い方が先手の前提でも計算し、始動役 + 遅い攻撃役の組に加点。おいかぜ・ねばねばネット・壁 + 積みも同じ形 (始動役 → 恩恵役)。天候シナジーの加点 (`_weather_synergy_bonus`) の一般化 | 1 日 | 同上。トリックルーム型・展開型のチームを 2〜3 用意してシムで比べる |
| S4 | **選出表 (シムで事前計算)** | 登録チームと相手プールの系統ごとに、S8a と同じ測定で最良の 3 体を出しておき、選出画面では相手の 6 体に最も近い系統の表を引く。モデルより安く、根拠 (勝率) が付く。S1 の適応が間に合わない間のつなぎにもなる | 1 日 | 表の勝率 (シム) と実戦の勝率の対応 |

S1 が本命。規則の改良 (S2〜S3) は「モデルが無いときの予備」の底上げで、7 月の実測 (規則 0.29) を考えると、規則だけで実戦の精度を
取り戻すのは難しい。

### 4.2 操縦

| # | 案 | 中身 | 工数 | 検証 |
|---|---|---|---|---|
| P1 | **RL ヒントに分布の門** | 登録チームが行動方策の学習プール (自己対戦のチーム) の傾向に無いとき (判定: 学習プールに同じ 6 体が無い、かつ速度計画か役割の構成が違う。最初は手動のフラグでよい) は `RL_BLEND` を下げるか切る。version 行に `action_policy.in_distribution` を残す | 半日 | `check_advisor_player --no-rl-blend` vs 既定を登録チームで 300 戦ずつ。正解つき局面で RL が順位を変えた局面の正誤 |
| P2 | **作戦書を助言に渡す** | 構築パイプラインは並びごとに役割 (`roles_of`、雛形 breaker / wall / sweeper_setup / tr_setter …) と速度計画 (`speed_plan`)、系統ごとの選出計画 (`s06_sets/<cid>.plan.json`) を持つ。登録チームにも同じものを作り (`config/my_team.json` に `役割` と `計画` を追加、Package なら `advisor_policy/plan.json`)、助言はそれで価値表を動かす: トリックルーム計画ならトリックルームの価値を「自分の残りの個体のうち相手より遅いものの数」で上げる、受け役なら回復・状態異常の価値を上げる、積みエースは起点があるときだけ積みを上げる、始動役は消耗を避ける (交代の価値) | 2〜3 日 | 正解つき局面 (新チームの対戦から作り直す) の一致率。シムの勝率 |
| P3 | **探索の重みの試験** | 受け回し・展開のチームでは 2 手読みの方が価値表より当たる可能性がある。`SEARCH_BLEND` を 0.3 前後で試す (`check_advisor_player --search-blend`) | 半日 | シム 300 戦と正解つき局面 |
| P4 | **正解つき局面を作り直す** | 今の 30 局面は前のチームの対戦から切り出したもの。新しいチームの対戦から整合 20 + 既知の失敗 10 を切り直し、ラベル (正しい状態 / 合法な行動 / 表示の期限) を付ける | 半日 | — (P1〜P3 の物差し) |

### 4.3 共通 (測定の枠組み)

- 版で分ける: 実戦の勝率は version 行 (指定 Package / 実際に読んだ選出モデル / 行動方策の sha) で層別し、「新しいチーム × 規則」
  「新しいチーム × 適応済みモデル」を分けて数える。16 戦程度では勝率の差は出ないので、まずは選出の一致率と局面の正誤で見る。
- チームの強さと操縦を分ける (§0-5): 登録チームを S0 の参照にして run (ふるい段まで) を 1 本回す。助言プレイヤーで操縦した
  シムの勝率が出る。これが低ければチームの問題が大きく、高いのに実戦が低ければ操縦 (と認識) の問題。

## 5. 判断が要る点

1. S1 の自動化の範囲: 登録チームが変わるたびにシムで 5000 戦前後 (数時間) を回してよいか。回すなら、接続テストと重ならない時間に
   限る (10/5 23 時台に煙試験と重なって受信の 16/18 枚を捨てた記録がある)。
2. 適応が終わるまでの間、◎ を規則にするか、未学習のモデルにするか (今は規則)。S4 の選出表をつなぎにするか。
3. P2 の「作戦書」の置き場: `config/my_team.json` に `役割` / `計画` の欄を足す (手入力) か、構築パイプラインの出力 (Package) から
   写すか。登録チームがパイプラインの外で作られたなら手入力になる。
4. 新しい傾向のチームをこのまま使うなら、パイプラインの参照 (S0) に登録して、次の run で候補と並べて測るか。

## 6. 実装に入る順

1. §1 の診断 (ログを受け取り次第)。
2. P4 (局面の切り直し) と S2 / P1 (半日ずつ、低リスク)。
3. S1 (本命。収集の時間が要るので早めに始める)。
4. S3 / P2 (設計から。構築パイプラインの役割・速度計画と語彙を揃える)。
5. P3 / S4 は診断の結果しだい。
