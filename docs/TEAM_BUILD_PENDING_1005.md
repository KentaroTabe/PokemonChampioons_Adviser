### 2.3 テーマのエース選出率

過去 2 run (エース = ミミロップ) の対戦記録に `theme_check` を掛けた。

  標本 4 並びの点は 0.862 / 0.893 / 0.919 / 0.934。保持の規則による偏りは避けられるが、点の低い並びは入らない。

### 2.7 昇格の定義

- registry の Package 12 件のうち 11 件は最終検証が 600 戦 (medium の上限)。100 戦は rule_0909 の 1 件だけ。

### 9.6 判断 (2026-10-05、§9.5 への回答としてユーザーから受け取ったもの)

| 判断待ち | 判断 | 条件・補足 |
|---|---|---|
| 戻り: 登録の個体を 2 体目として外してよいか | はい | 「登録した型を変更しない」と「その個体を構築から外さない」は別の制約。登録の個体でも、エース・必須枠・固定した核でなければ修理の候補から外してよい。参照チームはそのまま残す |
| 戻り: 2 枠の入替を先に測るか | はい | 次の run で検証の機会を確保するための判断で、2 枠の入替の方が強いと結論したわけではない |
| 型の自動修正でメガ石を外してよいか | 外さない | メガ石を外すと想定フォルム・特性・役割まで変わるので、黙って行う型の修正としては大きすぎる。まず石を保持して技の側の修正を検討し、必須技などの制約で直せなければ自動修正を止めて理由を残す。非メガ型への変更は、別の構築候補として明示的に扱う |
| 交代技のテストの期待値の変更 (4fd284cf) | 承認 | 元の期待値が対戦の仕組みに反していた部分の訂正。「先に倒されるなら通常の交代を優先」「先手なら交代技の上乗せが働く」を分けたテストも妥当。合格条件は具体的な点数より、必要な行動順と、危険な交代技を補正で復活させないことを中心に維持する |

同じ回答にあった設計の方針:

- 制約を 3 つに分ける: **個体を残す制約** / **型を保つ制約** / **メガ形態を保つ制約**。
- メガ型と非メガ型は別候補として扱う。ただし種族の同一性と、対戦中の個体の同一性は保つ。

  | 場面 | 扱い |
  |---|---|
  | 型生成・役割・相性評価 | メガ型と非メガ型を別候補にする |
  | 構築の種族重複チェック | 元の種族でまとめる |
  | 対戦中の状態管理 | 同じ個体がメガ前からメガ後へ変化するものとして扱う |

- 「非メガ型」と「メガ型のメガシンカ前」は別。後者はメガ石を持ち、メガ後の能力や特性を前提に組まれている。
- 修理: メガ型はメガ石と変化先を保持して技・配分を調整する。非メガ型は非メガでの役割に合わせて調整する。
  メガ型 ↔ 非メガ型の変更は独立した候補として生成し、役割と構築全体を評価し直す。
- 複数のメガ石持ちを候補に含めるときは、選出ごとに誰をメガシンカさせるかを決め、全員をメガ後の能力で評価しない。
- 同じ種族のメガ型から非メガ型への変更は「型・役割の変更」として記録し、「2 体を入れ替えた」件数には含めない。
- 既存の土台 (該当箇所は確認済み): 型候補の識別キーに持ち物が入っている (`tools/team_build/sets.py` の `SetCandidate.key`)、
  選出評価はメガ前とメガ後を別の表で持ち、誰をメガ枠にするかを選出ごとに決めている (`advisor/selection.py`)。
  これを生成・修理・評価・記録まで一貫させる。

この記録の時点で実装は未着手。直す箇所の見当: 2 体目の候補から型を固定した個体を除いている条件 (`repair.repair_variants`)、
測る順 (`repair.select_variants`: 全部の親の B → A を、A を先に)、持ち物の修理がメガ石も替えること (`set_lint.repair_set`)。

## 13. 規則の定義の変更: 先制技の判別と、こだわり系の例外 (運用側、2026-10-05 23 時台)

§12.1 の 2 点について、ユーザーから次の判断を受けて実装した (95f27457 → 7d842d0e)。

|---|---|
| 先制技 (性格と技) | どちらかに寄せる必要はない。「火力が必要な先制技」か「1 ダメージを与えられれば良い先制技」かを型によって判別する |
| こだわり系と変化技 | トリック / すりかえ を持つ型と すてゼリフ は例外としてよい |

### 13.1 判別の定義 (`set_lint.priority_needs_power`)

性格が下げる側 (攻撃か特攻) を使う攻撃技が**先制技だけ**のとき、その型で先制技に火力が要るかを見る。次のどれかなら「火力が要る」= 誤り。

1. 下げる側だけを上げる技を持つ (つるぎのまい、りゅうのまい など。上げてから撃つ型)。からをやぶる のように両方の攻撃を上げる技は
   数えない (どちらで戦う型かはほかの技で決まる)。
2. その攻撃を上げるこだわり系を持つ (下げる側が攻撃なら こだわりハチマキ、特攻なら こだわりメガネ)。
3. 下げる側を使わないダメージ源が 1 つも無い (その先制技が唯一の攻撃技)。

どれでもなければ「1 ダメージ入ればよい」(ほかの技で戦い、先制技は削り・とどめ・タスキつぶし) とみなし、誤りにしない。
先制技でない攻撃技が下げる側を使っていれば、これまでどおり誤り。判別に使う優先度と能力の上昇は、図鑑と `advisor/data/boost_moves.json`
から引く (`DexInfo.move` に priority と self_boosts を足した)。

この 3 つの条件は「型によって判別する」という判断を運用側が具体化したもの。条件を示して確認を求め、ユーザーから
「推奨通りで良い」の回答を受けた (2026-10-05 23 時台)。

### 15.1 軽い適応 (cheap) が参照で 0.313 になる原因の見立て (実装側)

コードから見える仕組み (`pipeline._screen_adapt_all` → `adapt.adapt_selection(min=max=1000)` → `train_selection.adapt_candidate`):

1. 収集は 1,000 戦。半分は乱択の選出、残りはタイプ相性の簡易規則 (`search_expert.teampreview_order`) の選出で、勝敗が 0/1 の標本。
2. 学習は汎用モデルを起点に lr 1e-4 で最大 200 epoch。同じ収集の 2 割 (約 200 件) の検証 MSE が最小の epoch を採る。独立 fold の実測で
   checkpoint を選ぶ S7 の手順 (`adapt.select_checkpoint`) は cheap には無い。
3. 単一チームでは相手の特徴が似通い、選出 120 通りの違いは特徴量の一部なので、ノイズの多い少数の標本では**そのチームの平均勝率**を
   学ぶ方が損失を下げやすい。120 通りの予測勝率の差 (順位の情報) が平らになるか、ノイズで入れ替わる。検証 MSE の改善 (gain_pct) は
   選択に使った同じ 200 件で測るので楽観的で、崩れを検出しない。
4. 配布版 (以前の my_team の 5,000 戦で微調整) が汎用より 0.09 高いのは、標本が多く、別のチームでも順位の情報が残っているため。

確かめ方 (実データ、対戦は不要): `python -m tools.team_build.experiments.cheap_drift --run-id improve_20261006_0128 --arm reference`。
汎用と cheap の 120 通りの点を相手ごとに比べ、広がりの比 (spread_ratio)・順位相関 (rho)・最良の一致 (top1_same)・平均の差 (shift) を出す。
広がりの比が 0.5 未満なら「平ら」、順位相関が 0.5 未満なら「入れ替わり」。`advisors/reference_screen/adapt_report.json` の gain_pct / improved も
一緒に見る (improved が真なのに平らなら、仮説のとおり)。

直し方の案 (判断待ち):
- (a) 較正の標本の variant を cheap から generic に (`BUILD_CALIBRATION_VARIANTS`)。較正に使う Δ を、順位の崩れたモデルで測らない。安い。
- (b) `adapt_candidate` に崩れの門: 微調整後の 120 通りの広がりが起点の半分未満なら起点の重みに戻す (報告に rejected: flattened)。
  cheap と S7 の両方に効く。収集の対戦は増えない。
- (c) cheap にも独立 fold の実測 (100 戦) で「起点より悪くない」ことを確かめる。確実だが腕ごとに +100 戦。
実装側の推奨は (a) を今の run の次から、(b) を cheap_drift の結果で仮説が確かめられたら。
