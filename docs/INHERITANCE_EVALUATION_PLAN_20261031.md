# 新プロジェクトへの引き継ぎ価値を判定するテスト設計

作成: 2026-10-31 / 初版で調査したコード: `3aac679a`。**初版作成時点では設計のみ**。実施結果と追加判断は `docs/inheritance_eval/` および各レビュー文書を参照。2026-11-02の追加要件は§11、学習コストを重視した実装方針の更新は§12。

## 1. 目的と判断の単位

外部の強い実装を中核にする新プロジェクトに、現在の資産を持ち込む価値があるかを調べる。
目標は、利用者1人のChampionsシングルにおける操作・選出・構築能力。M1・16GBのMacBook Air 1台を前提とする。
利用者を増やす実験、大規模な追加学習、全機能の移植、実戦勝率の人間による長期A/Bは要求しない。

**データを保管する判断、コードを移植する判断、判断ロジックを採用する判断を分ける。**
例えば、対戦ログを残しても旧ロガー全体を移植する必要はない。記事の型を使っても記事収集システム全体は要らない。

| 判定 | 意味 |
|---|---|
| データ保存 | 出典・版・用途制限を付けて保管。新システムの実行依存にはしない |
| コード再利用 | 正確さ、効果または必要機能、分離可能性、資源条件を満たす |
| 最小部分を移植 | 必要な辞書・変換・記録などだけを取り出す。既存の制御全体は持ち込まない |
| 外部実装／簡易実装に置換 | 同等以上の目的を小さい負担で達成できる。旧資産は比較資料として保存 |
| 保留 | 正解、外部基準、標本数、時間のいずれかが不足。良いとも悪いとも判定しない。初期移行には含めない |

「不採用」は初期移行の対象外という意味で、元ファイルの削除ではない。
既存テストの全合格、コード量、独自性、旧システム内での改善だけでは再利用を決めない。

## 3. 共通の比較方法

### 3.1 外部の基準 B0

操作・選出・構築ごとに基準を定義する。操作の強いエンジンがあることから、選出・構築の基準も完成しているとはみなさない。

- **B0:** 対象ルールに対応した外部実装を、元来の判断経路・データ・探索設定で動かしたもの。
- **B0＋X:** B0に引き継ぎ候補Xを1つだけ追加／置換したもの。
- **M:** 必要な入出力だけを持つ最小の変換・表示・記録。自作の戦術的な補正は入れない。
- **OLD:** 現行システム。診断用の参考条件。B0を上回ることの代用にはしない。

事前条件として、外部の版、Championsの規制、能力ポイント、メガ、6→3選出、合法手を確認する。
未対応なら、その能力の有用性試験は保留。例えば外部に選出機能がなければ、簡易選出との比較は改善の診断にはなるが、外部上位並みの選出能力の証明にはならない。

B0が対象ルールで動くことと、求める強さを持つことも別に記録する。別世代・別形式でのレートや大会成績をChampionsでの実績に読み替えない。
本計画が直接判定するのは「固定したB0に対する引き継ぎ価値」。B0自体の対象ルールでの能力が未確認なら、上乗せが成功しても他システムへの総合的な比肩を証明したことにはならない。

B0自体の移植・対応変更と、既存資産Xの追加を同時に行わない。対応修正が必要なら、その修正版を固定してから比較する。
旧採点で候補を削った後にB0へ渡すことや、外部の推奨を旧スコアで上書きすることを、無改変のB0と呼ばない。

### 3.2 正解を3種類に分ける

1. **事実の正解:** その時点の映像、登録済み自分の型、独立に生成した対戦状態から確認できる値。
2. **ルールの参照:** 対象mod・commitを固定したShowdownの遷移・合法性判定。実機固有の食い違いが疑われる場合は争点として残し、Showdownを無条件に真実とはしない。
3. **強さの証拠:** 条件を揃えた対戦結果。外部AIの一手や、そのAI自身の評価値を絶対的な最善手・真の勝率とは扱わない。

状態の正解には、観測できた事実と本来隠れている情報を分けて保存する。
試験対象に渡すのはその時点でプレイヤーに分かる情報だけ。後で判明した技・持ち物・選出を過去の入力へ戻さない。
シミュレーターの完全状態は採点側だけが保持し、方策や推定器には公開しない。

### 3.3 比較条件、偶然性、データ漏れ

- 自分と相手の構築・型、先後／側、相手方策、規制、データ、seedの束、時間予算を固定する。
- 相手方策を評価中に学習させない。X以外の自分の選出・操作も固定する。
- 同じ対戦・連続フレームを独立標本として数えない。誤差区間は対戦／セッション、構築試験は依頼・生成runも単位にする。
- 分割は対戦・セッション単位。構築生成の確認相手は生成・選別に使わない。
- 既存の失敗例は修理用。新規確認集合と混ぜない。過去に開発で広く使用したデータは「過去データ診断」と表示する。
- 同じseedでも行動が変われば乱数の消費順が変わる。同一の展開を保証しない。対応する対戦設定として扱い、実測した分散から区間を出す。
- 探索の反復数固定は入出力の再現性用、実時間固定は実用性能用。両者を混同しない。
- 出力一致率は情報の欠落検出に使う。違う手を選んだだけでは劣化と判定しない。

対戦の一次指標は勝ち1・引き分け0.5・負け0の平均対戦スコアとし、以下では便宜的に「勝率」と記す。勝敗・引き分け件数も別に出す。
AI側の時間切れ・不合法出力・クラッシュによる敗北を除外して良い成績にしない。共通の試験基盤の障害は、事前の分類規則で対応する両条件を無効として記録し、同じ設定で再実行する。費用上限で打ち切った未完了試合は未完了として残し、予定n未達の正式採用判定はしない。
相手には、利用者が遭遇する構築群と固定した操作方策を使う。1種類の相手方策しか動かせない場合は、その相手に対する結果と明記する。B0同士のミラー戦だけから人間相手の強さを推定しない。

### 3.4 採否の規則と暫定の数値

以下は**提案する初期値**であり、実測済みの性能やユーザー承認済みの仕様ではない。
試験の内容と予算を決める時点で固定し、結果を見て緩めない。旧システムの閾値を自動継承しない。

| 用途 | 採用候補にする条件 |
|---|---|
| 入出力・保存・変換など、判断を変えない部品 | 対象範囲の契約テストで意味の欠落・誤変換・不合法化0件。必要機能を満たし、最小実装より移植・運用の負担が小さい |
| 判断を改善する任意機能 | 確認試験の勝率差の推定値が **+5ポイント以上**、補正後95%区間の下限が0超。これは真の差が5ポイント以上との証明ではない |
| 同等の強さで高速化する任意機能 | 対応する処理時間を **20%以上削減**し、勝率差の区間下限が **−3ポイントより上**。差が有意でないだけでは同等としない |
| OCR・UIなど必要な接続機能 | 事実と行動の対応、期限、訂正可能性の受入を満たす。強さの上乗せを要求しないが、必要だから旧実装を必ず残すわけでもない |
| 標本・正解・外部基準が不足 | 保留。初期移行しない。必要機能なら最小代替を選び、未検証範囲を明示 |

勝率差は同じ相手設定の差を保持し、対戦単位（必要なら相手構築を上位単位）のbootstrap等で求める。
1つの機能の正式確認は、予備試験で固定した候補1つとB0の2条件を基本とする。
複数の正式比較から採用を選ぶ場合は、比較群と数kを先に固定して区間水準を `1−0.05/k` にする。
予備段階で試した全条件も記録し、正式確認のデータで再調整しない。

少数試合で「差がない」と証明することはできない。上の精度が資源内で得られなければ保留でよい。
例えば勝率50%付近、独立な2条件各100戦の差の95%区間半幅は概算14ポイント。600戦でも約5.7ポイントで、対応比較による改善幅も実測次第。
試合数だけから検出力を約束しない。

## 4. 用意する小さな検証セット

| セット | 初期規模と選び方 | 用途・制約 |
|---|---|---|
| F: 事実確認 | 既存画像から60決定、可能なら12対戦以上・3セッション以上。助言成功に依存せず時間・場面で抽出 | 状態・合法手・不明欄を人が確認。判読不能を捨てず別区分にする。満たせない件数は不足と報告 |
| R: 既知の失敗 | 既存30局面のうち根拠画像を確認できたもの＋事故記録 | 修理・回帰専用。Fの発生率や確認成績に混ぜない |
| S: ルール境界 | 80件を上限とする小さな独立fixture群 | HPのKO境界、交代、持ち物消費、形態、行動制約など。カテゴリ別の未対応を残す |
| C: 連続入力 | 初期は選出2本＋対戦4本、各30〜60秒 | 今は未確保。冒頭の観測可能な状態を与えるか十分な前段から再生。疎な画像の繰り返しでは代用不可 |
| P: 選出 | 自分の登録構築＋今後使う候補2構築、相手20構築を上限 | 選出モデルの学習に使われた相手か記録。不明なら診断用。最初から全組合せの大量対戦はしない |
| B: 構築依頼 | 自由、好きな1体固定、2体の核固定、現構築の2枠まで変更、の4依頼 | 形式・禁止・固定型・生成時間・返す候補数を揃える。実際の本人の希望で事前固定 |

Fは開発用・確認用を対戦単位で概ね半分にする。60決定で小さな誤り率を精密に推定できるとはしない。
頻出場面の一般抽出と、メガ・へんしん等の稀な境界を意図して集めたR/Sの結果は別表にする。
既知の失敗30件は今は正解未記入。`consistent` の分類を「正しい状態」と解釈しない。

## 5. 引き継ぎ候補ごとの試験

### I-00 データ・モデル・実験記録の保存価値

対象: 実戦ログ、画像、登録チーム、使用率snapshot、記事バンク、構築run、モデル、失敗記録。

- 全件のファイル一覧・hash・形式・規制・時期・生成元・重複・読取可否を集計する。DBは一貫した読み取り用snapshotを使う。
- 各形式から少数を選び、当時の自分の型、状態、使用モデル、結果をどこまで復元できるか確認する。
- `観測事実 / 推定値 / 生成物 / 実対戦結果 / 合成結果` を区別する。AI推奨は正解ラベルにしない。
- 指標: 用途ごとの使用可能件数、欠損理由、重複率、復元可能な決定数、保存容量、取り出しの手数。
- 判定: 正解・失敗再現・候補セット・比較基準のいずれかに使える範囲をデータ保存。復元不能でも事故調査用の保存は可。モデルは対応する特徴量・埋め込み・規制まで揃った場合だけ実行試験へ。
- 成果物: 資産台帳。元データは変更しない。保存価値の確認のために全モデルを対戦させない。

### I-01 日本語辞書・型登録・名前／単位／形式の変換

対象: `vision/normalize.py`、日本語辞書、`advisor/my_team.py`、登録・Showdown形式変換。

- 比較: 現行変換を切り出したもの vs 外部の標準変換＋最小の日本語対応。
- 入力: 登録構築の全個体、Sの形態・単位境界、表記揺れ、未知名、欠損値。対象規制の使用種・技・持ち物の名前対応を全走査する。
- 期待値: 手で確認したcanonical ID、対象modから取得した実数値、元の型。逆変換でも種・形態・技・持ち物・特性・性格・能力ポイントを保持。
- 重点: 能力ポイント0〜32と従来EV表記を混ぜない。通常／メガ、両陣営の同種、性別形態を分ける。不明名を別種へ黙って置換しない。
- 採用条件: 正確な入力の誤変換0件。曖昧な入力は確認待ち／不明として保持。曖昧さを残す機能と、不要な複雑さを分けて最小移植を選ぶ。
- 正しい出力を再現できるだけで、OCR誤読への強さまで認めない。後者はI-02で測る。

### I-02 OCR・画像認識・イベント追跡

対象: `vision/` の画面分類、名前、HP、技、選出、イベント、状態追跡。

- 比較: 現行一式 vs 固定ROI・基本OCR・明示的な訂正を使う最小経路。手作業で正した観測状態は上限参考として保持。
- Fでは観測可能な項目の正確さ、未知を誤って確定した件数、判読不能、決定単位の状態完成率を測る。
- HPは自分の数値HPと相手の表示割合／バーを分ける。整数％表示を正確な内部HPとしない。誤差とKO境界を誤る件数を併記。
- Cではイベントのprecision/recall、個体への帰属、状態への反映遅れ、交代や対戦終了でのリセット、手動訂正の保持を測る。
- 入力が欠けた後の回復も試す。HP、アイテム喪失、技固定、メガ、選出不明を古い確定値で埋めない。
- 暫定受入: 重大な誤確定（別個体・非選出への交代可・ひんし誤認・選べない技を可にする）0件、F/Cの決定窓の95%以上で期限内に必要状態が揃う。未確定や出力なしも分母に残す。0件は真の事故率0の証明ではない。
- 下流確認: 同じB0に正しい観測状態と認識状態を渡し、入力差のある決定を点検する。手の不一致は感度であって、そのまま誤答率ではない。
- 判定: 精度が足りる最小経路を選ぶ。個別の正規化・イベント辞書だけ有効ならそこだけ移植。C未確保なら時間方向の性能は保留。

### I-03 状態表現・外部エンジンへの接続

対象: `vision/state.py`、状態辞書、`advisor_player.py`、`rl_bridge.py`等の変換の考え方。

- 比較: 独立fixtureから外部へ直接与える経路 vs 同じ情報を旧状態表現経由で与える経路。
- SとFで、個体ID、側、HP、選出／非選出／不明、技PP・制約、消費／喪失アイテム、天候、壁、ランク、形態、履歴をフィールド単位で照合。
- 陰性試験: 後で判明した情報だけを変えても、それ以前の入力は変わらない。対戦を続けても前試合の推定・キャッシュは残らない。
- 再現性試験はseed・反復数・スレッドを固定。固定できないエンジンはB0の反復による揺れを先に測り、単発の一手一致を要求しない。
- 採用条件: 観測可能情報・合法行動の意味的な損失0件、未来／隠れ情報の混入0件。対応しない欄は明示し、暗黙の既定値で通さない。
- 判定: 旧状態を通すと情報が落ちるなら外部の状態を中心に新しく接続する。旧表現の維持を移行の条件にしない。

### I-04 使用率・相手バンク・型推定

対象: 使用率DB、`advisor/sets.py`、`ev_infer.py`、Smogon変換、実戦相手バンク・選出事前分布。

- 事前分布と観測による更新を分ける。まずB0の事前分布 vs 既存DBを比較。その後、事前分布を揃えてB0の更新 vs 既存推定器を比較する。
- 実ログでは判明直前の入力だけで予測し、後に確認された値で採点。月次統計は公開・取得前の対戦へ使わない。
- 指標: 判明した持ち物・特性のlog loss、候補集合の真値被覆、種の欠落率、予測不能率、強すぎる確信の誤り、推論時間。
- 技は保有確率と選択確率を分ける。未観測技を不採用としない。判明値だけの評価には観測されやすさの偏りがあるため「判明部分での成績」と表示する。
- 配分・見えない技を含む全状態の較正は、真の相手型を採点側だけが知る独立の合成ケースで補う。合成分布が実環境を代表する保証は別問題。
- 推定器は矛盾する観測、消費済みアイテム、へんしん、種・枠の対応変更をSで検査。誤った観測を確定的に信じて真の型を除外するケースを記録する。
- 実ログの改善だけでは行動への採用を決めない。改善した候補1つだけをB0に接続し、同じ探索時間で判断能力／速度を共通規則で確認する。
- 判定: DBの型候補だけ有用ならデータだけ移す。外部推定より良くない、または根拠不足なら旧推定器は初期移行しない。

### I-05 ダメージ計算・独自遷移・合法性と型の「常識」規則

対象: `advisor/damage.py`、`transition.py`、効果表、`tools/team_build/set_lint.py`、型の自動修理。

- 正しさ: Sの同じ状態・行動について、固定した対象modの遷移と照合。乱数は可能なら全分岐と確率を比較する。単に観測ダメージがmin〜max内にあるだけでは合格にしない。
- 参照を列挙できない効果は検証済みにしない。既存 `dmg_compare` が除外・近似する効果は別fixtureを用意する。
- 性格・持ち物・技が合法かと、戦術的に好ましいかを分ける。外部の合法性検証＋形式変換だけの条件を対照にする。
- 固定した合法セット集に旧lint／自動修理を適用し、拒否・変更された型、理由、形態・制約の破壊を全件列挙。合法でも誤りとは限らない例（特殊型の先制物理技、こだわり＋変化技等）を含める。
- ルール上不合法な型を通すことや、指定した型を黙って変えることは0件を要求。戦術的な型の拒否・修理は、I-07で構築結果を改善できるまで警告止まりの候補とする。
- 判定: 外部が同じ機能を提供するなら、正確さだけを理由に二重のエンジンを持たない。外部に欠ける効果の検証素材、名前辞書、必要な変換を優先して移す。

### I-06 選出モデル・選出規則

対象: 汎用／登録構築向け選出モデル、規則選出、相手選出の予測。

- 比較: 外部の選出方式 vs 既存モデル1つ。操作は両条件とも同じB0、相手も固定する。モデルの再学習は初期試験に含めない。
- Pで入力・特徴量・埋め込み・モデル版の整合を検査。全120順列の出力を合法な選出へ変換できるか確認する。
- 先発が同じで控え2体の順だけが違う出力は、実際の形式で同値なら同一選出として集計する。選出モデルの予測勝率を真の勝率としない。
- 安い予備試験: 登録構築と候補構築別に、選出の違い、違法出力、推論時間、推定の極端さを確認。人が過去に選んだ3体との一致は強さの指標にしない。
- 有用性: 予備段階で候補を1つに固定し、同じ相手設定で試合開始時の選出だけを変える。操作方策・探索時間・自分の型を固定して共通の採否規則を適用。
- 判定: 登録構築だけに効果があれば、その構築hash限定で採用候補。未知の構築への強さを主張しない。モデルが新しい操作方策と合わなければ保留／置換。
- 相手選出予測は全3体が確認できたケースで別評価。実際に登場しなかった個体を非選出とラベル付けしない。

### I-07 構築候補生成・絞り込み・修理・記事の型

対象: `gen_sets`、`role_sets`、`lineup_search`、被覆評価、repair、記事・上位構築の種、LLM構想。

- 初期はLLMなし。後で試す場合も1つの任意候補として、呼出時間・料金を含めて比較する。
- **生成の比較:** B0の生成 vs B0へ既存の型／核候補を加える。Bの同じ依頼、固定枠、型、合法性、壁時計時間、最終候補数（初期上限8）で比較。
- **順位づけの比較:** 候補集合を同一にして、外部の評価 vs 旧被覆評価を比較する。候補生成の差を混ぜない。
- **修理の比較:** 同じ親・変更可能枠・変更数・候補数・予算で、旧診断に基づく修理 vs 制約内の単純な変種生成。直す型と変える種の範囲も揃える。
- **記事の価値:** 出典・規制・型が検査できる記事の候補を追加。元記事を複製した別URLは同じ系列とし、本数を遭遇率にしない。記事parser全体の移植判断とは分ける。
- 安い指標: 制約充足率、合法な異なる型／並びの数、生成時間、重複、候補打切り、旧lintで消えた外部候補、生成集合の欠落。
- 価値指標: **同じ総計算時間で返した最終構築**を、選別に使わない相手・seedで同じ操作／選出方策に使わせた成績。予測値や相関だけでは採用しない。
- 予算は生成・順位づけ・シミュレーション・必要な適応・失敗再試行を合算する。事前学習済みモデル利用と今回の追加学習費用は区別する。
- 依頼4件は予備診断。見込みのある1つの変更だけを正式確認し、確認する依頼・生成seed・相手は予備と分離する。1依頼の成功を汎用的な構築力としない。
- 判定: 候補の型だけ効けば型データだけ移す。探索・修理の採用はそれぞれの上乗せを確認した場合のみ。既存S0〜S13を一括移植しない。

### I-08 旧行動方策・採点・探索・終盤評価

対象: PPO、RLブレンド、legacy、transition、endgame、独自search。

- 最初の用途を1つに限定: B0の代替、時間制約時の代替、探索の補助、のいずれか。用途のない部品は保存だけ。
- R/Sと登録構築由来の観測局面で、合法性、対象効果、時間を確認。既知の短い詰め局面で正解を確かめられるものだけ別に採点する。
- B0と手が違うこと、旧AI相手に勝つこと、自分の評価値が高いことを採用根拠にしない。
- 予備で用途を満たす候補だけを、同じ選出・同じ相手・同じ時間予算で正式比較。旧ルールとB0の混合比を大量探索しない。
- 特定局面だけ切り替えるなら、適用条件を確認試験前に固定する。失敗した局面を見て選んだ条件の効果は、その局面集では確認できない。
- 判定: 効果か必要な速度を示せなければ旧判断系は持ち込まない。単に単体で動くことを再利用価値としない。

### I-09 表示UI・手動訂正・キャッシュ・安定化

対象: `index.html`、`advisor/service.py`、`advice_key.py`、サーバーの表示・入力制御。

- 比較: 同じB0の推奨を出す最小UI vs 既存UI。判断内容を固定し、伝え方と操作だけを比べる。
- 自動試験: 応答逆転、途中の交代、対戦終了、タブ非表示、再接続、手動訂正、同一ターンのHP／技固定更新を注入。新状態に古い推奨を表示しないことを確認。
- キャッシュは更新キー・有効期限・訂正後の再計算を個別に確認。据え置き／安定化が新しい推奨を抑止する場合、その機能を外した条件と分ける。
- 期限: 決定画面を人が確認した時刻を起点とし、生成とブラウザ描画完了を分ける。サーバーのemit時刻だけで表示完了としない。時計差を補正する。
- 暫定の入力余裕は締切前5秒。利用者本人の短い操作課題で実測して実施前に固定する。旧p95≤3秒を新しい探索エンジンに自動適用しない。
- 暫定受入: 誤った個体・行動の対応、古い局面の推奨表示、訂正の意図しない上書き0件。全決定窓を分母に期限内有効表示95%以上。Xによる接続処理の追加p95は0.5秒以内を初期目安とする。
- 本人の確認: 違うが同程度の24課題を2UIに割り当て、順序を入れ替える。「指定された推奨を読み取り入力」「状態を訂正」を行い、誤操作・所要時間・手数を記録。勝率や一般利用者への効果は推定しない。
- 判定: 同じ機能を簡易UIが少ない負担で満たすなら置換。手動訂正等だけ良ければそこだけ移植。

### I-10 ログ・版固定・再生・実験管理

対象: `battle_logger.py`、`advisor/versions.py`、`data_pin.py`、registry、manifest、再生・集計。

- 比較: 既存の必要部分 vs JSONL＋小さなmanifest＋明示したファイル経路による最小記録。
- 同じ観測状態・推奨・表示イベントを保存し、空の一時ディレクトリから復元。モデル・DB・登録チームの参照を事前に固定する。
- 原本DBを更新した想定、モデルの欠損、hash不一致、途中行の破損、途中停止・再開を試す。指定版が無いとき最新へ黙って退避しない。
- 誤った勝敗・候補・版・費用を集計に入れた場合に検出できるか、既知の値を持つ小さなfixtureで確かめる。再試行や失敗を成功数から消さない。
- 採用条件: 記録した意味の欠落0件、版違いを検出、原本変更なし、集計結果が独立に数えた値と一致。
- 必要な再現性を達成するための依存数、設定項目、移植作業時間、記録量を比較。shadow／canary等の全管理体系は必要性を確認してから判断。
- 判定: 勝率改善は要求しない。小さなmanifestで十分ならそこまで縮小する。

## 6. 全候補に共通する「切り離せるか」の試験

コード再利用の候補だけを、一時ディレクトリの小さな実行パッケージにコピーして確認する。

1. 元リポジトリをimport経路から外し、指定したコード・データ・依存だけで対象機能を実行する。
2. 入力・期待出力・乱数・時計を固定し、元コードの対象範囲と比較する。
3. 元の `config/my_team.json`、配布モデル、ライブDB、ログ、環境変数への暗黙のアクセスを検出する。
4. インポートだけでネットワーク取得、学習、Showdown起動、常駐処理、元データへの書き込みをしないことを確認する。
5. 必要な依存・設定・修正箇所と、実際に費やした移植時間を記録する。

最初の切り出しは候補1つにつき人の作業2時間を上限とする案。超えたら継続の価値を再判定し、際限なく既存設計を修復しない。
外部実装にも同等の接続作業が必要なら、両方の作業量を記録する。行数の少なさだけでは判断しない。
部分移植後は該当するI-01〜I-10を再確認する。切り出し前の合格をそのまま引き継がない。

## 7. Mac1台での実施順・費用の上限

### 段階A: 外部AIを動かす前にできる整理

- I-00、I-01、I-05の型検査、I-10の記録契約、Fのラベル作成。
- 初期予算案: 自動処理は合計2時間、人のラベル・確認は合計2時間。超過分は未確認として次回へ分ける。
- Sのfixtureは再利用予定の機能に必要なものから作る。全効果の網羅テストを新規開発しない。
- この段階で、保管するデータ、移植不要な重複機能、検証不能なモデルを分ける。

### 段階B: 外部の基準を固定して安い比較

- B0の対象ルールでの動作確認、I-03の入力接続、I-02の下流確認、I-04/I-06/I-07/I-08の予備診断。
- 最初は同時実行1つ。探索時間の候補を局面あたり0.25 / 1 / 3秒など少数に固定して計測し、実用条件を選ぶ。これらは速度測定用で、短縮条件の強さを通常条件と同等とみなさない。
- 時間・メモリはプロセス群全体で記録する。OCRと探索の競合は別の負荷試験で確認。
- Cが揃えばI-02/I-09を行う。静止画の反復送信は負荷試験にだけ使い、イベント認識の精度測定には使わない。
- 初回の外部推論による予備診断は合計90分を上限とする案。移植・依存導入の作業時間は別に記録する。

### 段階C: 有望な候補だけ確認

- 最初の一巡では **判断能力を変える正式比較は1本だけ**。予備診断の効果、必要性、費用を見て事前に選ぶ。
- 試験本体を始める前に最大20分のスループット予備計測を行う。局面推論の時間だけから試合数を見積もらない。
- `予測時間 = 実測した完了試合あたり時間 × 条件数 × 予定試合数 + 起動・保存等の費用`。両者が探索する場合は相手側の時間も含む。
- 本体の機械占有は1比較6時間を上限とする案。予備の分散と速度から最終nを先に固定し、最終時点で1回判定する。
- 時間上限で未完了なら未完了。試験中の良い成績で早く止めて採用しない。追加する場合は計画変更として扱い、同じデータを都合よく再検定しない。
- 目標差を識別できない見積もりなら、対戦を始めず保留も可。旧基準の600戦を全候補に課さない。
- 生成の正式比較では依頼・生成の反復が必要。1構築の対戦数だけを増やして、生成器の再現性を代用しない。6時間に入らなければ対象依頼を限定するか保留。

実施は接続テスト・学習・他の構築測定と重ねない。既存プロセスをこの計画のために自動停止しない。
AC接続・省電力設定・同時処理数を記録し、A→B→B→A等で順序を均す。ウォームアップを分け、終盤の処理速度低下も残す。
メモリ圧迫や継続的なswap増加が出る条件は、そのまま常用可能と判定しない。

## 9. 試験記録と最終成果物

実施時の出力案は `logs/inheritance_eval/<run_id>/`。原本の実戦ログ・DB・登録チームには書かない。

```text
manifest.json        # コード・ルール・モデル・データのhash、条件、seed、時間予算
assets.jsonl         # 資産ごとの用途・読み取り可否・不足・移植依存
cases.jsonl          # 入力・公開情報の境界・期待値・出典・開発/確認区分
measurements.jsonl   # 全件。失敗・未実施・時間切れ・除外理由も残す
report.md            # 指標と区間、重大な不一致、費用、判定と対象範囲
```

試験前に埋める最小の仕様:

```json
{
  "test_id": "I-06",
  "asset": "既存の登録構築用選出モデル1つ",
  "role": "新しい操作方策の下での選出",
  "baseline": "外部選出方式の固定版（未確定なら試験開始不可）",
  "changed_component": "選出のみ",
  "fixed_components": ["操作方策", "相手方策", "自分と相手の型", "規制", "時間予算"],
  "primary_metric": "対応する試合設定での勝率差",
  "minimum_point_gain": 0.05,
  "confirmation_comparisons": 1,
  "final_n_per_condition": null,
  "machine_budget_hours": 6,
  "stop_on": ["条件不一致", "入出力の重大な不具合", "費用上限"],
  "confirmation_set": null,
  "status": "設計・未実施"
}
```

`final_n_per_condition` と確認集合が未確定のまま正式試験を開始しない。
最終報告は部品ごとに「用途 → 対照 → 正しさ → 効果 → 費用 → 採否 → 未確認範囲」を1行にまとめ、根拠へリンクする。
「旧モデルを保存する」「型データだけを移す」「UIを置換する」を別の判定として残す。

## 10. この設計の到達点

最初に決めるのは、**何を捨てるかではなく、何を新システムの実行依存にする根拠があるか**。
データと失敗事例は安く保管し、必要な接続機能は正確さと負担で選び、判断を変える機能には上乗せの証拠を求める。
確認できなかった機能を全部移植してから評価する順序にはしない。
