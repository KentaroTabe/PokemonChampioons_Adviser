## 0. 判断の軸と資源

### 0.1 3 つの区分 (一覧の区分を採用)
- **正しさ**: 仕様・入力事実に合っているか → 壊れていたら直す。有用性の実験はしない (§10)。
- **有用性**: 単純な方式より判断・成績・作業が良くなるか → 比較条件を揃えた測定で決める。
- **費用対効果**: 改善が計算時間・遅延・学習費用に見合うか → 測定に費用の欄を必ず付ける。

### 0.4 データ分割の用途 (レビュー指摘 1)
season_pin (10/7 作成、seed 20261005) は相手の系統を **search / selection / holdout** の 3 層に分けている (`tools/team_build/opponents.py` の tiers)。
用途を次のように固定し、**最終評価用の holdout は、方式やモデルを選ぶ繰り返しの比較には使わない**。

search 層はさらに 3 つの fold に分かれている (`BUILD_SEARCH_FOLDS=3`、`champions_agent/config.py`): **A = 選出モデルの適応データの収集、
B = 適応後の比較 (S8a / S8b)、V = checkpoint 選択の検証** (`BUILD_FOLD_ADAPT, BUILD_FOLD_EVAL, BUILD_FOLD_VALIDATE = 0, 1, 2`)。S10 の候補比較は selection、最終評価は holdout。
この既存の割当を維持し、本計画の実験は次の層・fold を使う (2 回目のレビュー指摘 1)。

| 用途 | 使う層 / fold | 繰り返し使用 |
|---|---|---|
| 選出モデルの適応 (データ収集) | search の fold A | 既存のまま |
| 選出モデルの適応の checkpoint 選択 | search の fold V | 既存のまま (200 戦、`BUILD_ADAPT_VALIDATE_N`) |
| RL 加点・選出方式・採点の構成要素など「方式」の比較 (§4、§5、§7)。登録チーム専用モデルの評価を含む | **search の fold B** (search 全体で測ると適応に使った fold A が混ざる) | 可。同じ比較を繰り返して良い方を選ぶと上振れするので、比較ごとに seed を変え、結果は全部記録する |
| 構築 run の候補比較 (S10) | selection | 既存のまま |
| 将来の行動 RL 学習の checkpoint・EMA の選択 (§3) | **学習相手に入っていない検証集合を学習開始時に明示的に指定する** (層の名前が「selection」であることは未使用の保証にならない。学習相手の構成と検証集合の系統 id を training_changes.json に書く) | 可 |
| 方式とモデルを固定した後の最終確認 (構築の採否と同じ) | holdout | **1 回だけ**。ここで方式を選び直さない |

§3 の旧記述「checkpoint ごとに holdout で評価して更新を決める」と §5 の旧記述「holdout で汎用と規則のどちらを使うか決める」はこの規則に反するので改めた。

### 0.5 採否の規則 (レビュー指摘 2)
各実験は始める前に次の 5 つを書く (§4 以降の表の「方法」欄に略記し、実験の記録ファイルに正式に残す)。

| 項目 | 既定 (実験ごとに変えてよい。変えたら理由を書く) |
|---|---|
| 主指標 | 対応比較の勝率差 (同じ相手列・同じ seed で条件だけ変える)。**試行のペアを保持して差の区間を出す** (対戦 i の勝敗の差 d_i ∈ {−1, 0, +1} の平均と、その bootstrap または正規近似の区間。各条件の Wilson 区間を別々に出すだけでは足りない)。副指標は決定的な場面の第一候補の一致率など |
| 実用上意味のある最小差 (MDE) | 0.05 (助言の採点・選出方式)。構築の採否は従来どおり holdout の verdict |
| 最終対戦数 (事前に固定) | **600 戦 / 条件**。採否はこの n に達した時点で 1 回だけ判定する (逐次判定をしない)。対応差の区間半幅は実測の分散から 300 戦 ±0.06、1,000 戦 ±0.035 (`config.py` の `BUILD_PICK_ABLATION_N` の注記) なので、600 戦で ±0.045 程度 |
| 中間確認 (300 戦) | 採否を決めない・止めない。費用の見積もりの更新と異常 (条件の取り違え、崩れた対戦) の確認だけ。費用上限は 1 実験 2 時間 (予備試験の予算) |
| 複数比較 | 基準条件に対する比較が k 本 (例: RL 加点 0 / ×5 vs ×25 で k = 2) なら、区間の水準を 1 − 0.05 / k に上げる。最良を選んだ条件は、別 seed で 1 回再測して上振れを記録する (これは補足であって多重比較の解決ではない) |
| 採用候補 / 不支持 / 判定不能 | **採用候補**: 差の推定値が MDE (0.05) 以上、かつ補正した区間の下限が 0 より上。**実用的改善を支持しない**: 区間の上限が MDE 未満。**判定不能**: それ以外 = 現状維持。「区間が 0 より上」だけでは 0.02 の差でも採用になり MDE と矛盾する (2 回目のレビュー指摘 2)。これは「真の改善が 0.05 以上と証明した」という意味ではなく採用判断の基準 |

**開始前に固定して記録する項目**: 比較数 k と基準条件、対象チーム (登録チームの sha)、モデル版 (選出モデル・RL の checkpoint の sha、pin)、相手の層と fold (fold B)・相手列の seed、最終対戦数。
**未完了**: 2 時間以内に 600 戦に届かなかった実験は採否を出さない (未完了として記録し、次の夜に同じ条件で続きを測るか、予備測定の結果から開始前に層別実験を分ける)。
この予算 (600 戦、2 時間) では、真の差が 0.05 前後の条件は**判定不能になることが多い前提**で扱う。判定不能が続く機能は、費用対効果の欄で「測るのをやめる (G)」か「専用の大規模測定 (D)」かを別に判断する。

「件数だけ」の規則は使わない。「10 戦で第一候補が変わらなければ `model_pick_real` を外す」は表示を整理する運用判断 (有用性の判定ではない) として残し、
「10 run で較正規則を見直す」は較正標本の測定件数 (捨てた並びの測定 40 本以上) で区切る。

## 1. 着手順と時期

### 1.1 段 0: 評価の土台 (10/7〜次の接続テストの前。2〜3 日、実装はサブエージェント)

### 1.2 段 1: 実戦経路 (次の接続テスト 3 回、10 月中旬まで。約 40 戦)
影の記録 (RL 加点の有無・選出候補 3 種・相手の選出予測) を残す。40 戦たまったら C の再分析 (§4.2、§5)。
同じ期間に、run の無い夜に D の 2 本 (§0.5 の規則: 最終 600 戦 / 条件、300 戦は中間確認のみ): **P1 (RL 加点 0 / ×5 / ×25)** と **選出方策 (規則 / 配布 / 登録チーム専用)**。
どちらも **search の fold B** で測り、方式を決めた後に holdout で 1 回だけ確認する (§0.4)。1 実験 1 夜 (各 ≈ 1.2 時間 + 予備測定)。

### 1.3 段 2・段 3: 構築 run への相乗り (1 run に主仮説 1 つ、追加は合計 +3 時間まで)
毎 run に全部を載せる方式はやめ (レビュー指摘 7)、**run ごとに検証する主な仮説を 1 つ選ぶ**。費用は「条件数 × (候補 + 参照) × 対戦数 + 学習時間」で積み上げ、
段 2 と段 3 を合わせて 1 run あたり +3 時間を上限にする。常時載せるのは費用 0 のもの (較正標本は実装済みなので既定のまま) だけ。

| 相乗りの候補 (1 run に 1 つ) | 既存の仕組み / 足すもの | 対照の揃え方 | 費用の積み上げ |
|---|---|---|---|
| 較正標本 (捨てた並びを S8a だけ測る) | `BUILD_CALIBRATION_SLOTS=4`、`BUILD_CALIBRATION_VARIANTS=("generic",)` (実装済み) | 捨てた並びと通った並びを同じ S8a の条件で測る。種・技・型の段階で消えて並びにならなかった候補は入らないので、別途「絞り込みを一部緩めた小規模探索」(§6) が要る | 4 枠 × 100 戦 ≈ +0.7 時間 (常時) |
| 予備評価で早く落ちた腕の追い測定 | 無い → S8a の脱落腕を `--candidates` で続きを測る段を足す | 通った腕と同じ対戦数 (300) まで続ける | 3 腕 × 300 戦 ≈ +40 分 |
| S9 (修理) の対照 | 無い → S9 と同じ親から作る無作為変種を足す | **親・変更枠数 (S9 は `BUILD_REPAIR_MIN_CHANGES=2` なので対照も 2 枠)・型変更の範囲・候補数・測定予算を揃える**。「無作為 1 枠入替」では診断の有無と変更規模が混ざる (レビュー指摘 5) | 3 腕 × 100 戦 ≈ +15 分 |
| 同時探索 joint と従来 legacy の両方 | `--search-mode both` (実装済み) | 両方の最終候補を同じ測定に入れる。増えた候補の測定費用を数える | 探索段 +10 分 + 増えた候補 × 300 戦 (約 +40 分) |
| 相手の操縦 heuristic / rl、相手プール latest / mixed、相手の選出方策 規則 / model | 最終候補 (`BUILD_FINALISTS=3`) を条件を替えて測り直す | **同じ条件で参照チームも測る** (条件が変わったときの登録チームとの差を出すため。レビュー指摘 5)。mixed は構築に使っていない後続の実戦データで評価する | 1 軸: (3 候補 + 参照) × 2 条件 × 300 戦 ≈ +1.6 時間 (既存の条件の結果は再利用するので実質 +0.8 時間) |
| 選出モデルの変種 (規則 / 汎用 / production / fresh) | 参照の腕として毎 run 測っている (10/7: 規則 0.473 / 汎用 0.603 / production 0.533 / fresh 0.317) | 同じ参照チーム・同じ相手列 | 0 (記録を集計するだけ、常時) |

順位の相関 (過去 0.53) は補助指標にとどめ、各候補の「同条件の参照に対する差と区間」を中心に判断する。接続テストと重ならない夜に起動する。
相乗りの測定 (300 戦) は**診断** (条件を替えると候補の差が変わるか、取りこぼしがあるか) であって、方式の採否を §0.5 で決める実験ではない。構築の採否は従来どおり holdout の verdict。
相乗りの結果から方式 (相手の操縦、プール、絞り込みの閾値) を変える判断をするときは、専用の D (600 戦 / 条件) を別に組む。

## 2. 接続テストで残すログ (段 0 で実装)

いま無いもの、または形を変えるもの。既存の行 (advice / display / events / outcome / rate / manual_fix / hp / version / session) はそのまま。
**実戦は比較の場ではなく記録の場**なので、どの行も「表示する助言」を変えない。

| 行・欄 | 内容 | 使う検証 |
|---|---|---|
| `advice_variant` 行 (advice 行とは別行、`advice_id` で紐づけ) | 同じ状態で RL 加点 0 / ×5 / ×25 (既定) の上位 3 と点差。**隔離条件** (レビュー指摘 4): (a) 採点の重みは環境変数ではなく関数の引数で渡す (`RL_BLEND_WEIGHT` を別スレッドから書き換えない。`check_advisor_player --no-rl-blend` も引数経由に揃える)、(b) 状態とモデル版を助言時点の snapshot に固定、(c) RL 加点より前の共通計算 (ダメージ・採点の基礎) を再利用し、**加点の後の KO 前割引・交代技補正まで再計算**する (最終点から RL 分を引くだけでは比較にならない)、(d) 待ち行列の上限 (既定 2 件) と破棄の基準は**状態の更新と期限** (助言の対象の局面が変わった、または生成から N 秒 (既定 3 秒) 過ぎた) で決める。10 fps では約 100 ms ごとにフレームが来るので「次のフレームが来たら破棄」では同じ状態でも捨ててしまい比較結果がほぼ残らない。**待機中の仕事を捨てる**と**実行中の計算を止める**を区別して数え、スキップ理由は advice_id ごとの `advice_variant` 行 (`skipped` / `skip_reason`) に残す (実装時の変更: frames 行はログ担当の範囲だったため。件数は advice_trace --variants で集計)、(e) 前面のページで通常のフレーム (10 fps) が届く条件で遅延の p50 / **p95** / max と**期限超過率**が悪化しないことを、接続テストの前に録画再生で確かめる | §4 RL 加点 (実戦で第一候補が変わる頻度と場面)。P1 のシム結果と突き合わせる |
| `selection_record` 行 (選出の advice 行とは別行、`advice_id` で紐づけ。実装時に advice 行の欄から別行に変更: 表示の後に別処理で計算して表示を遅らせないため) の `candidates` | 規則 / 配布モデル / 登録チーム専用モデル / model_pick_real の 3 体と確率・予測勝率。既に一部ある (model_pick / model_pick_real / rule) は advice 行に残す | §5 選出方策。実際の選出 (picked) との一致は補助指標 |
