# 有用性検証の計画 (2026-10-07)

別セッションが main (2026-10-07) を見て作った「有用性を検証すべき機能の一覧」(9 領域 + 正しさの前提) について、運用側が
**要素ごとの必要性を判断し、いつ・どの実験で確かめるか、接続テストと学習でどのログを残すか**を決めたもの。
一覧が「調査済みかどうか」の二重確認はしない (ユーザー指示)。判断の根拠は、この文書を書いた時点の記録と設定で、
確認していないものは「未確認」と書く。

## 0. 判断の軸と資源

### 0.1 3 つの区分 (一覧の区分を採用)
- **正しさ**: 仕様・入力事実に合っているか → 壊れていたら直す。有用性の実験はしない (§10)。
- **有用性**: 単純な方式より判断・成績・作業が良くなるか → 比較条件を揃えた測定で決める。
- **費用対効果**: 改善が計算時間・遅延・学習費用に見合うか → 測定に費用の欄を必ず付ける。

### 0.2 資源の実測 (2026-10-07)
| 資源 | 実測 | 含意 |
|---|---|---|
| 実戦 | 接続テスト 1 回 11〜15 戦 (第18回 15、第19回 11)、2〜4 日に 1 回。累計 251 戦 (10/7 の S1 の local_battles) | **実戦で A/B はしない** (条件 2 つを 0.05 の差で見分けるには数百戦要る)。実戦は「影の記録」(表示しない代替案の同時計算) と正解ラベルを残す場 |

## 1. 着手順と時期

一覧の勧める順 (土台 → 実戦経路 → 取りこぼし → 評価相手 → 高費用の機能) を採り、時期を次の 5 段に割る。

### 1.1 段 0: 評価の土台 (10/7〜次の接続テストの前。1〜2 日、実装はサブエージェント)
§10 の正しさの確認と、§2 のログの追加。既存のログ (第17〜19 回 + 10/7 試験) に当てて動くことを確かめてから接続テストに入る。

### 1.2 段 1: 実戦経路 (次の接続テスト 3 回、10 月中旬まで。約 40 戦)
影の記録 (RL 加点の有無・選出候補 3 種・相手の選出予測) を残す。40 戦たまったら C の再分析 (§4.2、§5)。
同じ期間に、run の無い夜に D の 2 本: **P1 (RL 加点 0 / ×5 / ×25)** と **選出方策 (規則 / 配布 / 登録チーム専用) の holdout 測定**。

### 1.3 段 2: 候補の取りこぼし (次の構築 run から毎回、相乗り)
| 相乗りする条件 | 既存の仕組み | 追加の費用 (概算) |
|---|---|---|
| 較正標本 (捨てた並びを S8a だけ測る) | `BUILD_CALIBRATION_SLOTS=4`、`BUILD_CALIBRATION_VARIANTS=("generic",)` (実装済み。採否規則は run 不足で未採用) | +0.7 時間 (設定のコメントの見積もり) |
| 予備評価で早く落ちた腕の追い測定 (3 腕 × 300 戦) | 無い → S8a の脱落腕を `--candidates` で続きを測る段を足す | +40 分 |
| S9 (修理) の対照: 同じ予算の単純近傍 | 無い → S9 の腕に「無作為 1 枠入替」を同数足す | +25 分 (6 腕 × 100 戦) |
| 同時探索 joint と従来 legacy の両方 | `--search-mode both` (実装済み) | 探索段 +10 分 |
| 選出モデルの変種 (規則 / 汎用 / production / fresh) | 参照の腕として毎 run 測っている (10/7: 規則 0.473 / 汎用 0.603 / production 0.533 / fresh 0.317) | 0 (記録を集計するだけ) |
合計 +3 時間弱。run が 9 時間 → 12 時間。接続テストと重ならない夜に起動する。

### 1.4 段 3: 評価相手への依存 (段 2 の run の最終候補に対して、相乗り)
最終候補 (`BUILD_FINALISTS=3`) だけを **相手の操縦 heuristic / rl の 2 方策** と **相手プール latest / mixed (実戦の構築を混ぜる)** で測り直す (3 候補 × 2 × 300 戦 ≈ 1.2 時間 × 2 軸)。順位の相関 (過去 0.53) と、Δ の符号が変わるかを見る。

### 1.5 段 4: 高費用の機能 (条件が揃ったときだけ)
- LLM 構想: 記事バンクを構想生成に接続した後に、規則のみと費用を揃えて比較 (今は 207 並び中 14 測って勝者 0。既定 off のまま)。
- 行動 RL の追加学習・チームごとの adapter: 学習を再開する判断があったときに §3 の規約で測る。
- 退役候補 (§9) は実験せず、使われていないことの確認だけで決める。

## 2. 接続テストで残すログ (段 0 で実装)

いま無いもの、または形を変えるもの。既存の行 (advice / display / events / outcome / rate / manual_fix / hp / version / session) はそのまま。
**実戦は比較の場ではなく記録の場**なので、どの行も「表示する助言」を変えない。

| 行・欄 | 内容 | 使う検証 |
|---|---|---|
| advice 行に `variants` | 同じ状態で RL 加点 0 / ×5 / ×25 (既定) の上位 3 と点差。表示する助言を送った後に別スレッドで計算し、処理の滞りがあれば省く | §4 RL 加点 (実戦で第一候補が変わる頻度と場面)。P1 のシム結果と突き合わせる |
| advice 行 (選出) に `candidates` | 規則 / 配布モデル / 登録チーム専用モデル / model_pick_real の 3 体と確率・予測勝率。既に一部ある (model_pick / model_pick_real / rule) ので欄を揃える | §5 選出方策。実際の選出 (picked) との一致は補助指標 |
| advice 行 (選出) に `opp_pick_pred` | combo_prior の上位 5 組と確率 | §5 combo_prior の対数尤度と較正 (正解は場に出た 3 体が全部分かった対戦だけ) |
| 対戦ごとの `frames` 行 (終了時) | 受信 / 処理 / 破棄 / hidden の比率 / 受信 fps (対戦の時間の幅で割る) | §3 隠れたページ。終了レポートの「約 7.8 fps」(送信 10 fps の仮定) をこれに置き換える |
| `roster_change` 行 | 相手の枠の置き換え・消失 (元の種、推定の確率、先の種、根拠) | §3 推定の枠の置き換え、0.95 の較正 |
| `guess_confirm` 行 | 推定を確定した時点の確率と、後に場で判明した種 (一致 / 不一致 / 未判明) | §3 確定閾値 0.95 の実際の正答率 |
| `hp_stale` 欄 (advice 行) | 助言時点で自分 / 相手の場の HP が最後に読めてからの秒数 | §3 HP 固着 (第19回は HP 無しの助言 44%) |
| manual_fix 行に `overwritten_at` | 手入力の訂正が後の推定で上書きされた時刻 | §3 手動訂正の持続性 |
| 選出ラベル 3 値 | 相手の 6 体を 場に出た / 出なかったが選出判明 / 不明 に分ける (今は 6 体 − 場に出た = 選出外) | §10 ラベルの正しさ、§5 選出予測の正解 |
| 終了レポート | fps と hidden 比率、推定の勝敗とその根拠、選出候補 3 種と実際、影の計算で第一候補が変わった回数 | テスト直後の確認 |
| 局面ラベル | 1 テストあたり 10 局面 (整合 7 + 失敗 3) を `logs/scenes/` に足す (advice_trace の候補から) | §3 状態復元率の推移 |

ログの追加はすべて対戦ログのスキーマに**欄を足す**だけにし、既存の読み手を壊さない (規約 5)。

## 11. 無効・任意・未接続の機能 (一覧の 9 節)

すべて **E**。再び使うときの検証条件は一覧のとおりで、再実験はしない。再使用の引き金になるものだけ書く:

## 13. 判断をお願いしたいこと

1. 終了処理の自動測定起動を **確認制** にするか (§9)。
