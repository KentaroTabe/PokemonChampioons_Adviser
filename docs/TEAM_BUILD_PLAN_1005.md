## 3. 評価と較正の設計 (判断 #7〜#12 の具体化)

### 3.1 代理評価 D1: 学習の代理を先に (判断 #11)

- **学習の代理** V_learned(T) = 相手チーム o (探索 fold B) の平均 max_S P(勝ち | T, o, S)。P は汎用の選出モデル。対戦なしで計算でき、
  測定済みの全 run で過去にさかのぼって検証できる。スクリプト: `python -m tools.team_build.experiments.learned_surrogate` (実験 8、本 commit)。
- 判定: run 内の順位相関 (学習 vs 被覆) を全 run で並べ、学習が中央値で 0.2 以上高ければ、探索の評価の主項を学習の代理にする
  (被覆は制約と診断に残す)。分布外の並び (`is_in_distribution` が偽) の割合も記録し、汎用モデルの再学習 (多数のチームでの収集) が必要なら
  Phase 2 の作業に加える。
- 被覆の作り直しは、学習の代理が足りない場合の次善。実験 1 の「被覆の重み 0」は、被覆が今の計算 (対面 0.5 / 後投げ 0.3 / 切り返し 0.2 の
  加重平均、脅威 30 種) では測定と無関係だと言っている。作り直すなら、系統ごとの被覆でなく「選出 3 体 × 相手 3 体」の対戦単位の値に戻す。

### 3.2 較正の採否規則 D2 (判断 #8・#9・#10)

1. **信号は run 内の対応比較だけ** (同一相手列の Δ)。段は混ぜない: 較正に使うのは S8a (300 戦、cheap の腕) の Δ だけ。S8b / S10 は別の
   確認に使う。
2. **較正の標本 = 無作為の並びの枠** (判断 #10、済): 各 run で S5 が生成して**保持しなかった**並び (s05_generated.json に全部残す) から、
   代理の点の 4 分位から 1 つずつの層化抽出で K = BUILD_CALIBRATION_SLOTS (4) 並びを引き (tag calibration)、軽い適応 (cheap 1,000 戦)
   の腕だけを 300 戦測る (BUILD_CALIBRATION_VARIANTS。較正に使うのはその Δ だけなので 3 変種は要らない: 判断 #4、+約 0.7 時間)。生存・修理の親・昇格には使わず (pipeline.exclude_tagged)、代理評価の較正
   (s08a_calibration) と summary の calibration_sample にだけ入る。--candidates / --strata で部分集合を測るときも常に含める。
   費用は約 +0.7 時間 (1003 の S8a は 10 チームを 3.9 時間。「84 並び」は保持した並びの数で測ったのは 10 チーム)。
3. **構造を変えない** (判断 #9): 重みの倍率の格子から 0 を外す (最小 0.25)。主項の削除は較正ではなく設計変更として扱う。
4. **偽陽性の統制** (判断 #8): (a) 並べ替え検定: run 内で Δ を 200 回シャッフルして「改善」の帰無分布を作り、観測の改善が 95 点を超える
   ときだけ候補にする。(b) 前向き検証: 候補の重みを**次の run の測定前に凍結**し、その run の無作為の枠を含む測定で順位相関が現在の重みを
   上回ることを 2 run 続けて確認してから採用する。leave-one-run-out は候補の選別にだけ使う。
5. 採用した重みは選出モデルと同じく registry で版を管理し、shadow 1 run を経て本番にする。
6. 必要な run 数: 同時探索の run があと 4 本 (約 90 時間、判断 #7)。Phase 1 で run を夜に収めてから積む。

### 3.3 実戦との差 D5 (判断 #5・#12)

- 登録チームの実戦の勝率 (対戦記録、同じ 6 体の試合だけ) と、直近 run のシムの参照の勝率を並べて `evaluation/real_vs_sim.json` と
  運用の記録に残す。±0.1 で測るには約 100 戦 (約 2 か月) 要るので、系統ごとの比較はしない。
- 差の 4 つの源 (§1) のうち、本番の選出モデルは Phase 0 で手当てする。残りは記録して傾向を見る。
- 運用の鎖 (どの順で何を見るか): 対戦記録 → `real_eval` (実戦の勝率・遵守の記録) と `experiments/env_validity` (一致率・実戦 vs シム) →
  `triggers` (基準線との比で再構築の引き金) → run → `promote --gate` (full run の数え方) → `--install`。基準線は採用した run の時点で
  `python -m tools.team_build.triggers --set-baseline` が書く。

## 9. 操縦 (2026-10-05 追記: 実戦の助言と測定で同じ経路)

前提「操縦はアドバイザーが行う」を実戦と測定の両方に通した。候補チームの操縦と環境チームの操縦が食い違うと測定の判断がぶれるので、
どちらも方策を名前で固定し、run の記録 (racing の結果と summary) に残す。

| 側 | 実戦 (助言) | 測定 (シム) | 決め方 |
|---|---|---|---|
| 自分 (候補) の選出 | ◎ = 学習の選出モデルの推し (SELECTION_PRIMARY_MODEL、`advisor.selection.choose_primary`)。相性の規則の推奨は「参考」として併記 | 同じ鎖: 選出モデル (`pick_policy advisor`) → 規則 (`rule`、advise_selection) → タイプ相性 (`teampreview`)。画面の変種 teampreview → rule | 配布版が分布外なら規則に落ちる。実戦でどちらが ◎ だったかは real_eval.selection_compliance が記録 |
| 自分の行動 | 行動方策 + 探索 | 同じ (RL のピン) | — |
| 環境チームの操縦 | (人) | BUILD_OPP_PILOT = rl (確定、10/5 実験 13: heuristic の参照 0.78 は実戦 0.41 と矛盾、rl 0.54〜0.61 は矛盾しない) | 実験 13 (参照の勝率 vs 実戦の勝率) |
