# 構築システム 計画書 (2026-10-05): 実験 1〜4 と 29 項目の判断を受けた切り分けの確定と実施順

目的は一つ: **与えられたテーマ (無いこともある) の下で、今の環境分布に対して期待勝率が最も高いチームを決め、根拠を示す**。
操縦はアドバイザー (選出モデル + 行動方策 + 探索) が行う。切り分けの原則は、良構造の問題はルールと統計、悪構造の問題は LLM か人、
実測に合わせて決めるものは較正 (統計)、の 3 区分 (判断 #7 で承認)。

入力: 2026-10-04 の実験 1〜4 の結果と補足集計、2026-10-05 の 29 項目の判断、上位プレイヤーのブログ一覧 (289 行)。
既存の文書との関係: 設計 (docs/TEAM_BUILD_REDESIGN_1002.md) と実装状況 (docs/TEAM_BUILDING_IMPLEMENTATION.md §12) を前提にし、
本書は「何を・どの順に・どう検証して」決めるかだけを書く。

## 3. 評価と較正の設計 (判断 #7〜#12 の具体化)

### 3.1 代理評価 D1: 学習の代理を先に (判断 #11)

- **学習の代理** V_learned(T) = 相手チーム o (探索 fold B) の平均 max_S P(勝ち | T, o, S)。P は汎用の選出モデル。対戦なしで計算でき、
  測定済みの全 run で過去にさかのぼって検証できる。スクリプト: `python -m tools.team_build.experiments.learned_surrogate` (実験 8、本 commit)。
- 判定: run 内の順位相関 (学習 vs 被覆) を全 run で並べ、学習が中央値で 0.2 以上高ければ、探索の評価の主項を学習の代理にする
  (被覆は制約と診断に残す)。分布外の並び (`is_in_distribution` が偽) の割合も記録し、汎用モデルの再学習 (多数のチームでの収集) が必要なら
  Phase 2 の作業に加える。
- 被覆の作り直しは、学習の代理が足りない場合の次善。実験 1 の「被覆の重み 0」は、被覆が今の計算 (対面 0.5 / 後投げ 0.3 / 切り返し 0.2 の
  加重平均、脅威 30 種) では測定と無関係だと言っている。作り直すなら、系統ごとの被覆でなく「選出 3 体 × 相手 3 体」の対戦単位の値に戻す。

### 3.2 較正の採否規則 D2 (判断 #8・#9・#10)

1. **信号は run 内の対応比較だけ** (同一相手列の Δ)。段は混ぜない: 較正に使うのは S8a (300 戦、cheap の腕) の Δ だけ。S8b / S10 は別の
   確認に使う。
2. **無作為の並びの枠** (判断 #10): 各 run で S5 が生成した並びから一様に K = 4 並びを引き、S8a と同じ深さ (cheap 1,000 戦 + 300 戦) で
   測る。昇格には使わず、較正の標本だけに使う (上位だけを測る選択バイアスを避ける)。費用は run の 5〜8%。
3. **構造を変えない** (判断 #9): 重みの倍率の格子から 0 を外す (最小 0.25)。主項の削除は較正ではなく設計変更として扱う。
4. **偽陽性の統制** (判断 #8): (a) 並べ替え検定: run 内で Δ を 200 回シャッフルして「改善」の帰無分布を作り、観測の改善が 95 点を超える
   ときだけ候補にする。(b) 前向き検証: 候補の重みを**次の run の測定前に凍結**し、その run の無作為の枠を含む測定で順位相関が現在の重みを
   上回ることを 2 run 続けて確認してから採用する。leave-one-run-out は候補の選別にだけ使う。
5. 採用した重みは選出モデルと同じく registry で版を管理し、shadow 1 run を経て本番にする。
6. 必要な run 数: 同時探索の run があと 4 本 (約 90 時間、判断 #7)。Phase 1 で run を夜に収めてから積む。

### 3.3 実戦との差 D5 (判断 #5・#12)

- 登録チームの実戦の勝率 (対戦記録、同じ 6 体の試合だけ) と、直近 run のシムの参照の勝率を並べて `evaluation/real_vs_sim.json` と
  運用の記録に残す。±0.1 で測るには約 100 戦 (約 2 か月) 要るので、系統ごとの比較はしない。
- 差の 4 つの源 (§1) のうち、本番の選出モデルは Phase 0 で手当てする。残りは記録して傾向を見る。

## 6. 記事バンク (上位プレイヤーのブログを LLM の基礎知識にする)

ブログ一覧 (289 行) の中身: 確度 A 100 / B 45 / 要追確認 144、記事 URL 175 本、シーズンは M-1〜M-5 と MCS、順位の中央値 98 位

**目的を分ける** (判断 #16): 自チームの型は役割の雛形から作る方針 (10/2 の D-10) を変えない。記事バンクが担うのは次の 3 つ。

1. **相手側の型** (環境モデル B3): 上位プレイヤーの実在の 6 体と型を、相手プールの型 (今は周辺分布からの合成) に置き換える材料にする。
   季節が違う記事の型は規制 (M-C) で合法性を検証し、不合法なら持ち物・技を落として印をつける。
2. **LLM の接地** (C6 / H2 / G1): 設計図の提案、規則の提案、記事の執筆のとき、関係する記事 (種・軸で引く) の構造化した主張を
   プロンプトに添える。LLM の一般知識でなく、この環境の上位の判断に寄せる。
3. **テーマの解釈**: 「エース X」が指定されたとき、X を使った上位構築の相方 (実在の共起) を、規則の列挙 (C5) の入力にする。

**作り方**

- 入力: 一覧の A / B (145 行) から始める。要追確認 (144 行) は記事 URL の特定が要るので、LLM + 検索で候補を出し人が承認する 2 段目。
  ダブルの記事は除く。
- 取得と抽出: 本文を取得 → Sonnet が固定スキーマに抽出 ({記事, 著者, 季節, 順位, 6 体の型, 選出パターン (相手 → 3 体), 対面の主張,
  構築の意図, 注意}) → 規則が検証 (種 id の解決、合法性、季節の規制)。画像でしか型を載せていない記事は「抽出不可」と印をつける。
- 保存: 構造化した事実と出典 URL、短い引用 (200 字以内) だけ。本文は保存しない。
- 費用: 175 記事 × Sonnet 1 回で一度きり。毎月の MCS の記事を追加する運用。
- 検証: 20 記事を手で突き合わせて抽出の正しさ (型の一致率) を出す。相手プールへの効果は実験 6、設計図への効果は実験 10 で測る。
