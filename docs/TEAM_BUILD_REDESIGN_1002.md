## 2. 現状の問題 (事実)

点検は `scratchpad` の survey_sets2.py / abilities_survey.py / same_set_check.py で行った (読み取りのみ、再生成可能)。

1. **全並びで同じ型**: 1002d の探索 76 並びで、3 並び以上に入る 35 種のうち 21 種が技構成 1 種類。ティンカトン 40 並び 1 型、
   バクフーン 31 並び 1 型。arch_0924 は 45 種中 15 種 (サーフゴー 32 並び 1 型)。原因は S6 が「全並び共通の脅威 30 種への被覆」で
   種ごとに独立に選ぶため。並びごとの差は後付けの 4 処理 (メガ石の差し替え、場の前提、規則・軸の差し込み、アイテムクローズ) だけ。
2. **石を外した代替は使用率を見ない**: 1002d のカイリューは 26 並び全部で、代表型 (はねやすめ/しんそく/かえんほうしゃ/りゅうせいぐん @石)
   から生成型 (げきりん/じしん/ばかぢから/アイアンヘッド @たべのこし) に差し替わった。ゴツゴツメット 23.5% の使用率型は被覆で負けた。
3. **提案 300 型の出所**: 代表型 166、生成型 48、登録型 58、指定型 14、代替 14。生成型は役割辞書の並び順と「威力 × 命中」で技を採り、
   デメリット (自己能力低下・反動・固定・ため・命中・自爆) と文脈 (トリル・天候・特性) を見ていない。
4. **差し込みが型を壊す**: ハリーマン つるぎのまい + まきびし + みちづれ、アシレーヌ ねむる単体、カビゴン 生成型 → カゴのみ (クローズ)
   などが測定・最終候補に入った。
5. **特性**: 参戦 459 種 (メガ後を含む) の特性 226 種類のうち、`advisor/damage.py` が扱うのは 46。無効・吸収 10 は済み。
   火力 21、タイプ付与 7、命中 3、被ダメ 12、被弾時 24 などが未。へんげんじざい・リベロ・そうだいしょう は最終候補の常連なのに補正なし。
6. **条件つき技**: アイアンローラーは「フィールドが無いと失敗」をどの処理も知らない (生成でも助言でも威力 130 の技)。
7. **戻りの経路**: S9 介入実験 (interventions.py) は雛形のみ (記録だけ、`--repairs` 既定 0、過去 run で未実行)。
   改善案 run (improve_*) が人手の外側ループ。対戦記録 (battle_log.py) には選出・先発・交代・KO・資源・メガ使用・残り個体があり、
   敗因統計 (loss_stats.py) は構造化済み。

## 3. 新しい全体像

```
S0 仕様  S1 使用率  S2 相手プール  S3 種と型の特徴 (役割別、要求時計算)
   └→ S4 構想: 役割の設計図 (核 2〜3 体 + 役割、補完枠の要件、計画の制約、担当)        … §4
        └→ S5 並びと型の同時探索 (旧 S5 + S6):                                          … §5
              A. 核 3 枠: 型まで同時に決める
              B. 補完 3 枠: 「今の並びに足りないもの」で 1 枠ずつ (小さなビーム)
              C. 6 体の制約 (持ち物の一意性 / メガ石 / エース / 除外) と合法性検査
              └→ s06_sets.json / s06_sets/<並び>.txt (出力の契約は変えない)
S7〜S13 測定 (変更なし)
   S8a screening 後・S8b 後: 診断 → 制約 → S5 の修理モード → 変種を racing の腕に追加 (2 周まで)   … §14
   S12 封印 holdout は最後に 1 回
```

- S5 の番号は「S5」のまま使い、S6 は S5 の最終工程 (検証と出力) として吸収する。run.py の `--stages` と run dir の成果物名は維持する。
- 役割 → 型 → 並び の順は、S4 (役割の設計図) → S5-A/B (役割の雛形から型を一体で作る) で保証する。差し込み (規則・軸の技や持ち物) と
  アイテムクローズは廃止し、同じ要求を「役割の雛形」と「制約」で表す。

## 4. S4: 構想の出力 (役割の設計図)

### 4.1 出力スキーマ (authoritative、検証対象)

```json
{"concepts": [{
  "name": "str",
  "win_condition": "setup_sweep | offense_trade | cycle_pressure | hazard_chip | speed_control | bulky_attrition | priority_cleanup | anti_meta",
  "style": "offense | balance | bulky_offense | cycle | setup | speed_control | anti_meta | specific_core",
  "archetype": "axis_id | null", "branch": "branch_id | null", "special_branch": "id | null",
  "core": [{"species_id": "id", "role": "役割 id (§6.1)"}, ...],          // 2〜3 体。エース指定があれば必ず含む
  "mega_id": "id | null",
  "complement_requirements": [{"role": "役割 id", "targets": ["family_id または threat_id"], "note": "str"}, ...],   // 残り枠の要件 (最大 3)
  "plan": {"field": {"weather": "sun|rain|sand|snow|null", "terrain": "electric|grassy|psychic|misty|null"},
           "speed_plan": "outspeed | trick_room | neutral", "lead_item": "focussash|null"},
  "targets": {"beats": ["family_id", ...], "concedes": ["family_id", ...]}
}]}
```

- `core[].role` と `complement_requirements[].role` は §6.1 の語彙に限る (enum 検証)。`targets` は S2 の系統 id か S1 の脅威 id。
- 種の指名は核だけ。補完枠は要件 (役割 + 見る相手) で書かせ、種は書かせない (書いても `display` 扱い)。
- 検証は従来どおり id / enum のみ (実装文書 §10)。違反は差し戻し。エース指定・規則の設置役/エース・除外は現行の検証を維持。

### 4.2 入力の軽量化

- 今は 350 種の特徴 (被覆・役割) を渡し、1002 の S4 は 96 系統で $26.82 / 32 分。
- 新しい入力は「種ごとの要約」(タイプ、持ちうる役割、主要な系統への強弱の要約、メガの有無) と「相手の系統の一覧 (使用率順)」、
  「役割の語彙と各役割の意味」。見積もりは入力の半分以下 (未確認、実装時に計測)。

### 4.3 規則ベースの baseline と軸 (archetype)

- 規則の系統 (rule: framing × ace) と軸の系統は、同じスキーマで `core[].role` を機械的に埋める (設置役 → `hazard_lead`、エース → `sweeper_setup` 等)。
- 歴史的な系統 (`already_found`) の重複判定は core の種集合のままで良い。

決定の根拠: D-13、D-22。

## 5. S5: 並びと型の同時探索

### 5.1 入力と出力

- 入力: S4 の構想 (§4)、S2 の相手プール (探索 fold)、S1 の脅威、S3 の特徴 (§5.6)、型の雛形 (§6)、仕様 (所持・除外・固定・指定の型・エース・規則)。
- 出力: 従来の s06_sets.json と s06_sets/<並び>.txt。行には新たに `roles` (個体 → 役割)、`assignments` (個体 → 担当する系統)、
  `selection_plan` (主要な系統 → 出す 3 体) を足す。

### 5.2 探索の順序 (核 3 枠 → 補完 3 枠)

**A. 核 3 枠 (同時)**

1. S4 の核が 3 体ならその 3 体。2 体なら 3 体目は B の 1 枠目として順に選ぶ (D-24)。その枠の不足の列挙では「計画が要求する役割」
   (トリックルームの始動役、天候の始動役、受け出し先) を最優先にし、選ばれた個体は核扱い (担当は核と同じ) にする。
2. 核の各個体について、役割の雛形から型の候補を作る (§6、種 × 役割ごとに最大 `BUILD_SET_CANDIDATES_PER_ROLE` (初期値 3) 個)。
3. 核の型の組み合わせ (3 体なら最大 3^3 = 27、2 体なら 9) を、核だけの選出として評価する (§5.3)。
   核どうしの型の整合 (トリックルームの始動と下を取る配分、天候始動と恩恵、バトンタッチの受け) はここで一緒に決まる。
4. 上位 `BUILD_CORE_BEAM` (初期値 3) 組を残す。核が 2 体のときは、3 体目を順に選んだ後に核 3 体の型を一度だけ選び直す
   (3 体目の役割に合わせて始動役の配分などを合わせる。27 組の再評価なので安価)。

**B. 補完 3 枠 (順に)**

各枠で、現在の並び T (3〜5 体) に対して:

1. 不足を列挙する: (a) 相手の系統ごとに「T から出す最良 3 体」の評価が低い系統 (穴)、(b) 計画が要求する役割で未充足のもの
   (S4 の `complement_requirements` と雛形の必須役割)、(c) 選出の自由度 (主要な系統に対して出せる 3 体が 1 通りしか無い)。
2. 候補を作る: 所持の種 × 役割 (不足に対応する役割に限る) × 型の候補 (§6)。相手の天候・フィールド・持ち物の一意性・メガ石の上限・
   エース・除外・固定枠を候補の段階で満たさないものは捨てる (§5.4)。
3. 各候補の増分 = 評価 (§5.3) の T ∪ {候補} − T。穴を埋める候補は、その系統を「担当」として記録する。
4. 上位 `BUILD_COMPLEMENT_BEAM` (初期値 3) を残して次の枠へ。6 体で制約に当たったら直前の枠だけ戻す (1 段のバックトラック)。

**C. 仕上げ**

- 6 体が揃ったら持ち物の一意性・メガ石・エース・除外を再確認し (候補段階で満たしているので検査のみ)、Showdown の validate-team を通す。
- 系統ごとに距離の離れた並びを複数残す quota (現行の select_with_quotas) はそのまま使う。
- 現行チーム枝 (登録の 6 体) と近傍は、登録の型を一体の候補として固定し (役割は型から逆引き)、同じ評価で測る。

決定の根拠: D-19、D-21、D-06。

### 5.3 評価関数 (3 体選出を前提にする)

今の `team_coverage` は脅威ごとに「最良 0.7 + 次善 0.3」を使用率で加重した平均で、6 体がまとめて戦う前提になっている。
新しい評価は「6 体から 3 体を出す」構造を持つ。

```
V(T) = Σ_F w_F · max_{S ⊂ T, |S| = 3} v(S, F)        (F = 相手の系統、w_F = 使用率の重み × セッションの指定)
v(S, F) = 平均_{o ∈ F の 6 体} [ 0.7 · max_{s ∈ S} cov(s, o) + 0.3 · 次善 ]     (cov は与ダメ・被ダメの行列の値、場込み)
        + 役割の充足 (S の中に先発・勝ち筋・受けが揃うか)
        − 速度・持ち物の重複による減点 (同じ仕事の個体が 2 体)
```

- 6 体の 3 体部分集合は 20 通りで、系統数 (探索 fold 約 100) との積は小さい。cov は (種, 型, 場) で記憶する。
- 核の評価は S = 核 3 体で固定、補完の増分は max の更新だけなので安価。
- `selection_plan` (系統 → 出す 3 体) はこの max の引数で、記事と測定の選出モデルの初期値に使う。
- 穴の罰則 (BUILD_LINEUP_HOLE_*)、共起、冗長は現行の項を v(S, F) の中に移す。

決定の根拠: D-21、D-04 (担当)。

### 5.4 制約

| 制約 | 扱い |
|---|---|
| 持ち物の一意性 | 候補の段階で、既に並びにある持ち物を持つ型は候補にしない (差し替えはしない)。型の候補は持ち物の候補を複数持つ (§10) |
| メガ石 | 構想の mega_id が持つ。他の個体の石持ち型は候補にしない。エース指定ならエースだけ (BUILD_ACE_MAX_MEGA_STONES) |
| エース・固定枠・除外 | 現行どおり (核に必須、除外は候補から外す) |
| 指定の型 (custom_sets) | その型だけを候補にする (役割は型から逆引き) |
| 天候・フィールド | 並びの始動源 (特性・技) と型の依存技の整合 (§7.6)。始動源が 2 系統衝突する並びは減点 (完全禁止にはしない) |
| 規則 (rules) | 設置役の技とエースの持ち物は役割の雛形の必須要素として候補を作る (差し込みはしない) |

決定の根拠: D-11、D-12、D-13。

### 5.5 S3 の特徴

- 従来の「種 × 代表型」の特徴に代えて、「種 × 役割 × 型」の被覆行列を要求時に計算して記憶する (キャッシュ: (種, 型のキー, 場)).
- 1002d の S3 は 279 種で 13 秒だった (run.log 13:43:56 → 13:44:09)。型の候補が種あたり最大 役割 3 × 3 = 9 なら 9 倍で 2 分程度 (未確認、実装時に計測)。

### 5.6 擬似コード

```
for concept in S4:
    cores = core_candidates(concept)                       # 核 (2〜3 体) × 型の組 (≤ 27)
    beam = top_k(cores, key=V, k=BUILD_CORE_BEAM)
    for slot in range(6 - len(concept.core)):             # 核が 2 体なら 1 枠目は核扱い (計画の役割を最優先)、その後に核の型を選び直す
        next_beam = []
        for T in beam:
            needs = shortfalls(T, families, concept.complement_requirements)   # 穴・未充足の役割・選出の自由度
            for cand in candidates(needs, pool, templates, constraints(T)):
                next_beam.append((T + cand, V(T + cand), assign(cand, needs)))
        beam = top_k(next_beam, k=BUILD_COMPLEMENT_BEAM, diverse=True)
    lineups += [finalize(T) for T in beam if legal(T)]     # 制約の再確認 + validate-team
lineups = select_with_quotas(lineups)
```

## 6. 型の雛形 (役割 → 型を一体で)

### 6.1 役割の語彙

| 役割 id | 意味 | 技の構成 | 持ち物の候補クラス | 配分・性格 | 特性の方針 (§9) |
|---|---|---|---|---|---|
| sweeper_setup | 積んで複数ターン殴る | 積み 1 + 攻撃 3 (主 STAB は反復できる技) | 消費回復 (オボン/ラム)、タスキ、たま、石 | 速攻か耐久は種で決める | 火力・加速・耐性 |
| breaker | 1 発の火力で崩す、退く | 攻撃 3〜4 (+交代技) | こだわり系、たま、石 | 速攻 | 火力 |
| cleaner | 先制・速度で締める | 先制技 1 + 攻撃 3 | タスキ、たま、スカーフ | 速攻 | 加速・火力 |
| tr_ace | トリックルーム下で殴る | 攻撃 3〜4 (低下技可) | たま、こだわり | 素早さ 0、下を取る | 火力 |
| weather_ace / terrain_ace | 天候・フィールドの恩恵で殴る | 依存技 1〜2 + 攻撃 | たま、こだわり、石 | 速攻 | すいすい等 |
| hazard_lead | 先発で設置 | 設置 1〜2 + 攻撃/妨害 | タスキ、ゴツメ | 耐久か速攻 | 耐性・がんじょう |
| hazard_removal | 設置の除去 | 除去 1 + 攻撃 2 + 回復/交代 | 残飯、ゴツメ | 耐久 | 再生 |
| speed_control | トリル/追い風/ねばねばネット/まひ | 速度操作 1 + 攻撃/妨害 | ねんど、タスキ | 役割次第 | いたずらごころ |
| weather_setter / terrain_setter | 天候・フィールドの始動 | 始動技 or 特性 + 攻撃/交代 | 始動延長の岩、ねんど | 耐久 | 始動特性 |
| pivot | 交代技で回す | 交代技 1 + 攻撃 2 + 回復/妨害 | 残飯、スカーフ、チョッキ相当は無し | 耐久 | 再生 |
| wall_physical / wall_special | 受け | 回復 1 + 攻撃 1〜2 + 妨害 | 残飯、ゴツメ、オボン | 耐久 (速い種は不可: D-17) | 耐性・再生 |
| status_spreader | 状態異常をまく | 状態技 1〜2 + 攻撃 + 回復 | 残飯 | 耐久 | — |
| support_screens / support_cleric | 壁・願いごと | 壁 2 + 攻撃/妨害 | ねんど | 耐久 | いたずらごころ |
| trapper / suicide_lead | 道連れ・自爆・起点作り | 自爆・みちづれ + 設置/妨害 | タスキ | 役割次第 | — |

- 雛形は config (`BUILD_ROLE_TEMPLATES`) に置く。各雛形は「必須の技の種類」「任意の技の種類」「持ち物のクラス」「配分の方針」
  「特性の方針 (タグ)」「評価の観点 (どの相手で測るか)」を持つ。
- 1 つの種に複数の役割がありうる (ユキメノコ: 石があれば sweeper/breaker、無ければ hazard_lead や speed_control)。
  役割の適性は種族値・learnset・特性から機械的に出し、使用率は参考 (D-10)。
- 速い種 (素早さ種族値 ≥ `BUILD_WALL_SPEED_MAX`、初期値 95) は wall_* の候補にしない。使用率の型が壁 (アローラキュウコンの
  雪・オーロラベール) ならその型は一体の候補として入る (D-17)。

### 6.2 型を一体で作る

- 生成は雛形ごとに「特性 → 持ち物 → 技 → 性格・配分」を同時に決める (別々の最適化はしない)。
  特性は §9 の適合、持ち物は §10 の候補クラス、技は §7・§8、配分は現行の微調整 (想定する相手 = 担当) を使う。
- 候補数は種 × 役割ごとに最大 `BUILD_SET_CANDIDATES_PER_ROLE` (初期 3): 雛形の生成型 1〜2 + 使用率の型 (一体の候補、§6.3)。
- 常識フィルタ (set_sanity) は「一体で作った型が壊れていないか」の最終検査にだけ使う (こだわり + 変化技、カゴ + ねむる無し、
  きのみ技 + きのみ無し)。差し替えで壊れた型を拾う用途は無くなる。

### 6.3 使用率の型の扱い

**実測 (D-26、2026-10-02、snapshot 54、使用率上位 30 種)**: 公開データに「一体の型」は無い。

- championsbattledata は技・持ち物・特性・性格 (stat_alignment)・配分 (stat_points)・同居を**それぞれ別の周辺分布**で出す。性格と配分も
  別の行 (上位 30 種の spread_usage は性格だけの行 300 + 配分だけの行 300、両方入った行は 0)。代表型 (meta_sets) はそれらの最多を
  整合規則 (choose_coherent_spread) で縫い合わせた**合成**であり、実在の型ではない。
- pokedb の上位構築 (S5、10/02 時点 192 チーム) は 1 体ごとに種と持ち物だけ (技・特性・性格・配分は無い)。結合情報として使えるのは
  「種 × 持ち物」と「同じチームにいた 6 体」。
- 自分の対戦ログ (実戦バンク) は相手の技・持ち物・特性を観測した範囲で結合しているが、部分的。
- 周辺分布の集中度 (上位 30 種の平均): 最多の持ち物 65.6%、4 位の技 51.0%、最多の特性 89.7%、最多の性格 59.8%。
  最多の持ち物が 50% 未満の種が 9/30 (ガブリアス 33.8%、ハッサム 32.2%、ヒスイダイケンキ 32.5%、ブリジュラス 37.4% など)、
  4 位の技が 50% 未満の種が 12/30 (ライチュウ 23.8%、ガブリアス 28.3%、リザードン 34.8%、ミミロップ 34.9% など)。
  この約 1/3 の種では、合成した代表型が「誰も使っていない組」である可能性が高い (ガブリアスの代表型は 石 Z + じしん + ステルスロック +
  りゅうせいぐん + りゅうのしっぽ)。

**扱い (設計)**:

- 使用率から「一体の型」は作らない。候補の主役は役割の雛形から一体で作った型 (§6.2)。
- 使用率は属性ごとの**根拠** (その技・持ち物・特性が実戦で使われている証拠) として使う: 雛形の生成で同評価の候補が並んだときの参考 (D-10)、
  記事での注記 (「この技は使用率 2% で一般的でない」)。一般的でない型でも評価が高ければ採る (D-07)。
- 代表型は「合成」の印をつけた 1 候補として残す (比較の基準として有用。1002d までの提案との連続性)。
- pokedb の「種 × 持ち物」は実在の結合なので、持ち物の候補クラス (§10) の順位に使う (その種で実際に多い持ち物を先頭に)。
  「同じチームにいた 6 体」は S4 の構想の根拠 (核の相性) に使う (現行の teammates と同じ)。
- 順位付けの既定 (REP_MARGIN) と使用率差の罰則 (BUILD_SET_USAGE_WEIGHT) は廃止する。

決定の根拠: D-10、D-13、D-17、D-07。

## 7. 攻撃技

### 7.1 優先表 (データ)

- `advisor/data/move_priority.json`: 物理/特殊 × 18 タイプごとに、技を「安定技」と「それ以外」に分け、各技に理由タグを付ける。
  安定技 = デメリット無し・命中 90 以上・条件無し。それ以外 = 自己能力低下 / 反動 / 外すと自傷 / 数ターン固定 / ため / 反動で動けない /
  命中 ≤ 80 / 自爆 / 条件つき。タグは Showdown の技データ (self.boosts、recoil、hasCrashDamage、lockedmove、flags.charge/recharge、
  accuracy、selfdestruct、onTry) から機械的に起こし (tools/build_move_data.py)、人手で見直せる形にする。
- 表はユーザーが見て直す前提 (D-02)。実装はこの表を一次情報にし、learnset でその種が覚えるものだけに絞る。

### 7.2 耐久・速攻の判定

- 耐久 = 役割の雛形が wall_* / hazard_removal / pivot / status_spreader / support、または配分が HP か防御側に `BUILD_BULK_POINTS_MIN`
  (初期 24) 以上、または持ち物が回復系・ゴツメ。
- 速攻 = 配分が素早さに `BUILD_FAST_POINTS_MIN` (初期 24) 以上で耐久投資が無い、または持ち物がタスキ・たま・こだわり系。
- どちらでもない個体は「耐久」側で扱う (安定技優先)。閾値は config。

### 7.3 採用規則

| デメリットの種類 | 耐久の個体 | 速攻の個体 | 補足 |
|---|---|---|---|
| 自己能力低下 (攻撃側) | 不採用 (同タイプの安定技が無く、無いと担当に穴が空くときだけ) | 1 発化 (§7.4) に効くなら採用 | 積み型は §8 の計画で判定 |
| 自己能力低下 (防御側: インファイト等) | 不採用 (ボディプレス / ドレインパンチ を先に) | 採用可 | 壁型は不可 |
| 反動 | いしあたま / すてみ 以外は不採用 | 1 発化に効くなら採用 | マジックガード は反動無し |
| 外すと自傷 | 不採用 | 1 発化に効くなら採用 | |
| 数ターン固定 (げきりん等) | 不採用 | こだわり持ちか速攻型なら採用 | |
| ため・反動で動けない | 条件 (晴れ等) が並びにあるときだけ | 同左 | |
| 命中 ≤ 80 | 安定技を先に | 1 発化に効くなら採用 | 雨の かみなり/ぼうふう、雪の ふぶき は命中 100 扱い |
| 自爆・捨て技 | 役割が trapper / suicide_lead のときだけ | 同左 | 費用は §12 |
| 条件つき (§7.6) | 条件が並びで成立するときだけ | 同左 | |

- あまのじゃく (カラマネロ、ジャローダ、メガムクホーク、メガカラマネロ) は自己能力低下を上昇として扱い、低下技を最優先にする (D-05)。
- 同タイプ複数は制限しない (D-14)。被覆の増分で選ぶので自然に散るが、必要なら 4 技同タイプも可。

### 7.4 1 発化の加点

- 被覆表の値は「与ダメージ割合 (命中込みの期待値)」。候補技の採点に、担当する相手 (§5.2 で記録した系統の個体) について
  「安定技で 2 発 → この技で 1 発」になる個体の重み和 × `BUILD_OHKO_BONUS` を加える。担当外の相手には加点しない (D-04)。
- 加点は速攻の個体だけ。耐久の個体は安定技の順位をそのまま使う (D-03)。

### 7.5 連続技・可変威力・急所・命中 (計算)

- `advisor/data/move_effects.json` (tools/build_move_data.py が Showdown から起こす) に以下を持つ: multihit (回数または範囲)、
  multiaccuracy (1 発ごとの命中判定)、basePowerCallback の種類 (重さ / 速度比 / 状態異常 / 持ち物の有無 / 味方の瀕死数 / 連続使用)、
  willCrit (確定急所)、critRatio、accuracy、self.boosts、recoil、drain、hasCrashDamage、lockedmove、charge/recharge、selfdestruct、onTry の条件。
- 期待ダメージ = Σ_hit P(hit) × 威力_hit × 補正。連続回数は 2〜5 回なら 35/35/15/15 % の期待値 (スキルリンクは 5 回固定)、
  3 回固定、2 回固定を区別する。multiaccuracy の技 (トリプルアクセル、トリプルキック、ネズミざん) は P(hit_k) = acc^k、
  それ以外は 1 回の判定を全発に掛ける。確定急所は 1.5 倍、急所率上昇 (スナイパー等) は確率で。
- 可変威力: 重さ依存 (けたぐり、くさむすび、ヘビーボンバー、ヒートスタンプ) は相手の体重から、速度比 (ジャイロボール、エレキボール)
  は実効素早さから、状態異常依存 (たたりめ、ベノムショック、からげんき) は並びに付与手段があるときだけ倍、ふんどのこぶし・
  おはかまいり は選出での期待値 (初期は +1 段)、はたきおとす は持ち物あり前提で 1.5 倍。
- 命中は被覆表の全技に掛ける (生成だけでなく使用率の型の採点にも効く)。補正: ふくがん、はりきり、ノーガード、ちどりあし、
  すながくれ・ゆきがくれ、こうかくレンズ、雨のかみなり・ぼうふう、雪のふぶき。
- 計算は `advisor/damage.py` に入れ、助言 (実戦) と構築で同じ関数を使う。助言側の挙動が変わるので、変更は training_changes.json に記録する。

### 7.6 条件つき技と天候・フィールド

- `move_effects.json` の `condition` に種類を持つ: terrain_required (アイアンローラー: さらに使うとフィールドを消す)、berry_eaten (ゲップ)、
  target_asleep (ゆめくい)、user_asleep (いびき、ねごと)、first_turn (ねこだまし、であいがしら)、opponent_attacking (ふいうち)、
  no_item_held (アクロバット)、weather (ソーラービーム、ウェザーボール、ぼうふう/かみなり/ふぶきの命中)、terrain (ワイドフォース、
  ライジングボルト、ミストバースト、グラススライダー)。
- 生成では、条件が「自分の型」「並びの始動源 (相方の特性・技)」「相手」のどれで成立するかを判定し、成立しない技は候補にしない。
  ウェザーボールは並びの天候で決まるタイプとして採点する (晴れなら炎、雨なら水、砂なら岩、雪なら氷)。始動源が無ければ候補外。
- 並びの天候・フィールドが 2 系統衝突する場合 (リザードン Y + カバルドン) は減点し、記事に注記する (完全禁止はしない: D-12 は「意識させる」)。
- 助言側もこの表を使い、条件が成立しない技を推奨しない (アイアンローラーの過大評価の修正)。

決定の根拠: D-02〜D-05、D-08、D-12、D-14。

## 8. 積み技

- 3 軸で決める (D-01):
  1. **何が下がるか** (boost_moves.json / move_effects.json の self.boosts): 攻撃側の低下 (オーバーヒート系 −2、ゴールドラッシュ −1、
     ばかぢから 攻撃 −1 防御 −1)、防御側の低下 (インファイト系)、素早さの低下 (アームハンマー等)。
  2. **型の計画** (役割): sweeper_setup は上げた能力を下げる技を主 STAB にしない (反復できる STAB があれば残り枠のとどめとしてのみ)。
     breaker / pivot / cleaner は低下技を優先して良い。wall_* は防御側の低下技を避ける。tr_ace は素早さの低下を気にしない。
  3. **特性と代替**: あまのじゃくは低下技が最良。低下しない代替が無い種 (サーフゴー) は同居を許し、反復できる STAB を主にする。
- 積み技の候補は、役割の雛形が要求する上昇 (主攻撃 / 防御側 / 素早さ) に合うものだけ。速度計画が trick_room の並びでは素早さを
  上げる積み技を候補にしない。攻撃型で主攻撃が上がらない積み技 (こうそくいどう単体) は、速攻の個体が担当の相手に対して上を取れて
  いないときだけ。
- 使用率の型は一体の候補なのでそのまま。技 1 本の入れ替えは行わない (D-10)。
- 常識フィルタの積み技一覧はデータ由来に済み (c3cf2573、D-18)。

### 9.2 選択 (並びへの適合)

- 特性は型の一部として §6.2 で決める。候補の特性それぞれに、並びの構想 (天候・フィールドの計画、交代戦、速度計画) と担当する相手
  (物理が多ければいかく、炎が多ければもらいび) に対する価値をタグから出し、最大のものを採る。使用率は同点のときだけ (D-10)。
- 価値 0 の特性しか無い種はそのまま (ヒスイバクフーンの frisk)。

### 9.3 計算への反映

- `advisor/damage.py` は特性の分岐をコードで持つのをやめ、効果表を読む (式の種類は固定の enum: 倍率、タイプ変更、無効、命中、急所、
  反動無効、追加効果の削除)。助言と構築で同じ表を使う。

決定の根拠: D-09、D-10。

## 10. 持ち物

- 型の候補は「持ち物の候補クラス」(§6.1) から複数の持ち物を持つ (例: sweeper_setup → オボン / ラム / タスキ / たま、使用率にある
  持ち物を先頭に)。並びに既にある持ち物の候補は捨てる (D-11)。クローズによる差し替えは廃止する。
- 消費アイテムと特性 (かるわざ、しゅうかく、はんすう、ほおぶくろ)、きのみとゲップ、カゴのみとねむる、こだわり系と変化技 (トリック・
  すりかえを除く) は雛形の整合規則として候補の段階で満たす。
- こだわり持ちの型にはトリック・すりかえを補助枠の候補に入れる (M-C で 57 種が習得、D-15)。
- 6 体の持ち物が全部埋まらない (候補が尽きる) 場合は、その並びを捨てる (差し替えで無理に通さない)。

決定の根拠: D-11、D-15。

## 11. 性格・配分

- 現行の微調整 (想定する相手に合わせた上を取る / 耐える / 倒す の配分探索) を、想定する相手 = 担当する相手にして使う。
- トリックルームの個体は素早さ 0、下を取る方向 (現行どおり)。壁型の性格は使わない側の攻撃を下げる (現行どおり)。

## 12. 自爆・捨て技の費用

- 自爆 (だいばくはつ、ミストバースト、じばく)、おきみやげ、みちづれ、いのちがけ は役割 trapper / suicide_lead の雛形でだけ候補にする。
- 評価では「1 回だけ数える」: 被覆表の値はその技で倒せる相手 1 体分だけ加え、使った個体を失う費用 (その個体の以降の被覆を 0 にした
  V の減少) を引く。使用率の型にある自爆技も同じ費用で比べる (D-16)。

## 13. 常識フィルタの位置づけ

- 残す: こだわり + 変化技 (トリック以外)、カゴ + ねむる無し、きのみ技 + きのみ無し、攻撃的持ち物 + 耐久配分。
- 廃止: 差し替えで壊れた型の救済 (差し替えが無くなる)。デメリット技の個別の禁止は作らない (D-05)。
- 使い方: 一体で作った型の最終検査のみ。違反は候補から外す。

## 14. 測定からの戻り (S8a / S8b → S5)

### 14.1 位置

- S8a screening (cheap 適応 + 100〜300 戦) の後と、S8b の後の 2 か所。それぞれ 1 周、合計 2 周まで (`BUILD_REPAIR_ROUNDS`、初期 2)。
- 診断に使う対戦は探索 fold (SEARCH fold B) の記録だけ。SELECTION と封印 HOLDOUT は使わない。holdout は最後に 1 回 (現行どおり)。

### 14.2 診断 → 制約

対戦記録 (battle_log.py: 選出・先発・交代・KO・資源・メガ使用・残り個体) を敗因統計 (loss_stats.py) にかけ、以下を制約に変換する。

| 診断 | 制約 |
|---|---|
| 負けに最も効いた相手の系統 (loss_by_opponent_family、n ≥ `BUILD_REPAIR_MIN_N`) | `must_cover`: その系統を担当する枠を作る |
| 一度も選出されなかった個体 (unused_members) | `replace_candidates`: 差し替え対象 |
| 誰に何で倒されたか (ko_source) の集中 | その技・個体への受けを要件に |
| 発動しなかった持ち物・使われなかった技 (resource_usage) | 型の変更対象 |
| メガの使用と勝敗 (mega_usage_vs_outcome) | メガ枠の見直し |
| 選出ごとの敗率 (loss_by_our_selection) | selection_plan の更新 |

### 14.3 修理モード

- S5 を「修理モード」で呼ぶ: 親の並びのエースと核は固定、変更は `BUILD_MAX_CHANGES` (既存、2) 枠まで。
  型だけの変種 (B) を先に、個体の入替 (A) を次に作る。選出方策だけの変種 (C) は S7 の適応で扱う。
- 変種には系譜 (parent、変更内容、根拠の診断) を付け、racing の次のラウンドに腕として加える (racing はラウンドごとに腕を増やせる)。
- LLM の仮説は使わない (D-28: LLM の役割は大まかな方針から核を形成することに限る)。interventions.py の仮説スキーマと検証は廃止し、
  決定的な経路 (診断 → 制約 → 修理モード) だけにする。
- 構想そのものが特定の系統に負け続ける場合の S4 への戻り (再構想) は後の版。

### 14.4 歯止め

- 周回 2 回、変更 2 枠、腕の追加は 1 周あたり `BUILD_REPAIR_ARMS` (初期 6) まで。
- 封印 holdout は最後に 1 回。記事に系譜と診断を出す。

決定の根拠: D-20。
