# 海外で開発されたポケモン対戦 AI の知見の調査 (2026-10-30)

開発者依頼の調査。この プロジェクト (画面認識 → 状態 → 採点 (legacy / transition) → 表示、構築はシムの対戦評価 + 封印 holdout、
相手の型は使用率 DB と実戦バンク) の次の設計に活かせる知見を集めた。コードは変更していない。

- 読んだもの: 論文 (arXiv)・GitHub の README・Smogon の公開フォーラムと統計の公開ファイル・Hugging Face のモデルカード・競技の公式ページ。
  個人のブログ記事の本文は読んでいない。一覧は §8。
- 数値はすべて出典に書かれていた値で、この調査で測ったものは無い。出典の本文で確かめられなかったことは「未確認」と書いた。
  WebFetch の要約を経由して読んだため、図の中の数値 (GXE の表など) は読めていないものがある。
- この プロジェクト側の記述は、作業ツリーの docs と advisor/ のコードで確かめた (どの文書・ファイルかを書いた)。

## 0. 要点

> 訂正 (2026-10-30 レビュー): 「実機で人に勝っている」は「Showdown 上の対人戦で実績がある」に、「レート 1500 以上」は「cutoff 1500 の重み付け」に訂正。transition の V は RL を使わない。「P7 で不採用」「LLM の行動予測が低精度」は今それを優先しない根拠であり、方式全般が無用である証明ではない (行動予測は確率分布の良さと意思決定への効果で評価する)。

1. Showdown 上の対人戦で実績がある系は、今回確認した競技・調査の範囲では 2 系統 (この プロジェクトのような画面認識からの運用実績はどちらも示していない): **探索 (Foul Play: Rust の高速エンジン + 同時手番の MCTS)** と
   **リプレイからのオフライン RL (Metamon とその派生)**。NeurIPS 2025 の PokéAgent Challenge の上位は全部この 2 つで、LLM 系は及ばなかった (§1.5)。
2. 相手の型は、どの系も **使用率統計で候補を作り、観測 (ダメージ・行動順・判明技・天候の継続ターン等) で絞り、尤度で重みづけしてサンプリング** する。
   この プロジェクトの ev_infer (候補集合のベイズ更新) と同じ考え方で、違いは「点推定を探索に渡すか、複数の世界を深い探索に渡すか」(§3.2)。
3. **Smogon の使用率統計に Champions の BSS (gen9championsbssregmb / regmc) が出ている** (2026-09 の regmc、cutoff 1500 の集計で 69,462 戦。1500 はレーティングの不確実性を含めた重み付けの基準で、対戦数をその帯の独立標本数とは扱えない: https://www.smogon.com/forums/threads/weighted-stats-faq.3478570/)。
   配分 (Spreads)・同時採用 (Teammates)・Checks and Counters を含む。この プロジェクトは Smogon を gen9ou の予備としてしか使っていない (§2.1)。
4. 画面から実機で運用している対戦 AI は見つからなかった。主な系は全部 Showdown のプロトコルで動く。画面系は名前の読み取り・オフライン解析の段階 (§1.12)。
5. 取り入れる価値が高いのは、費用の小さい順に「Smogon の Champions BSS 統計を事前分布の候補に足して実戦バンクで尤度を比べる」「外部ボットを評価の相手に加える」(§6)。
   LLM をターン内に置くこと、浅い探索に多世界サンプリングだけを足すこと (既に棄却済み) は勧めない (§7)。

## 1. 各 AI

### 1.1 Foul Play (pmariglia、2025 再公開) と旧 showdown bot
- 出典: https://github.com/pmariglia/foul-play (README)、Smogon フォーラム https://www.smogon.com/forums/threads/3767378/ (2025-07-05 〜 2025-12)、
  PokéAgent Challenge の報告 https://arxiv.org/html/2603.15563 の付録 E.1。旧リポジトリ https://github.com/pmariglia/showdown は現在 Foul Play と同じ README。
- 方式: Rust の対戦エンジン poke-engine で探索する。旧版の expectiminimax (到達は 5 ターン程度、付録 E.1) を、同時手番に強い MCTS (DUCT、ルートで並列化) に置き換えた。
  有望な手筋は 10 ターン以上、そうでない手筋は 2〜3 ターン。局面評価は手作りの静的評価で、ロールアウトは使わない。
- ダメージ乱数: 16 乱数 × 急所の 32 通りを、**倒せるかどうか等の実際の影響で束ねる** (付録 E.1)。
- 相手の型: Smogon の使用率、フォーラムの構築、公開リプレイから候補を作り、ダメージ・技の優先度・天候の継続ターン・使った技から絞り、
  **尤度で重みづけして相手の構成をサンプリング**して探索する (付録 E.1)。
- 計算時間: Showdown の持ち時間に合わせて 1 手あたり約 7 秒を目安にし、時間が余れば 2 回目の探索を回す (フォーラム、開発者の発言)。推奨は 4 コア・16GB。
- 結果: PokéAgent Challenge の Gen 9 OU で優勝 (決勝 50–14)。Gen 9 Random Battles で GXE 90% 超 (最高 2341)、Gen 9 OU で GXE 80% 超 (最高 1879) (付録 E.1)。
  フォーラムでは gen3ou で一時 4 位 (開発者は運が良かったと書いている)。
- 開発者が挙げた弱点: どくどく のような遅れて効く効果を評価しにくい、評価関数を NN に替えたら遅くなり反復回数が減って弱くなった、ボットと知られると突かれる。
- 示唆: (a) 乱数の束ね方は transition の M2c と同じ考え方 (§5)。(b) 探索の強さは「速いエンジン × 時間」で出ている。この プロジェクトの遷移は Python で未対応の効果が残るため、同じ深さは前提が違う。
  (c) 評価を重くしないこと。

### 1.2 Technical Machine (David Stone)
- 出典: https://github.com/davidstone/technical-machine (README)、documentation/team_building.md。年は README に記載なし (例のチームは 2020 年初めの統計、未確認)。
- 方式: 深さ指定の探索 (全体の探索の深さ + その後の 1 対 1 の読みの深さ、既定 2 と 0、合計 4 以下を推奨)。探索の名前は README に無い (expectiminimax かは未確認)。
- 相手の型: 使用率から始め、**見えた個体・技ごとに同時採用の倍率を掛けて**残りの個体と技を順に埋める (例: カイリキー 12.98% が セレビィ 同伴で約 1.3 倍)。
  持ち物・特性は技構成から最頻のものを選ぶだけ。対戦中の証拠は たべのこし のような明らかなものだけで、こだわり系の行動からの推定はできない。
- 努力値: 使用率ではなく計算で、同じ耐久を最小の努力値で作る配分に詰め、残りを配る。
- チームプレビューがある形式では「どの部分集合を出し、どれを先発にするか」の問題になると書いている。
- 結果: README に評価の数値は無い。
- 示唆: 同時採用の条件づけは、この プロジェクトでは構築の助言 (`advisor/team_advice.py` の teammate_usage) にしか使っていない。相手の型や選出の予測に使うかは検討の余地 (§6-5)。

### 1.3 Athena2020 (Sarantinos、2022)
- 出典: https://arxiv.org/abs/2212.13338 (ar5iv 版で本文を確認)。
- 方式: 2 ターン先読み、各決定で利得行列を作り、同時手番なので alpha-beta の代わりに前向きの枝刈りと分散の置換表。相手の手は利得行列と履歴から後悔最小化のモデルで予測し、最善応答を選ぶ。
- 不確実性: 乱数は約 8 値に限定し、分岐は次のターンだけ、それ以降は平均的な運を仮定。種族が分かれば使用率で残りを推定、分からなければ整数計画で代表種族を選ぶ。
- 結果: Gen 7 Random Battle で 643 戦 (2020-08-22〜25 頃)、最高 33 位。AWS の 48 コア機 4 台。
- 示唆: 「利得行列 + 相手の手の予測 + 最善応答」はこの プロジェクトの legacy の探索 (`advisor/search.py`) とほぼ同じ構造。チームプレビューの無い形式なので相手種族の推定部分はそのままは使えない。

### 1.4 Metamon (Grigsby ほか、UT Austin、2025)
- 出典: https://arxiv.org/html/2504.04395v2 (RLC 2025)、https://github.com/UT-Austin-RPL/metamon (README)。
- 方式: 探索なしの Transformer (15M〜200M) を、人のリプレイからの模倣学習とオフライン RL で学習。相手への適応は入力の履歴だけで行う。
- データ: 観戦ログから**一人称の視点を復元**する。見えない情報は「使用率と、似たリプレイで判明したチーム」で埋め、判明した情報は対戦の前の時点まで遡って書き戻す。
  論文時点で Gen 1〜4 の 475k 戦超 (約 950k 軌跡)、README では raw replays 2.7M 戦・parsed 5.3M 軌跡。希少な種族は全期間の統計に退避。
- 構築: 多様性のための自動生成 (形式あたり 11k)、リプレイから推定した上位勢のチーム、フォーラムの見本チーム 10〜20 の 3 種。README は見本チームに過学習したと書いている。
- 結果: 最良のモデルが Gen1OU で GXE 79.9% (Glicko-1 1761 ± 35)、最高 31 位、活動中の上位 10% と推定。Foul Play には Gen 3・4 で互角、Gen 1・2 で上回る。
  自己対戦のデータは自分相手には強くなったが、人相手の成績の改善は一貫しなかった (論文)。
- 示唆: 「自己対戦で強い ≠ 人相手で強い」はこの プロジェクトのシムと実戦のずれの議論と同じ。リプレイからの模倣は Champions の大量のリプレイが無いと始まらない (§6-7)。

### 1.5 PokéAgent Challenge (NeurIPS 2025 競技) と上位の手法
- 出典: https://pokeagent.github.io/ 、報告 https://arxiv.org/html/2603.15563 (2026-03)。
- 形式: 対戦部門は Gen 1 OU と Gen 9 OU が中心 (VGC は状態空間の比較で触れるだけ)。人のリプレイ由来 4M 超の軌跡、リプレイから推定したチーム 200K 超、フォーラムの見本チームを配布。
- 結果: 上位は全部 RL か MCTS で、LLM の推論を使った参加者はいなかった。予選通過 16 枠のうち 13 枠は公開の RL の基準 (Metamon) を拡張したもの。
  既定の持ち時間 (1 手 60〜90 秒) は LLM の推論には足りず、長時間用の順位表を別に作った。評価は Full-History Bradley–Terry を主とし、Glicko-1 を Elo より優先。
- 上位の手法 (付録 E.1):
  - PA-Agent (Gen 1 OU 優勝): Metamon を土台に、モデル同士の対戦データを 6 回足すオフライン RL (人のデータの比率を 100% → 10%)。
    **候補チームを 50 以上の並びと総当たりさせ、勝率 60% 超だけを残す**。予選の GXE 80.35%。
  - Foul Play (Gen 9 OU 優勝): §1.1。
  - 4thLesson (Gen 1 OU 準優勝): Metamon のモデルの微調整 (最適化手法の変更等)、自己対戦のデータ 30 万〜40 万を追加。
  - Q (Gen 9 OU 準優勝): 50M の Actor-Critic。ヒューリスティックのボット相手に仕組みを学ばせ、固定の「コーチ」と過去の自分相手に戦略を学ばせる。最大の伸びは学習に使うチームの集合を替えたとき。
- 示唆: 評価相手の多様さ (外部のボット・チームの集合) が強さを決めている。相手チームの集合を替えたときの伸びが最大という Q の記録は、この プロジェクトの相手プールの議論と同じ方向。

### 1.6 PokéLLMon (Hu ほか、2024)
- 出典: https://arxiv.org/abs/2402.01118
- 方式: LLM に対戦のテキストの結果を返して方策を直す (in-context RL)、外部知識の参照で幻覚を抑える、同じ行動を複数回生成して一貫させ「慌てて交代する」現象を抑える。
- 結果: ladder で勝率 49%、招待した人との対戦で 56%。
- 示唆: 慌てた交代 (強い相手を前に逃げ続ける) は LLM 系に共通の失敗として PokéAgent の報告でも挙がっている。ターン内の LLM は使わない (§7)。

### 1.7 PokéChamp (Karten ほか、2025)
- 出典: https://arxiv.org/abs/2503.04094 (本文は html 版)
- 方式: 深さ k の minimax で、LLM が「自分の候補手の生成」「相手の手の予測」「葉の局面評価」の 3 つを担う。候補には常に 1 手読みの最善の技と、ヒューリスティックのボットの最善の交代を加える。
  1 手読みはダメージ計算で倒すまでのターン数を出し、命中は期待値で扱う。k や候補数の具体値は本文から読めなかった (未確認)。
- 相手の型: Showdown の過去データ (技の候補・努力値・持ち物) と LLM の推論で能力値の尤度を推定。データは 300 万戦超 (うち高レート 50 万超)。
- 結果: GPT-4o で PokéLLMon に 76%、最強のルールベースのボットに 84%。Gen 9 OU の Elo 1268、時間切れを除いた推定 Elo 1300〜1500。
  **実機の ladder の約 3 分の 1 を時間切れで落とした** (持ち時間 150 秒 + 1 手 最大 15 秒)。相手の手の予測の正解率 (top-1) は 13〜16%。
- 示唆: 相手の手の予測は LLM でも当たらない (13〜16%)。この プロジェクトで P6-b (相手行動の事前分布) が棄却されたこととも矛盾しない。

### 1.8 EliteFurretAI (VGC、開発中)
- 出典: https://github.com/caymansimpson/EliteFurretAI (README)。年は README で未確認。
- 方式: 人のデータで初期化 → 自己対戦 (RNaD、リーグ学習)。深さ制限・強い枝刈りの探索 + 方策・価値ネットの MCTS を計画。
- 結果: 教師ありモデル (約 30.9M) が人の行動の top-1 55.0%、top-3 83.5%。チームプレビュー (選出) の予測は、上位勢が同じチームを使うため過学習と自己評価。RL は始まったところ。
- 示唆: メガ進化に対応した特徴量を持つ点は Champions に近い。選出の予測が上位勢のチームの偏りで過学習する、という注意はこの プロジェクトの選出モデルにも当てはまりうる (未確認)。

### 1.9 VGC-Bench (Angliss ほか、2025、AAMAS 2026)
- 出典: https://arxiv.org/abs/2506.10326
- 内容: VGC の人の対戦ログ 70 万超、ヒューリスティック・LLM・行動模倣・自己対戦/仮想プレイ/double oracle の基準。
- 結果: 1 チームのミラーでは専門の競技者に勝てる。チーム数を増やすと単一チーム最良の手法は弱く・突かれやすくなるが、未知のチームへの汎化は良くなる。
- 示唆: 「学習・評価に使うチームの数」と「特定チームでの強さ」の取引。この プロジェクトの「登録チームに特化した学習」と「一般的なチームでの評価」の使い分けと対応する。

### 1.10 FutureSightML (チームだけから勝率を予測)
- 出典: https://huggingface.co/HotHams/FutureSightML (モデルカード)。作者名・年はモデルカードに無い (未確認)。
- 方式: Transformer + 個体同士の相性行列の枝、640 超の手作り特徴の XGBoost との組み合わせ。形式ごとに較正。メガ進化等の世代の仕組みを特徴に含む。
- 結果: チームだけからの勝敗予測の AUC (レートを揃えた held-out): Gen 9 OU 0.760、Gen 3 OU 0.859 など。
- 示唆: 構築探索の前段の安い代理評価の候補 (§6-6)。ただし学習には構築と勝敗の組が大量に要る。

## 3. 問いごとのまとめ

### 3.1 操縦 (技・交代の選択)
| 系 | 手の選び方 | 深さ | 相手の手 | 局面評価 | 時間 | 実機の実績 |
|---|---|---|---|---|---|---|

### 3.2 相手の型の推定
- 共通: 使用率で候補を作る → 観測で絞る。Foul Play の観測はダメージ・技の優先度・天候の継続ターン・使った技。Technical Machine は同時採用の倍率。Metamon は似たリプレイの判明チーム。
- 探索への渡し方: Foul Play は**尤度で重みづけしたサンプリング**を深い MCTS に渡す。PokéChamp は能力値の尤度を推定して LLM に渡す。Technical Machine は最頻を 1 つ。
- 持ち物: Technical Machine はメッセージで分かるものだけ。こだわり系を行動から推定する仕組みは確認できた範囲では Foul Play の「使った技」以外に無い (詳細は未確認)。
- 努力値: Technical Machine は「同じ耐久を最小の努力値で」の計算。ほかは使用率の Spreads。

### 3.3 構築
- Metamon: 自動生成の多様なチーム / リプレイから推定した上位勢のチーム / フォーラムの見本 (少数) の 3 種。見本チームへの過学習を README が認めている。
- PA-Agent: 候補を 50 以上の並びと総当たり、勝率 60% 超を残す (この プロジェクトの測定段と同じ発想)。
- Technical Machine: 使用率と同時採用の確率に比例したサンプリングで多様なチームを作る。
- FutureSightML: チームだけからの勝率予測 (AUC 0.76〜0.86)。
- **記事のような少数の実例を構築の入力に使う例**: フォーラムの見本チーム 10〜20 を評価・学習に使う例 (Metamon、PokéAgent) はあるが、少数の記事から型・並びを抽出して探索の種にする例は見つからなかった。

### 3.4 実機での運用
- 画面から運用している対戦 AI は見つからなかった (§1.12)。
- 時間の制約の記録: Foul Play は約 7 秒/手、PokéChamp は 150 秒 + 15 秒/手で 1/3 時間切れ、PokéAgent は 60〜90 秒/手が LLM に足りない、Athena は数秒/手。
  この プロジェクトの実機の基準 (p95 ≤ 3 秒、docs/STATUS_20261023.md) は、人が読んで入力する時間を残すため、これらよりずっと厳しい。

## 4. 前提の違い (この プロジェクト vs 海外の対戦 AI)

| 項目 | 海外の主な系 | この プロジェクト | 影響 |
|---|---|---|---|
| 状態の入手 | Showdown のプロトコル (誤りなし) | 画面認識 (フレームの破棄、誤認識。docs/PROJECT_STATUS.md §2.1) | 深い探索ほど入力の誤りを強く信じる (docs/TOP_PLAYER_PLAN.md の指摘) |

| エンジン | Rust の poke-engine、Showdown 本体 | Python の transition (未対応の効果あり) + ローカル Showdown (シム) | 助言の経路で深い探索をする速さが無い |

## 6. 取り入れる価値の高い順

費用は「小 = 1 セッション程度の実装 + 既存の道具で検証」「中 = 数セッション + 新しい測定」「大 = データ取得や新しい依存を含む」。効果は見込みで、測っていない。

1. **Smogon の Champions BSS 統計を、型の事前分布の候補として評価する**
   - 期待する効果: 実機の DB に欠けやすい配分・持ち物・技の候補の補強 (Spreads・Items・Moves)。少数派の型の取りこぼしが減る可能性。
   - 費用: 小。chaos の取得は `usage_scraper.py` にある。フォーマット名と名寄せ (メガの表記等) の追加、既存の混合の設計 (docs/DESIGN_PRIOR_MIXING_20261023.md) に入れるだけ。
   - 前提の違い: Showdown の模擬のプレイヤー層・Showdown 版 Reg M-C の内容が実機と同じかは未確認。混ぜて悪化しうる。
   - 検証: 実戦バンクの判明技・持ち物・観測ダメージに対する予測の対数尤度を、現行の DB / Smogon / 混合でオフライン比較 (holdout の対戦で)。良ければ決定再生ハーネスで推奨の反転率。

2. **外部の強いボット (Foul Play) をシムの評価相手に加える**
   - 期待する効果: 評価軸が自前の方策・相手プールに閉じている偏りを減らす (Metamon の「自分相手に強くなっても人相手には一貫しない」、Q の「相手の集合で最大の伸び」)。強さの外部の基準ができる。
   - 費用: 中〜大。Rust のビルド、新しい依存 (要承認)。Champions の形式 (メガ・BSS の 3 体選出) に poke-engine が対応しているかは未確認で、対応していなければ使えない。
   - 前提の違い: Foul Play は 7 秒/手の想定。シムでは時間を揃える必要がある。
   - 検証: まず動作確認 (数十戦、合法手・選出が通るか)。通れば legacy / transition のそれぞれと 600 戦。

3. **legacy の探索の乱数の束ね方を transition と揃える (倒せるか否かで束ねる)**
   - 期待する効果: 確定数の境目での誤判断の減少。transition は既にやっているので、legacy を既定のまま使う期間の改善。
   - 費用: 小 (`advisor/search.py` の {min, avg, max} を transition の分岐の解決に寄せる)。
   - 前提の違い: なし (形式に依存しない)。ただし既定の切替の判断 (legacy → transition) が近いなら費用対効果は下がる。
   - 検証: 対応比較 (fold B) 600 戦と決定再生。

4. **観測の手がかりを足す (天候・フィールドの継続ターン → 持ち物、行動からのこだわり系の推定)**
   - 期待する効果: 持ち物の推定の精度。BSS は 3 体で対戦が短いので、1 回の観測の価値が大きい。
   - 費用: 小〜中。画面から継続ターンを読めるか (メッセージで終了ターンが分かるか) が前提で、ここは未確認。
   - 前提の違い: Showdown は継続ターンがプロトコルで分かる。画面では読み落としがある。
   - 検証: 実戦バンクで、手がかりを入れた推定の持ち物の正解率 (判明した対戦だけ) を比較。

5. **同時採用 (Teammates) と先発 (leads) の統計で相手の選出・先発・型を条件づける**
   - 期待する効果: 相手の 3 体の選出と先発の予測、並びに依存する型 (例: トリックルームの起点役がいる並び) の推定。
   - 費用: 中。Smogon の chaos の Teammates と leads は種族単位。この プロジェクトの選出予測の現状は今回確かめていない (未確認)。
   - 前提の違い: Technical Machine の倍率はプレビューの無い形式の残りの推定。BSS はプレビューで 6 体見えるので、「どの 3 体を出すか」への条件づけとして使う。
   - 検証: 実戦バンクの相手の選出の予測の top-3 一致率・対数尤度を現行と比較。

6. **チームだけからの勝率予測を、構築探索の前段の代理評価として試す**
   - 期待する効果: 探索の候補の絞り込みの精度 (現在の課題「代理評価 (被覆) と実戦のずれ」に対する別の代理)。
   - 費用: 大。チームと勝敗の組が大量に要る。シムの対戦結果で学習すればデータはあるが、シムの偏りをそのまま学ぶ。
   - 前提の違い: FutureSightML の AUC は Showdown の人の対戦 (6 体全部出る形式が主)。3 体選出では選出が勝敗を左右するのでチームだけの予測は弱くなる見込み (未確認)。
   - 検証: 過去の run の候補 (測定済みの勝率がある) で、予測と測定値の順位相関。

7. **リプレイからの模倣・オフライン RL (Metamon の型)**
   - 期待する効果: 人のプレイに近い方策・相手モデル。外部では最も確かな実績 (上位 10%)。
   - 費用: 大。Champions の BSS のリプレイを大量に集める必要があり、取得先 (Showdown のリプレイ) はこの プロジェクトの参照先に無い (利用規約と robots.txt の確認、判断が先)。
   - 前提の違い: Showdown の模擬の人のプレイ ≠ 実機の人のプレイ。実機の対戦は画面からしか得られない。
   - 検証: 量が揃うかを先に調べる (公開リプレイの件数)。揃わなければ着手しない。

## 7. 取り入れない方がよいもの

- **LLM をターン内の意思決定に置く**: PokéChamp は実機で約 1/3 を時間切れで落とし、PokéAgent では上位に LLM 系がいなかった。相手の手の予測も 13〜16%。p95 ≤ 3 秒の制約ではなおさら合わない。
- **浅い探索に多世界のサンプリングだけを足す**: Foul Play のサンプリングは深い MCTS と速いエンジンと組で効いている。この プロジェクトでは P7・P7' として既に棄却済み。深い探索を入れる判断が先。
- **局面評価を重い NN に置き換えて探索の回数を減らす**: Foul Play の開発者が試して弱くなった。探索を深くする方向に進むなら評価は安く保つ。
- **深い探索 (MCTS) を助言の経路にそのまま入れる**: 速いエンジンと 7 秒/手が前提。Python の transition は未対応の効果が残り、画面の誤りは深い探索で増幅される。やるならシムのプレイヤーで効果を測ってから。
- **相手の手の予測モデルを作り込む**: LLM でも当たらず (PokéChamp)、この プロジェクトでも P6-b が棄却。期待値と保証値のブレンドで足りている。
- **プレビューの無い形式向けの相手種族の推定 (Athena の整数計画など)**: BSS は 6 体見えるので不要。
- **見本チーム数個だけで評価・学習する**: Metamon が過学習を認めている。記事由来のチームは相手プールの一部に留める。
