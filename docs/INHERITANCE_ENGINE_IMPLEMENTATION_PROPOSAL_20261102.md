# 外部エンジンの対象ルール対応と新プロジェクトへの開発提案

2026-11-02。ユーザーと確認した「学習・評価の計算コストを主な制約とし、必要な実装には積極的に投資する」方針に基づく提案。
対象はChampionsシングル Reg M-C、利用者1人、M1・16GBのMacBook Air 1台。

## 1. 開発担当への返信

**Foul Play＋poke-engineの対応を「小」で止めず、「中」「大」の主要項目まで実装対象に含めて進めることを提案します。**
実装は小さな変更に分け、関連する試験を通した部分から統合し、次の項目へ進みます。
行数、共通コードへの変更、状態表現の拡張だけを理由に保留しません。

今回のルール対応には、大規模な追加学習は不要です。確認したpoke-engineの操作経路は固定の評価関数と探索を使い、Foul PlayにはBSSの選出を探索する経路もあります。
必要な実装を進め、判断全体の待ち時間・メモリを測り、必要な箇所を最適化する順序を採ります。

外部データ4件が未配置でも、状態を直接与えるルール試験と修正は進められます。
データ配置・常駐8100の運用作業は別の依存事項として扱い、無関係な実装を待たせません。

次の成果物は、動く修正版、対応範囲の一覧、関連試験の結果です。実装に必要な調査を行ったら、その結果を使って修正まで進めます。
懸念には、具体的な対処案・確認方法・続行できる条件を添えてください。

### これまでの方針から変える点

- 「小まで進め、中・大は保留」を取り下げます。小・中・大は作業規模の説明に使い、着手を止める境界にはしません。
- 「へんしんで状態拡張が必要」「修正150行超」「新規効果5件超」などを自動的な候補見直し条件にしません。
- 単体の速度低下だけで対応を捨てません。同じ判断時間での正しさ・判断品質と、プロセス群全体の資源を確認します。
- 正式なB0採用、旧資産の継承、他システムに比肩する能力の主張には、引き続きそれぞれの検証を必要とします。実装への着手と最終採用は別の判断です。

## 2. 今回のレビュー結果を反映する

- Syrup Bombの継続は、T1〜T5の状態遷移とソース確認から「欠落・不具合」へ確定することを提案します。
- Triple Axelは「探索上の意図的な近似（命中回数の分布は不一致、採用未確定）」と記録します。平均の閾値10%は変更しません。
- 上記を反映した46チェックポイントの区分は、一致24／近似1／観測後だけ対応3／欠落18／参照側未確定0／レビュー待ち0です。これはレビュー上の整理であり、保存済みの測定出力は変更せず、更新した報告に履歴を残します。
- 一致24件は試した局面と許容条件での一致です。Crabhammerの表の誤りが乱数幅の検査を通った点も踏まえ、値の直接照合と動的な照合を併用します。

## 3. 実装の順序と完了条件

参照はShowdown d849b220のChampions modと継承元を解決した値・挙動とします。
実機との食い違いや参照側の未確定仕様は項目ごとに分離し、仕様が確定している他の実装を進めます。

| 順序 | 実装対象 | 完了条件 |
|---|---|---|
| 1 | 表データ、名前・状態変換の検査、メガの行動順 | 対象値を直接照合し、行動順の境界ケースが一致。既知の名前が黙って既定値へ変わらない |
| 2 | 持ち物のu16化、はどうのぼうご、壁・天候・地形の延長、レッドカード、Syrup Bomb | 発動前から探索に効果が入り、持続・終了・消費・交代を再現。命令を取り消すと元の状態へ戻る |
| 3 | Triple Axel、おやこあい、バトルスイッチ | 命中・途中終了・形態変化と行動順を参照側に照合。確定数の境界で倒せる確率を確認 |
| 4 | へんしん・かわりもの | 技・PP・能力値・特性等のコピー範囲、交代時の復元、探索の適用と取り消しを確認。観測後の入力も別に確認 |
| 5 | Foul Playの操作・BSS選出との統合、実機性能の調整 | 同じ入力契約と対応表を両経路で使い、完走・合法性・待ち時間・メモリを測定。修正版と条件を固定できる |

段階1で既知の表の差（Make It Rain、Syrup Bomb、Crabhammer、メガ、Meteor Assault、Slash等）を修正します。
Drampa-Mega、Swagger、Freeze-Dry、Dire Claw／Double Shockのflagも、参照仕様を確認できたものから対応します。
未照合64件と、黙って落ちる持ち物22件について対応状況の表を作り、Reg M-Cで必要な残件を上の工程へ割り当てます。
一覧の作成だけで対応完了とはせず、名前の認識・効果の実装・動的な検証を区別します。
イリュージョン等の観測・相手推定に属する問題は、探索内のルールとは分けて統合工程へ割り当てます。

対応表は「参照仕様／入力で表現可能／探索内の効果／観測後の追跡／検証ケース／次の変更」を持つ程度に留めます。
旧チェックポイント数と独立した不具合の数を混同せず、修復、検出して停止、未対応を別に集計します。

### 設計の選択

**持ち物は、まずu16のみで実装します。** 変種を潰して番号を空ける方法は採りません。
命令型の6→8バイトという見積もりを、プロセス全体のメモリ1.3倍と読み替えません。
局面ごとの実測と統合後のRSS・swap・待ち時間を見て、必要な場合に差分i16等の圧縮を追加します。
差分命令を導入する場合は、番号の境界、連続した変更、適用と取り消しを検証します。

**名前と状態の検査は、当面Foul Play側の共通関数に置きます。**
変換前の既知の値を保持し、操作・選出の両経路で往復後と照合します。
相手情報が未観測である状態、正当な空欄、判明済みだが未対応の名前を区別します。
相手型の候補が未対応だった場合も黙って捨てず、推定の条件変更や未対応として記録します。
新プロジェクトからエンジンを直接呼ぶ際は、同じ契約を接続部分へ移し、検査を通らない入口を作りません。

**Triple Axelは命中ごとの分岐を実装する方針です。** 威力約35への調整で平均だけを合わせる案は採りません。
命中回数、急所の条件、1・2・3発で倒せるHP、途中のひんしや防御効果を確認します。
分岐数が実用上の問題になれば、必要な確率を保持する集約・サンプリングを検討し、同じ時間予算で影響を測ります。
既存の急所分岐の推定分類は汎用的な正解判定にせず、実装後の分岐の意味に基づく検証へ置き換えます。

**へんしん系は、状態表現を拡張して実装する方針です。**
元の技等を保持する必要があること自体を中断理由にしません。コピー範囲と復元の契約を先に定め、必要な情報を追加します。
状態の保存・読込の形式が変わる場合は版を更新し、旧形式を黙って別の意味で読まないようにします。
追加状態によるメモリへの影響は測定し、実測で必要な最適化を行います。

## 4. 大規模学習を使わない検証と性能改善

1. 表の差は、継承を解いた参照データとの直接比較で検出します。
2. 効果は、少数の状態遷移と境界局面で検証します。完全情報を与える試験はエンジンのルール検査に限定します。
3. 状態を書き換える命令は、適用後の値と、取り消した後の状態の一致を確認します。
4. 関連する試験を通した変更を順次統合し、まとまった版で回帰確認します。各変更のたびに大量対戦を要求しません。
5. 性能は固定局面で早期に測り、外部データ配置後に操作・選出の全経路でも測ります。MCTS単体の反復数を判断全体の速度に読み替えません。
6. 外部データが揃ったら、まず3戦の完走で接続を確認し、その後に固定した局面群・対戦条件で品質を評価します。3戦だけで強さを判定しません。

測定はウォームアップと本測定を分け、判断全体のp50／p95、時間切れ、プロセス群のRSS・CPU・swapを記録します。
探索時間、相手型のサンプル数、並列数を少数の条件で調整し、Mac上の競合と長時間動作時の低下も確認します。
キャッシュを使う場合は状態・データ・ルール・エンジンの版を含め、修正前の結果を再利用しないようにします。

試験設計§7の90分・6時間等は、予備診断・正式比較の機械占有に対する初期予算案です。
これをルール実装の総時間上限に流用しません。正式比較は開始前に条件と予算を固定し、結果を見て判定基準を緩めません。
予備段階では有望な条件へ計算を集中し、最終確認用の相手・試行を選別用から分けます。

## 5. 操作・選出・構築へつなげる

### 操作と選出

修正版エンジンとFoul PlayのBSS選出を共通の基盤にします。旧選出モデルの再学習を前提にしません。
観測可能な情報だけを使い、相手の型・選出の推定を含む全経路を測定します。
旧モデルや旧規則を加える場合は、外部版を固定した後にB0＋Xとして比較します。

### 構築

公開された型・構築・統計、保存済みの利用可能なデータから合法な候補を作る方式を第一案とします。
候補の重複除去、安い評価による絞り込み、変更した枠に関係する評価の再利用、見込みのある候補への対戦配分で計算を節約します。
安い評価で有望な候補を落としていないかも小さく検証し、最終候補は選別に使わない相手で確認します。
まず単純な候補生成・評価を基準として固定し、旧構築器は候補生成や絞り込みの部品ごとに効果を比較します。
Foul Playの操作・選出が動くことを、構築能力も完成したという意味にはしません。

### 新プロジェクト

新プロジェクトはPython 3.9を継承せず、環境構築時にサポート中の安定版と依存のmacOS arm64対応を確認して選びます。
今回の外部環境で3.12が動いた結果は参考にしますが、採用版を自動的に3.12へ固定しません。
ローカルとCIの条件を揃え、旧資産は新しいPythonで読取・変換・推論の契約を検証します。
Python移行のための大規模再学習や、現行プロジェクトの環境の一括更新は前提にしません。

## 6. 続行・調整・見直しの判断

通常の既知ルールの修正は、関連試験を通して次の実装へ進みます。工数が増えた場合は見積もりを更新し、作業を分割します。
性能が悪化した場合は、まずボトルネックを測り、状態表現、命令、サンプル数、キャッシュ等を改善します。

候補や構成を見直すのは、実測で必要な判断期限・メモリ条件を満たせず改善案でも解消できない場合、
参照に合わせた正しい状態を表現できず代替案の方が目的を達成できる場合、または同条件でより良い実装が確認できた場合です。
その場合も、残る問題・試した対処・代替案・再利用できる成果を示します。

未確認の正しさや性能を成功として報告しない方針は維持します。未確定の1項目があっても、独立して進められる項目を実装します。
正式なB0にはコード・パッチ・データ・設定・規制を固定し、対応範囲と残る近似を明示します。
対象ルールへの修正と旧判断ロジックの追加は分離し、強さの比較中に基準を変えません。

## 7. 外部データ・8100と作業報告

外部データ4件は既存の手動配置手順を継続します。未配置を空データで通さず、入手できない対象があれば別条件のデータ構成を明示して検討します。
常駐8100の変更は、PIDの確認、復旧手順、具体的な1戦の確認コマンド、起動時と稼働中の外部宛て通信の観測を手順書へ揃えます。
外部取得と常駐への適用は従来のユーザー判断・権限に従います。この提案は、それらが実行済みであることを示しません。

次回報告は、先に開発担当への返信、その後に開発者向けの説明を置きます。
実装した項目、正しくなった挙動、検出して停止する項目、関連試験、性能、残件と次に実装する内容を簡潔に示してください。
ユーザー判断が必要な項目には推奨案を添え、独立した作業の進捗も報告します。

## 8. 開発者向けの説明

最終目標は、Mac1台で他システムに比肩する操作・選出・構築能力を持つ新プロジェクトです。
現在は、動作した外部エンジンを対象ルールへ対応させる段階です。大規模な独自学習を避けるために、ルール実装・探索・統計の利用・評価計算の効率化へ投資します。
今回の方針変更により、中・大の対応も進める提案に変わりました。次の到達点は、実装と局面検証を重ねた修正版で操作・選出を完走させ、実用条件を測ることです。
強さは別途評価し、その基盤の上で構築探索と旧資産の有用性比較へ進みます。
