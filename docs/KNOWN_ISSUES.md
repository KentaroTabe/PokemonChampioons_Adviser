# 課題台帳 (機能別・ファミリー別)

接続テスト第2〜11回・監査・インシデントの記録から、欠陥を**個別事象ではなく
ファミリー**として整理した台帳。状態は
✅解消 (再発防止テストあり) / 🟡緩和 (主経路は塞いだが残余あり) /
👁 要観察 (要求は有効だが今すぐ確実に改善できない。観察条件を明記) の3値。
更新は接続テストの終了処理・監査のたびに行う。詳細な経緯は
docs/CONNECTION_TEST_CHECKLIST.md と docs/incidents/ を参照。

## A. 対戦情報の認識・抽出

### A1. メッセージ取り逃しファミリー (最重要・構造的)

**構造**: ゲームのメッセージは演出中に1〜2秒で流れ、処理落ちで破棄された
フレームの情報は永久に失われていた (負荷時54-76%破棄の実測)。
「メッセージを読んで状態を更新する」設計は原理的に不完全で、
(1) **確実に取れる情報源からの決定的反映**、(2) **破棄フレームからの
救出バッファ** (2026-08-31: 軽量トリガーでメッセージ/ポップアップ域を
退避し非同期OCR — キャプチャと処理の分離)、(3) 定点での照合、の三層へ
設計を移した。

**測定基盤 (2026-08-31 新設)**: `scripts/advice_replay.sh` — 決定再生
ハーネスで「認識誤り→推奨反転率」をフィールド別に実測できる。初回
(120決定点): 自分HP固着28.1% / 相手判明技消失23.9% / 相手HP固着20.7% /
選出フラグ消失18.9% / 相手ひんし見逃し10.2% (高マージン反転0)。
**認識投資の優先順位はこの表に従う** (件数の多さではなく提案への影響順)。

共通原則: **書き込みは my_team のみ・対戦状態に触れない・2フレーム裏付け・
検証を通らない読みは登録しない** (誤登録より未登録)。

**2026-09-06 方針変更 (ユーザー決定): 型登録は手入力ベース。画面認識による登録は諦める。**
第12回接続テストで、パーティ管理画面の読み取りはドドゲザンを持ち物/配分/性格のみ、
ブリジュラスは特性・技が旧登録のままなど部分登録に留まり、手入力の値を上書きする
危険の方が大きいと判断。上記の画面経路はコードとして残すが
`advisor/my_team.py` の `AUTO_REGISTER_FROM_SCREEN = False` で既定無効。
登録は `bash scripts/register_my_team.sh` (推奨構築 final_team.json から一括、
フォルムは「種族ID」で保持し自分側の種族解決が尊重する) か config/my_team.json の直接編集。
回帰テスト: tests/test_my_team_manual.py
**持ち物のメガ石** (2026-09-29 第17回): 手入力の「メガガブリアスZナイト」が文字列類似で無印の石に解決され、選出画面の OCR も
末尾 X/Y/Z を落とす。→ 石名は構文 (種族部 + 接尾辞の厳密一致) で解決し、画面の読みと登録が同じ種の石のフォルム違いなら
登録を採る (tests/test_mega_stone_names.py)。名前表の表記は「<種族名>ナイトX/Y/Z」だが、どちらの並びでも解決できる。
なお、画面経路のローカルテスト tests/test_look_more.py (images/look_more、git 管理外) は 9/6 時点で能力タブ由来の持ち物/特性/技が保存されず失敗する (今回の変更を退避しても同じ失敗 = 既存の回帰)。方針上、画面経路には工数をかけないため未修正のまま記録する。
