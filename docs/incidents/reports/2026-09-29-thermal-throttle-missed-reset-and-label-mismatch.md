## 1. 前提: 接続テストと試用 Package

接続テストは、操作パネル (launchd 常駐、8010) の「開始」で助言サーバー (8000) を起動し、Switch の画面を 10 fps で送って
助言を受けながら実戦を行い、「終了」で対戦ログの集計・決定監査・試用 Package の実戦サマリー・改善案の測定起動・一括視覚監査
を行う。試用 Package は `logs/.experiment_package` の experiment ラベルで指定し、対戦ログの先頭 (session 行) に package_id
が書かれる。9/25 に run arch_0924 の 1 位 L06_C020 (リザードン / カバルドン / サザンドラ / メタグロス / アシレーヌ /
オオニューラ) を canary + install + ラベル ON にしていた。

助言サーバーは受信フレームを処理できたぶんだけ拾う (処理中に届いた分は最新 1 枚を保持し、それ以外は破棄。破棄分は
メッセージ域だけ退避して後から OCR)。対戦の区切りは、選出画面に「入場」したときに状態をリセット (世代番号 battle_seq を
上げる) し、対戦ログはその世代番号でファイルを分ける。学習ループ (`train_forever`) は 9/27 13:40 から稼働していた
(`config/training.env` は on_demand。起動の経緯は未確認)。

## 2. 何が起きたか

### 2-1. 熱圧迫による処理率の低下

統合ログ (`/usr/bin/log show`, `symptomsd`) の熱圧迫の遷移:

| 時刻 | thermal-pressure |
|---|---|
| 00:31 | Moderate |
| 00:59 | **Heavy** |
| 01:17 | Moderate |
| 01:19 | **Heavy**(02:26 に Moderate へ) |

同時刻に動いていたもの: 学習ループのサイクル 89 (00:44〜01:17) と 90 (01:17〜02:13、`smoke_train` 4 環境)、Showdown、
助言サーバー (Apple Vision OCR + 探索)。サイクル 90 は balance の学習が 912 秒で正常に終わったあと、offense (01:32〜01:52)
と cycle (01:52〜02:13) が**タイムアウト**した (機械全体が遅くなった証拠)。

助言サーバーの `[server] scene=… 受信=… 処理=…` 行から対戦ごとに処理率を出すと:

| 対戦 (ログ) | 開始 | 処理率 | 助言あり (決定監査) |
|---|---|---|---|
| 1 (001841) | 00:18 | 50% | 100% |
| 2〜4 (L06、002443 / 002904 / 003520) | 00:24〜00:44 | 63 / 66 / 34% | 67 / 88 / 100% |
| 5〜9 | 00:44〜01:24 | 46 / 98 / 65 / 43 / 43% | 67 / 80 / 100 / 57 / 100% |
| 10 (012421) | 01:24 | **18%** | 90% |
| 11・12 (013036、2 戦連結) | 01:30 | **9% / 9%** | 32%(後半の戦は 0) |
| 13 (014801) | 01:48 | **9%** | 50% |
| 14・15 (015515、2 戦連結) | 01:55 | 18% | 19%(後半の戦は 0) |

セッション全体: 受信 42,018 / 処理 11,400 = 処理率 27% (2.7 fps)。7/27 の基準 (62% 破棄、3.8 fps) より悪い。

### 2-2. 対戦状態が次戦に持ち越された(助言が止まった直接原因)

処理率 9% では、ユーザーが素早く操作する command 画面 (技選択の前の画面) を 1 フレームも取れないことがあり、その対戦は
turn が 0 のまま終局した (013036 の前半、015515 の前半)。勝敗文言・ランク画面は取れたので `outcome` と `battle_ended` は
立ち、`battle_active` は下りた。

次戦の選出画面は確定 (3 フレーム連続) で検知されたが、リセット判定が

```python
if self.state.turn > 0 or self.state.battle_active:
    self.reset()
```

だったため (turn=0 かつ battle_active=False)、リセットされなかった。その結果:

- `outcome` が残ったまま次戦に入り、助言は `not state.get("outcome")` の条件で**一切計算されない**(015515 の後半: 助言 0 件、
  013036 の後半: 助言 0 件)
- 世代番号が上がらないので対戦ログも分割されず、1 ファイルに 2 戦 (`analyze_battles` は 13 戦と数えたが実際は 15 戦)
- 前戦の場のポケモンの状態 (持ち物 None、HP 0) が次戦の表示に残った

記録に残っていたサイン: 013036 / 015515 の `events` に `battle_end_rank` が 2 回、`rate` が 2 回。決定監査で「turn 0」の
決定が 14 件並び、後半に「助言なし」が連続。

### 2-3. こだわりロックを無視した推奨(002904、L06 の 2 戦目)

サザンドラ (こだわりスカーフ) が 1 ターン目にりゅうせいぐんを使った。使用文「サザンドラのりゅうせいぐん」は取れず、
自分への効果「特攻ががくっと下がった」(72.6 秒) だけが読めた。engine のこだわりロックは `last_move` (技の使用文から
立つ) を根拠にするため、ロックを知らないまま 2 ターン目 (83.6 秒) に**あくのはどう** (85.8 点) をりゅうせいぐん (73.1 点)
より上に推奨し、118 秒にはとんぼがえりを推奨した。138.6 秒に 2 回目のりゅうせいぐんの使用文が取れて初めて
「こだわり中: りゅうせいぐんしか選べません」になった。

もう 1 つの形 (002443、L06 の 1 戦目): サザンドラに交代したあと command 画面を取れず助言が更新されないまま、直前の
アシレーヌ向けの助言 (ムーンフォース) が表示に残った。ログ上の助言 (137 件) には、ロックを engine が認識していながら
別の技を推奨した例は無い。

### 2-4. 試用 Package の実戦サマリーの混入

experiment ラベルは対戦のたびに session 行へ package_id を書くだけで、実際に使ったパーティを見ない。ユーザーは 3 戦目まで
L06 で対戦し、以後は自分のパーティ (ブリジュラス / ガブリアス / ミミロップ / ペロリーム / イダイトウ / アシレーヌ) に
替えたが、ラベルは ON のままだったため、終了レポートの Package 実戦サマリーは 13 ログ (7 勝 6 敗) をすべて L06 の
実戦として集計した。1 戦目もパーティの読みは不完全だが、使った技 (ステルスロック / つるぎのまい / おはかまいり) から
自分のパーティと判断できる。

### 2-5. 一括視覚監査の失敗

終了処理の `tools.audit_session` が `FileNotFoundError: 'claude'` で落ちた。操作パネルは launchd の環境 (PATH =
/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin) で動き、claude CLI は `~/.local/bin/claude` にある。
チャット/ターミナルから終了処理を実行していた 9/16 までは PATH に入っていたので気付かなかった。

## 5. なぜ防げなかったか

1. **学習と同時実行の判断が古い実測に基づいていた**: 開始スクリプトの「停止不要と実測で確認済み」は 7/27 の測定 (平均 95 →
   102 ms) で、その後 OCR 救出・探索・選出モデルが増え、負荷も 1 時間以上続く前提になっていなかった。9/7 第14回でも
   同時実行で処理率 10% を経験し「測定中はテストしない」と決めたが、学習ループは対象外のままだった
2. **リセット判定が「command 画面を 1 回は取れる」ことを暗黙の前提にしていた** (turn > 0)。処理率 9% はその前提を壊す。
   気付けたはずのサイン: 9/7 第14回の記録に「command シーンが 27 分で 2 回しか記録されず turn が 0 のまま、選出画面での
   状態リセットも走らず」とあり、負荷起因と整理して条件の欠落を追わなかった
3. **こだわりロックの根拠が技の使用文だけだった**。使用文は演出中の短時間表示で取り逃しやすく、その技の確定的な自己効果
   (特攻 −2) は別の文で読めていたのに使っていなかった
4. **experiment ラベルがパーティを見ない**。ラベルは「これから試す」宣言で、対戦ごとに実際の 6 体と照合していなかった
5. **launchd の PATH の違い**を、パネル経由の終了処理を初めて本番で通した今回まで踏んでいなかった

## 8. 教訓 / 未対応の課題

- **処理率が落ちる要因は増える一方なので、負荷の判断は毎回実測する**: 統計行に処理時間を入れた。次回のテストで学習 ON/OFF の
  処理率を比べ、必要なら「テスト中は学習を止める」を開始処理に組み込む (ユーザー判断)
- **「画面 X を 1 回は取れる」前提の判定は、取れなかった場合の別の根拠を持つ**: リセット判定は勝敗の記録で補った。ターン数
  そのものも取り逃しに弱い (turn 0 のまま終局) — ターンの根拠に「行動解決の観測」以外を足すのは未対応
- **メッセージの取り逃しは、その事象の副作用から推定できることがある** (自己能力変化 → 技)。相手側の技の推定 (相手のりゅうせいぐん →
  判明技) は誤りの影響が大きいので未対応
- **ラベルは実測と照合する**: experiment ラベルは Package のパーティと突き合わせるようにした。ラベルの自動 OFF (別パーティを
  検知したら外す) は未対応 (次のテストでパーティを戻したときに困るため、警告に留めた)
- 一括視覚監査は手動で実行できる状態。パネル経由の全ジョブが同じ PATH 問題を持ちうる (node は /opt/homebrew/bin にあるので
  影響なし、`claude` だけが `~/.local/bin`)
- 学習ループは `config/training.env` が on_demand なのに 9/27 から稼働している。起動の経緯は未確認 (ユーザー確認待ち)
