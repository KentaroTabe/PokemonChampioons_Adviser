# インシデント記録: シミュレータ (advisor-as-player) が選出していない 3 体を評価に含めていた (交代候補・残存戦力・終盤評価)

## 1. サマリ

## 2. 前提

- advisor-as-player は、助言エンジン (`advisor.engine.evaluate`) をそのままプレイヤーにしてローカル Showdown (BSS、6 体から 3 体を選出) で対戦させ、助言の勝率を測る評価経路 (`champions_agent/env/advisor_player.py`)。構築の測定、RL 加点の比較、採点方式の比較がこの経路を使う。
- 助言エンジンは自分側の個体の「選出の印」(is_picked) で、交代候補・控え・残数・終盤評価の行列・transition 方式の残存戦力 (V の M) と未判明の残り (my_unknown) を決める (`advisor/party.battle_party_indices`)。実機では選出画面の読みから 3 体に印が付く。
- 実行側 (`choose_from_advice`) は、助言の第一候補が poke-env の `available_switches` に無ければ飛ばして次の候補へ進む。

## 3. 何が起きたか

`battle_to_state` (修正前):

```python
own_vals = list(battle.team.values())   # 6 体
...  _side_state(own_vals, active, True, ...)  # 全個体に is_picked=True、remaining = 生存数 (6 体のうち)
```

poke-env の `battle.team` は対戦中も 6 体のまま (10/15 に実測: 修正後の 56 決定すべてで party = 6)。選出 3 体は `battle.last_request["side"]["pokemon"]` の ident にしか現れない。そのため助言は 6 体を自分の戦力として評価し、交代候補に未選出の 3 体が入り、実行側が選べない候補を飛ばして 2 位以下の行動を取っていた。

異常のサインは記録に残っていた: 対戦記録 (battles.jsonl) の決定ごとの「第一候補」と「実行行動」が種類・id で違う決定が 3 分の 1 以上あり、`choose_from_advice` が候補を飛ばした回数も数えられたはずだった。ただし、決定の記録には合法手が無く、飛ばした理由も残していなかったので、集計は 10/15 の全数集計まで行われなかった。

## 5. 失われたもの

- 生データ: なし。
- 派生物: advisor-as-player による判定の全部 (採点方式の比較の「実用的改善を支持しない」、P1 の「×25 維持」、アークの P9 系、構築 run の順位) が「未選出を戦力に数えた比較」になっている。結論の取り直しは測定が要る。
- 時間: 採点方式の比較 (157 分) と予備確認 2 回、P1 (99 分)、アークの再測定 (5.5 時間)。

## 6. なぜ防げなかったか

- 実機の状態 (選出の印は画面から入る) と同じ辞書をシムで作ったが、「選出の印をどこから取るか」をシムで検証していなかった。poke-env の `battle.team` が 6 体のままであることを確かめずに使った。
- 気付けたはずのサイン: (1) 対戦記録の第一候補と実行行動の不一致が 4 割を超えていたのに、監査の集計が無かった (実機の決定監査は「人の行動と助言の一致」を見るが、シムでは「助言が実行できたか」を見る集計が無かった)。(2) `choose_from_advice` が候補を飛ばした回数を数えていなかった。(3) 採点方式の比較の予備確認で、勝率 0.46 / 0.32 という低い値を「一般的なチームだから」と解釈して深掘りしなかった。
- 「測定入力の受入」は型の参照の一致 (M2d) まで進めたが、選出の制約の検査を含めていなかった (レビュワーの指摘どおり「型の参照一致だけでは入力全体の正しさを保証できていなかった」)。

## 7. 復旧手順 (2026-10-15 実施)

- `champions_agent/env/advisor_player.py`: `picked_mask_of(battle)` が `battle.last_request` の side.pokemon から選出を決め、`battle_to_state` は選出だけに is_picked=True、remaining は選出のうちの生存数。要求が無い・チームプレビュー中は従来どおり (全個体)。
- 確認: 修正後の 6 戦 (legacy 3 戦 23 決定、transition 3 戦 33 決定) で「未選出への交代」の不一致 0。印の付いた個体 = 3 体 = 選出、`available_switches` との照合で食い違い 0 (43 決定)。
- 影響した判定の取り直しは未実施 (§9)。

## 8. 恒久対策

- 選出の印の決め方を関数 (`picked_mask_of`) に分け、`switchable_check` で状態の交代先と poke-env の `available_switches` を毎決定で照合し、食い違いを stats (`switchable_mismatch`) に数える。
- 全数集計の道具 `tools/diag_scoring_compare.py` (第一候補と実行行動の不一致の分類、未選出の範囲、実行した順位)。
- 診断用の記録 (`ADVICE_DIAG_LOG=1`): 決定ごとの採点入力・合法手・全候補・退避理由・実行行動・飛ばした候補を残し、`replay_diag` で再生できる。
- 回帰テスト: `tests/test_sim_picked_roster.py` (6 関数)、`tests/test_diag_scoring_compare.py` (4 関数)。
- 記録: `docs/KNOWN_ISSUES.md` C 節、正式記録 `docs/USEFULNESS_P2_SCORING_20261013.md` §5 に追記。

## 9. 教訓 / 未対応の課題

- シムの状態は実機の状態と「同じ辞書」であっても、各欄の出所を 1 つずつ検証する。特に「選べる行動」は実行側 (poke-env) の集合と毎決定で照合する。
- 助言が実行できた割合 (第一候補の実行率) を、シムの測定の受入条件に入れる。
- 未対応: (1) 影響した判定の取り直し (採点方式の比較、P1 の RL 比較、アークの P9 系、構築 run の順位) をどの順で行うかは判断待ち。(2) 残る不一致 2 種 (交代技の後の繰り出し `pending_pivot_switch` がシムに無い、技の固定・とらわれが `available_moves` と登録の補完で戻る)。(3) rl_bridge の own_bench は party の先頭 2 体を取り選出の印を見ない (実機も同じ)。(4) P1 の RL 比較の記録 (docs/USEFULNESS_P1_RL_BLEND_20261009.md) への注記。
