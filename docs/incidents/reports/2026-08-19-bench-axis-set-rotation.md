# ベンチ評価軸のセット回転 (meta_sets 未固定による絶対値比較の破壊)

- **発生**: 2026-08-19 06:33 (snapshot 9 投入)。二度目の回転が 2026-08-22 06:42 (snapshot 12)
- **検知**: 2026-08-24 (発生から5日後)。学習状況の説明準備中に、凍結重み `_best` の
  定点が 8/18→8/19 で約8SE動いていたことを発見し、遡って特定
- **復旧**: データ損失なし (復旧対象は「判定手順」)。検知当日に判定手順を補正し、
  検知の恒久対策を導入
- **影響範囲**: ベンチマーク軸 (対ヒューリスティクス絶対値) の 8/19 前後比較と、
  `_best` 昇格判定。学習分布・h2h 相対軸・選出モデルは無傷
- **失われた生データ**: なし

## 1. 前提

学習の評価には複数の軸がある。

- **ベンチマーク軸**: current / `_best` をヒューリスティクス相手に測る絶対値。
  14分ごとの50戦 (サイクル内)、日次定点3,000戦 (`tools/track_progress`)、
  節目の10,000戦。`_best` 昇格判定 (直近5回平均 vs 過去最良) もこの軸
- **h2h / vs_agents 軸**: current を凍結エージェント (3性格の `_best`) と直接
  対戦させる相対値。P1 (アンカー常駐、8/25判定) の主要指標

どちらの軸でも、両陣営のチームは `env/ranked_teams.py` が組む。**種族と持ち物**は
pokedb の上位構築アーカイブから取り、`POOL_PIN` でファイルを固定できる
(2026-08-05 の事件後、評価は s3 285構築に固定済み)。一方、**技・特性・性格・
能力ポイント**は championsbattledata 由来の `meta_sets` テーブル (各種族の
最頻セット) から補完する:

```python
# env/ranked_teams.py
def _load_meta_sets() -> dict:
    with db.get_connection() as conn:
        snap = db.latest_snapshot_id(conn)   # ← 常に最新スナップショット
```

つまり評価チームの「種族」は固定されていたが、「中身」は毎朝 06:30 の
使用率DB更新に追従していた。meta_sets は各項目の **top-1** (技は top-4) を
取るため、元データの使用率がわずかに動くだけで順位境界のセットが離散的に
入れ替わる。

## 2. 何が起きたか

championsbattledata の Current シーズン集計が 8/19 朝の取得で大きく動き、
meta_sets の再構築で **234種中127種の代表セットが実質変化**した
(技集合・持ち物・特性・性格・配分のいずれか。技の並び替えのみは除外した数)。
例: ノイバーン こだわりスカーフ→いのちのたま、ヒスイダイケンキ 技4本総入替、
ラウドボーン たべのこし→オボンのみ。

時系列 (すべて実測):

| 日時 | 出来事 |
|---|---|
| 8/16-8/18 | snapshot 6→7→8: 実質変化 **0種** (軸は安定、8/16 レポートの「ベンチ相手は不変」も当時は正しい) |
| 8/18 21:50 | 日次定点: `best_model` 0.5887 (8/11以降 0.571-0.603 で安定した水準) |
| 8/19 06:33 | snapshot 9 投入: **実質変化 127種** (うち技集合のみ63、持ち物17)。usage% の変動は全種 1pt 未満、抽選 weight の変動ゼロ = 抽選分布は不変で**セット中身だけが回転** |
| 8/19 07:16-07:29 | サイクル内50戦ベンチ (current) がこの間に一段下がる (日平均 8/18 0.610 → 8/19 0.541) |
| 8/19 21:50 | 日次定点: `best_model` **0.486** (前日から約8SE の段差)。⚠ このサインは記録されていたが5日間誰も見なかった |
| 8/22 06:42 | snapshot 12: **実質変化 88種** (二度目の回転)。`best_model` はさらに 0.482→0.456 へ |
| 8/23-8/24 | snapshot 13, 14: 変化 0種 (8/22 の軸のまま安定) |
| 8/24 | 本調査で発見。凍結 `_best`+相性選出を再測: **0.4587** (3,000戦) — 8/17 の 0.593 (10,000戦) から約13pt 低下を確認し、軸側の変化と確定 |

原因コードは §1 の `_load_meta_sets` (最新スナップショット追従)。
championsbattledata 側がなぜ 8/19 と 8/22 にまとめて動いたかは**未確認**
(観測上は約3日おきの一括更新に見える。シーズン進行でゲーム内集計が
入れ替わったものと推定するが、サイトの更新規則は不明)。

## 3. 被害の内訳

すべて実測値。

| 測定 | 8/19 以前 | 8/19 以後 | 備考 |
|---|---|---|---|
| `_best` ベンチ (凍結重み) | 0.593 (8/17, 10,000戦) / 定点 0.571-0.603 (8/11-8/18) | 0.456-0.486 (定点5点) / 0.4587 (8/24 再測) | **軸段差の直接証拠** (重みは 8/2-8/3 から不変) |
| current 50戦ベンチ日平均 | 0.603 / 0.610 (8/17-8/18) | 0.541-0.572 (8/19-8/21) | 約 -0.05。軸要因と方策要因が分離不能に |
| current 定点 3,000戦 | 0.594 (8/18) | 0.537-0.564 (8/19-8/23) | 同上 |
| `_best` 昇格判定 | 記録 0.612-0.712 (7/30-8/3、旧軸) | 新軸の `_best` 実力 ≈0.46 | **記録が構造的に到達不能になり昇格凍結** (7/29 に修正した「上振れ記録に守られる」問題の軸違い再発)。昇格候補が実際に出たかは未確認のため、失われた昇格の件数は不明 |
| P1 ベンチガードレール | 基準 0.605 (8/17) | 新軸では比較不能 | 名目適用すると P1 を誤って棄却する状態だった |

**無傷だった範囲** (同じ粒度で確認済み):

- **h2h / vs_agents 軸**: 両陣営が同じチーム分布を使う対称設計のため、相対値
  として成立し続けた。実測でも段差なし (h2h_balance_best: 0.539→0.587→0.591→
  0.620→0.590→0.602 と滑らかに推移)。ただし §5 の交絡に注意
- **学習分布**: 学習チームが生きたメタに追従するのは仕様どおり (被害ではない)
- **使用率データそのもの**: 2026-08-05 と違い、データは正当なメタ変化。汚染なし
- **選出モデル**: 収集データは自前の実対戦で、8/23 の再学習 (M2解消) の測定は
  収集と評価が同一軸内のため影響なし
- **アドバイザー配布**: `_best` は変わっていないため挙動は安定 (昇格凍結は
  「より強い候補が配布されない機会損失」であって劣化ではない)

## 4. 失われたもの

- **生データ**: なし。snapshot 8 の meta_sets も DB に残っており、旧軸での
  再測は技術的に復元可能 (ピンを 8 に向ければよい)
- **派生物**: 8/19 を跨ぐベンチ絶対値の前後比較可能性。8/19-8/24 のベンチ系列は
  「新軸の値」として内部比較のみ有効
- **時間**: 8/19 以降の `_best` 昇格機会 (件数不明)

## 5. なぜ防げなかったか

1. **「不変の確認」を「不変の保証」と取り違えた。** 8/16 のレポートで
   snapshot 6→7 の meta_sets 不変を確認し「評価基準は据え置き」と結論したが、
   それは当日の観測にすぎない。固定 (pin) は ladder ファイル側にだけ実装し、
   セット補完側は latest 追従のまま放置した
2. **気付けたはずのサイン**: 8/19 21:50 の定点で凍結参照 `best_model` が
   約8SE 動いた値が JSONL に記録されていた。定点は値を書き溜めるだけで、
   「凍結参照が統計誤差を超えて動く」ことへのアラートがなかった
3. 日次更新ログは「取得 235件 / rows=235」と件数しか出さず、中身の回転が
   見えなかった

## 6. 復旧手順

データ復旧は不要。実施したのは判定手順の補正と検証:

```bash
bash scripts/agent_bench.sh 3000 balance 20260730 matchup   # → 0.4587 (軸段差の確定)
```

meta_sets の snapshot 間 diff は一時スクリプトで直接 SQL 比較した
(実質変化の定義は `count_substantive_changes` として本体に恒久化)。
P1 (8/25) の判定手順の補正は `champions_agent/train/training_changes.json`
の 2026-08-24 エントリに事前登録した (測定開始前の手順修正):

- 主要指標 (h2h) は登録どおりだが、**軸対照**として P1 適用直前の凍結アンカー
  (checkpoints/anchors/*_20260818.zip) の h2h を同日に測り、ベースライン 0.514 が
  新軸でも成立しているか確認する
- ベンチガードレールは旧基準 0.605 との比較をやめ、**同日・同軸のペア比較**
  (アンカー vs current、各10,000戦・同一シード・逐次) に置換
- 全測定は 8/25 06:30 更新の完了後に開始し、更新でセット回転が再発していないか
  を先に確認する (回転していても同日内で完結すれば内部整合は保てる)

## 7. 恒久対策

- `champions_agent/data/build_meta.py`: meta_sets 再構築時に前スナップショット
  との実質セット変化数を毎朝の更新ログへ出力し、閾値
  (`config.META_SET_CHANGE_WARN` = 10種) 以上で警告 (`count_substantive_changes`)
- `tools/track_progress.py`: 凍結参照 `best_model` が前回から
  `config.FROZEN_REF_WARN_SIGMA` (=3) SE を超えて動いたら警告 (`deviation_sigma`)
- 回帰テスト: `tests/test_meta_axis_guard.py` (並び替え非計上 / 実質変化の計数 /
  8/19 実測値で警告が発火することの再現)

## 8. 教訓 / 未対応の課題

- **凍結参照は最良の軸センサー。** 動かないはずのものが動いたら、まず測定側を
  疑う。今回それを人力に頼って5日落とした
- **「毎日更新されるデータから top-1 を取る」構造は境界で離散的に跳ねる。**
  評価基準に使うなら固定が必須で、片側 (ladder) だけの固定は固定にならない
- 未対応 (P1 判定後に実施予定):
  1. **評価側の meta_sets ピン** — 評価経路だけスナップショットを固定する設計。
     学習側は生きたメタ追従を維持する必要があり、共有経路
     (`build_ranked_teams`) の分離設計が要る
  2. **`_best` 昇格記録の再基準化** — ピン導入と同時に新軸で記録を取り直す
     (7/29 の方式に従う)。それまで昇格は事実上停止したままである点に注意
