# インシデント記録: 使用率DB更新の最中に隔離学習が27時間ハング

- **発生**: 2026-08-16 19:41 JST(使用率DB復旧の実行中)
- **検知**: 2026-08-17 22:36 JST(翌日の本判定を実施する前の状態確認で発覚。27時間後)
- **復旧**: 2026-08-17 23:15 JST(ハングしたプロセスを停止。実験は本判定で
  棄却済みのため再開しない。恒久対策の1と2は同日実装、3は未対応)
- **影響**: 隔離実験 `arch_v7mlp` の自己対戦が停止し、事前登録された本判定が
  計画学習量の約62%で行われた。**本番の学習は無傷**
- **失われたもの**: 27時間分の学習(推定5〜9Mステップ)。
  チェックポイントとログは無傷

---

## 1. 前提: 隔離実験と本番の走らせ方

新アーキテクチャの検証は、本番の学習に触れずに並走させる方式を採っている
(`docs/RL_V7_SET_ENCODER_DESIGN.md`)。

| | 本番 | 隔離実験 |
|---|---|---|
| 起動 | launchd → `train_forever.sh` → `train_nightly.sh` | `scripts/arch_v7_run.sh`(手動 nohup) |
| 学習の実体 | `tools.smoke_train --timeout 1038` | `champions_agent.train.train_battle`(直接) |
| 並列環境数 | 4 | 2 |
| モデル出力先 | `champions_agent/train/checkpoints/` | `logs/arch_v7mlp/checkpoints/` |

どちらもバトルごとに使用率DBからチームを生成する
(`ChampionsTeambuilder` → `build_random_party`)。

## 2. 何が起きたか

2026-08-16 19:40:07〜19:41:23、別インシデントの復旧として使用率DBの更新
(`update_usage_db.sh`)を実行した。隔離学習のログはその最中の **19:41:10 を最後に
出力が途絶え**、以後27時間、一行も進んでいない。

```
logs/arch_v7mlp/run.log 最終行   2026-08-16 19:41:10
最後の節目                       第181/300回 (08-16 19:26 開始)
最後のチェックポイント            08-16 19:38 / 18,505,728ステップ
```

プロセスは死んでおらず、**生きたまま CPU 0%** で停止していた。
`sample(1)` で採取したスタックは `_Py_read` → `read()` システムコールでブロック。
2026-08-11〜12 に46時間止まったデッドロックと同じ形である。

### 原因(推定・未確認)

トレースバックが残っていないため機構は確認できていないが、コード上は次の
競合が成立し、停止時刻とも秒単位で一致する。

1. `ingest_usage_stats` は **`usage_snapshot` 行を先に作成**し、そのあとに
   使用率の行を流し込む
2. `build_meta`(`meta_sets` の生成)は**別プロセスとして後から**走る
3. その数秒間、`latest_snapshot_id()` は新スナップショットを返すが、
   そのスナップショットの `meta_sets` はまだ空
4. この窓でチーム生成が走ると `build_random_party` が
   「meta_sets の候補数(0)がパーティサイズ(6)未満です」で例外を投げ、
   バトル開始のハンドシェイクが壊れて環境が応答を待ち続ける

## 3. 被害の内訳

- **隔離実験 `arch_v7mlp`**: 8/16 19:41 以降の学習がすべて失われた。
  判定時点の学習量は 18.5M ステップで、計画 30M(300ラウンド×100k)の約62%
- **本判定への影響**: 8/17 の本判定は事前登録どおり実施した
  (arch_v7mlp 0.475 vs 本番current 0.605、差 -0.130、95%CI -0.144〜-0.116 で棄却)。
  差の大きさとCI幅(±0.014)、8/15定点 0.4947 からの横ばいを踏まえると
  27時間分で覆る余地は小さいが、**「学習を続けていれば届いた」の反証にはならない**
- **8/16 の無益性足切り(参考値0.45)は未実施**。日次トラッキングが
  8/15 21:53 を最後に走っておらず、ハングと合わせて二重に見落とした

### 無傷だったもの

- **本番の学習**: 同じ時刻に走っていたが停止していない。
  `tools.smoke_train --timeout 1038` の watchdog 経由で、
  仮に同じ例外を踏んでも17分で打ち切られて次ラウンドへ進む
- **チェックポイント**: 8/16 19:38 保存分が正常に残っており、本判定に使用できた
- **使用率DB**: 更新自体は正常に完了している(snapshot 7、222構築)

## 4. なぜ防げなかったか

**watchdog が本番経路にしか入っていなかった。** 2026-08-12 の停止インシデントを
受けて「watchdog 導入済み」と記録したが、入ったのは `tools.smoke_train` の
`signal.alarm` であり、隔離実験の `scripts/arch_v7_run.sh` は
`train_battle` を直接呼んでいて時間制限がない。

これは前日(2026-08-05 の使用率DB汚染)とまったく同じ構造である。あちらも
チームプール側だけが保護され、DB書き込み側が無防備のまま残っていた。
**根が同じ不具合を片側だけ塞ぐ**という同一の失敗を、2件連続で踏んだことになる。

気付けたはずのサインは、run.log の更新が19:41で止まっていたこと。
節目行を追う監視はあったが、**止まったことを検知する仕組みが無い**
(無音は「異常なし」と区別がつかない)。

## 5. 恒久対策

1. **スナップショットの可視性を原子的にする(2026-08-17 実装済み)** —
   `latest_snapshot_id()` を既定で「`meta_sets` に行があるスナップショットのみ
   返す」に変更(`require_meta=True`)。ingest 直後〜`build_meta` 完了までの
   窓では前のスナップショットが返り続け、チーム生成は壊れない。
   `meta_sets` を作る `build_meta` だけが `require_meta=False` で生の最新を見る。
   回帰テスト: `tests/test_snapshot_visibility.py`(5ケース)。
   日次更新を launchd で有効化しても、本番学習がこの窓を踏むことはなくなった
2. **隔離実験にも watchdog(2026-08-17 実装済み)** — `arch_v7_run.sh` の
   `train_battle` 直呼びを、本番と同じ `tools.smoke_train --timeout` 経由に
   変更(1ラウンド上限は既定3600秒、`ROUND_TIMEOUT` で変更可)。
   打ち切っても途中保存があるため進捗は失われない
3. **無音検知(未対応)** — run.log が N 分更新されなければ警告する。
   節目行の監視だけでは停止を検知できない

## 6. 教訓

1. **長時間ジョブが走っている最中に、その依存データを書き換えない。**
   読み取り側が毎バトルDBを引く設計なら、更新は原子的に見せるか、
   ジョブを止めてから行う
2. **「片側だけ塞ぐ」を繰り返さない。** 2件連続で、同じ根の不具合が
   保護されていない経路から再発した。修正時は「同じデータ・同じ処理を
   使う別経路」を洗い出してから閉じる
3. **無音を異常として扱う。** 進捗ログの節目を見る監視は、
   止まったジョブに対して何も言わない
