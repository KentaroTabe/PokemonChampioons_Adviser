# 2026-10-04 LLM 審査の実験で、失敗した呼び出しが「指摘なし」として集計された

## 1. サマリ

- 発生: 2026-10-04 17:05〜17:13 (検証実験 4 の Haiku 2・3 周目、20 束の呼び出しが全部失敗)。
  検知: 同日 17:13 (結果の出力の直後。2・3 周目の指摘率が 0.0、呼び出し記録が 60 件のはずが 100 件)。
  復旧: 同日 22:50 (失敗した 20 束だけ呼び直して結果ファイルを上書き)。
- 影響: `logs/build_search/experiments/llm_audit.json` の Haiku 側の値と、tier 間・規則との一致度が偽の値になった
  (Haiku の繰り返し間 κ 0.333、多数決の指摘率 0.0、tier 間 κ 0.0、規則との κ 1.0)。約 5 時間 37 分、結果ファイルに残っていた。
  この値を根拠にした判断は無い (17:13 の報告で無効と明記した)。
- 失われた生データ: なし。成功していた 40 回 (Sonnet 30 回 + Haiku 1 周目 10 回) の記録は無傷で、やり直しではそのまま再利用した。
  失われたのは、やり直しの約 40 分と、原因が分かるまでの待ち時間。

## 2. 前提

検証実験 4 (`tools/team_build/experiments/llm_audit.py`) は、構築システムが役割の雛形から生成した型を LLM に見せ、
閉じた選択肢 (性格と技の不整合、持ち物の不整合など 7 カテゴリ) で「変な点」を判定させる。同じ 100 型を
Sonnet と Haiku でそれぞれ 3 周ずつ判定し、繰り返し間・tier 間の一致度 (Cohen の κ) を出す。κ が 0.7 以上なら
LLM を判定器として使える、という判断の材料にする (変更案の項目 14)。

呼び出しは `tools/team_build/llm/provider.py` の `ClaudeCLIProvider` が `claude` CLI をヘッドレスで起動して行う。
`provider.call` は失敗すると最大 2 回再試行し、それでも駄目なら `{"ok": False, "authoritative": {}}` を返す (例外は出さない)。
CLI はこのチャットのセッションや構築 run の S4 (Opus) と同じアカウントの利用上限を共有している。

## 3. 何が起きたか

1. 15:03 に実験 4 を起動した (10 型ずつ 60 回の呼び出し)。Sonnet の 30 回 (1 回 195〜215 秒、16:46 まで) と
   Haiku 1 周目の 10 回 (17:05:35 まで) は成功した。
2. 17:05:42 の呼び出しからアカウントの利用上限に当たった。CLI は rc=1 で終了し、標準出力の JSON に
   `"api_error_status":429` と `You've hit your session limit · resets 7:40pm (Asia/Tokyo)` を返した。
   Haiku 2・3 周目の 20 束はそれぞれ 3 回試行して全部失敗した (60 回の試行、17:13:26 まで、1 回 5〜8 秒)。
3. 実験のコードは `provider.call` の成否を見ていなかった (修正前):

   ```python
   res = provider.call(stage, tier, SYSTEM, payload, schema=SCHEMA,
                       validator=lambda a: [] if isinstance(a.get("verdicts"), list) else ["verdicts が配列でない"])
   labels.update(parse_verdicts(res.get("authoritative") or {}, chunk))
   ```

   `parse_verdicts` は「応答に無い id は空集合」を返すので、失敗した束の 10 型は全部「指摘なし」になった。
4. 17:13 に実験が正常終了の形で結果を書いた。出力には `[haiku#2] 指摘率 0.0` `[haiku#3] 指摘率 0.0` と出ていた
   (他の 4 周は 0.56〜0.68)。記録ディレクトリには 100 件のファイルがあり、うち 60 件が `_a1` `_a2` `_a3` の失敗の試行だった。

## 5. 失われたもの

- 生データ: なし。失敗した試行の記録も残っている (原因の特定に使った)。
- 派生物: 結果ファイルは上書きで正しい値になった。誤った版は作業用ディレクトリに控えがあるだけで、リポジトリには無い。
- 時間: やり直しの 39 分 (22:11〜22:50) と、上限のリセット (19:40) を待った時間。
- 費用: 失敗した 60 回の試行は記録上の費用が無い (`cost_usd` が null)。実験全体は $9.33 (Sonnet $6.75、Haiku $2.58)。

## 6. なぜ防げなかったか

- 実験のコードが呼び出しの成否を見ていなかった。テスト (`test_llm_audit`) は成功する mock だけを通していた。
- 「判定が無い」と「指摘が無い」を同じ値 (空集合) で表していたので、集計の段では区別できなかった。
- 60 回の呼び出し (約 3 時間) を、同じ時間帯に S4 の Opus 呼び出し (約 $24) とチャットのセッションが同じ上限を使っている状態で始めた。
  CLI から上限の残量を確かめる手段は未確認。
- 気付けたはずのサイン: 2・3 周目の指摘率 0.0 (他の周は 0.56〜0.68) と、記録 100 件 (想定 60 件)。
  今回は出力の直後に気付いたが、結果ファイルだけを後から読む人には分からなかった。

## 7. 復旧手順

1. 失敗の試行の記録から原因を確認した (429、上限のリセットは 19:40)。
2. コードを直し (8 章)、記録から再利用できる束を呼び出しなしで数えた: 再利用 40、呼び直し 20 (Haiku 2・3 周目だけ)。
3. やり直した:

   ```
   python -m tools.team_build.experiments.llm_audit --run-id ace_lopunny_1003 --n 100 --repeats 3 \
       --tiers sonnet,haiku --resume logs/build_search/experiments/llm_audit/20261004_150315
   ```

4. 確認: 6 周すべて「判定が得られた型 100 / 100」、結果の `n_failed` が全部 0、Sonnet の値が 17:13 の版と同じ。

## 8. 恒久対策

- `tools/team_build/experiments/llm_audit.py`
  - `audit_once`: 呼び出しが `ok` でなければ、その束の型を None (判定なし) にする。
  - `flag_rates` / `agreement` / `majority`: None を分母から外す。対ごとの κ は両方で判定が得られた型だけで出し、その数 `n` を結果に書く。
  - 結果に `n_failed` (周ごとの判定なしの数) を書き、1 つでもあれば出力で知らせる。
  - `--resume <記録のディレクトリ>` と `cached_verdicts`: 同じ段・同じ入力・同じ system の成功した記録を再利用し、失敗した束だけ呼び直す。
- 回帰テスト: `tests/test_team_build_experiments.py` の `test_llm_audit`
  (失敗する provider で全部 None になること、None が指摘率と κ の分母に入らないこと、成功の記録は再利用して呼び出さないこと、
  失敗の記録と system の違う記録は再利用しないこと)。

## 9. 教訓 / 未対応の課題

- 失敗と「該当なし」を同じ値で表さない。集計に渡す前に区別を持たせ、分母を結果に書く。
- LLM を数十回呼ぶ処理は、途中で止まっても成功分を再利用できる形にしておく (今回は記録に入力と応答が残っていたので後付けできた)。
- 未対応: `provider.call` は 429 でも同じ呼び出しを 2 回再試行する (上限に達していれば必ず失敗する)。
  429 は再試行せずに呼び出し側へ伝える方がよいが、S4 の挙動にも関わるので今回は変えていない。
- 未対応: 長い LLM 処理を始める前に利用上限の残量を確かめる手順が無い。
