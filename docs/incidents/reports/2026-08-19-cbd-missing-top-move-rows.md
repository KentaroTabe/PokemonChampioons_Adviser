# 2026-08-19 championsbattledata の技上位行欠落による代表型の汚染

- **発生**: 2026-08-18 18:12Z 生成の championsbattledata (以下 cbd) データを取り込んだ
  2026-08-19 06:33 (snapshot 9) から。以後 2026-09-05 (snapshot 27) まで毎日
- **検知**: 2026-09-05 (発生から17日後)。構築候補のカバルドンが
  「まもる / ほえる / こおりのキバ / ストーンエッジ」という実在しない型で生成されたことから遡って特定
- **復旧**: 同日。build_meta に「技データが薄い種は直近の健全な型を引き継ぐ」保護を入れ、
  最新スナップショット 27 を再生成 (47種を置換)。過去分 9〜26 も同保護で作り直し
  (評価軸 META_PIN=24 だけは軸を動かさないため据え置き)
- **影響範囲**: `meta_sets` (各種族の代表型) の技構成。学習の相手プール・ベンチ/h2h の
  相手チームの中身・アドバイザーの相手型予測・構築提案の型に流れる。
  8/19 の [ベンチ軸セット回転](2026-08-19-bench-axis-set-rotation.md) の根本原因でもある
- **失われた生データ**: なし (cbd の日次ペイロードはアーカイブ済み。ただし欠落は
  cbd 側の書き出しで起きており、欠落した行そのものは当日のデータとしては存在しない)

## 1. 前提

使用率DB (`champions_agent/data/db/champions.sqlite3`) は毎朝 06:30 の日次更新で
2 つの外部データから作られる。

- **pokedb オープンデータ**: 上位ランカー構築 (223構築)。種族の使用率%・共起率・
  ベンチ用チームプール (種族と持ち物) の元
- **championsbattledata (cbd)**: ゲーム内「バトルデータ」の日次収集 API。
  種族ごとに `move / held_item / ability / stat_alignment / stat_points / teammate`
  の各カテゴリ **上位10行** (`rank` 1〜10、採用率%) を返す

`champions_agent/data/build_meta.py` は各種族について、cbd の各カテゴリの
**最多 (技は上位4)** を貼り合わせて代表型 (`meta_sets`) を作る。この代表型が
自己対戦の相手プール、ベンチ/h2h の相手チームの技・特性・性格・配分の補完、
アドバイザーの相手型推定 (`advisor/ev_infer`)、構築提案 (`tools/evaluate_team`) に流れる。

つまり「技の上位行が欠ければ、6〜10位の技だけで代表型が組まれる」構造だった。

## 2. 何が起きたか

cbd の書き出しが、2026-08-18 18:12Z 生成分から、**日替わりの 26〜48種で `move`
カテゴリの 1〜5位の行を落とし、6〜10位の行だけを返す**ようになった。
他カテゴリ (持ち物・特性・配分・共起) は 10 行揃っており無傷。

実データ (アーカイブ `champions_agent/data/archive/cbd_Current_singles_<日付>.json.gz`、
カバルドンの `move` 行):

| 取得日 | cbd 生成時刻 (UTC) | move 行数 | 上位の技 |
|---|---|---|---|
| 9/03 | 09-02 15:23 | 10 | じしん 97.7% / あくび 94.3% / ステルスロック 83.4% / ふきとばし 56.9% / なまける 42.9% / まもる 12.0% … |
| 9/04 | 09-03 16:36 | **5** | **まもる 12.0% / ほえる 4.1% / こおりのキバ 1.5% / ストーンエッジ 1.4% / がんせきふうじ 1.3%** |
| 9/05 | 09-03 16:36 (同一) | 5 | 同上 (cbd 側が 9/3 16:36Z から更新されていない) |

9/4 の 5 行は 9/3 の 6〜10 位と一致する (採用率もほぼ同じ)。つまり上位 5 行が
書き出しで落ちている。当日の `build_meta` はこれをそのまま最多として採用し、
カバルドンの代表型が「まもる / ほえる / こおりのキバ / ストーンエッジ @ゆうばんストーン」
になった。

原因コード (保護導入前の `build_meta_sets`):

```python
moves = _top_n(conn, "move_usage", "move_name", snapshot_id, name, 4)  # 残っている行の上位4をそのまま採用
```

## 4. 失われたもの

- **生データ**: なし。cbd 日次ペイロードは全日アーカイブ済み。ただし欠落した
  上位行は cbd 側で落ちているため、その日の値としては復元できない
  (直近の健全な日の値で代用する = 恒久対策の引き継ぎ)
- **派生物**: snapshot 9〜27 の `meta_sets` (欠落由来の 29〜50種/日)。
  保護つきで作り直し可能 (§6)
- **時間**: 8/19 の軸段差の原因調査 (当時「cbd 側が動いた」で打ち切り)、
  9/2 のウォッシュロトム型の個別対処

## 5. なぜ防げなかったか

- **取り込み時に行の形を検証していなかった**。cbd は各カテゴリ 10 行が仕様なのに、
  5 行でも黙って受け入れた
- **build_meta は「残っている行の最多」を疑わない**。上位種の最多技が 12% という
  値は、健全なら起き得ない (上位30種の最多技は全期間で 46〜99%)
- **セット回転の警告が常時鳴っていた**ため、日次の 34〜63 種回転を「cbd の自然変動」
  と読んでいた。警告は「軸が動いた」ことしか伝えず、「なぜ動いたか」を示さなかった
- 気付けたはずのサイン: `build_meta` の日次ログに「実質セット変化 127種」が出た
  8/19 の時点で、変化した種の技の採用率を 1 つでも見れば
  「1 位の技が 12%」に気付けた

## 7. 恒久対策

- `champions_agent/data/build_meta.py`: `is_thin_moveset` / `carry_forward_row`。
  最多技の採用率が `META_THIN_MOVE_PCT` (40%) 未満の種は、直近 10 スナップショット
  以内で技データが健全な (生の最多技 ≥ 40%) スナップショットの代表型を引き継ぐ。
  引き継げる過去が無ければ従来通り当日の最多で組む (棄却しない)。
  引き継いだ種のうち使用率 `META_THIN_LOG_MIN_USAGE` (5%) 以上は日次ログに名前を出す
- `build_meta_sets(snapshot_id=...)` で過去スナップショットを作り直せるようにし、
  `tools/repair_meta_thin.py` を追加 (META_PIN は自動除外)
- 閾値の根拠: 健全な上位30種の最多技は 46〜99%、欠落時の残り最多は 4.9〜28.9%
  (アーマーガア 28.9% が最大)。40% で全期間の欠落 (26〜48種/日) を分離できた
- 回帰テスト: `tests/test_meta_thin_guard.py` (5 件: 純粋判定 / 引き継ぎ元の選択 /
  build_meta_sets の引き継ぎ / 過去指定の再生成 / 履歴なし時の従来動作)。
  CI サブセット (`scripts/ci_tests.sh`) に登録
- 副次効果: cbd がシーズン切替直後にサンプル薄で同じ症状 (上位技の分散) を
  示しても、旧シーズンの健全な型が維持される

## 8. 教訓 / 未対応の課題

- **外部データは行の形 (件数・順位の連続性) を取り込み時に検証する**。「値が変わった」
  警告だけでは原因に辿り着けない。異常の中身を 1 件見るコストは小さい
- **代表値の妥当性を絶対値で見る**。「残っている中の最多」は最多ではない
- 上位種の最多技 < 40% を取り込み時 (ingest) にも警告する対策は**未実装**
  (build_meta の引き継ぎログで代替)
- 8/19〜9/1 の学習分布の歪み (寄せ集め型の上位種が相手プールに混ざった影響) は
  **未測定**。学習は最新 meta_sets を毎サイクル読むため、9/5 以降は自然に解消する
- META_PIN=24 の軸は寄せ集め型 4 種を含んだまま。9/9 の再基準化で解消予定
