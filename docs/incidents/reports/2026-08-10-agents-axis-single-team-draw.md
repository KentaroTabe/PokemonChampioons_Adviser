# インシデント記録: 対エージェント軸が「1走行1チーム」で8日間測られていた

- **発生**: 2026-08-10(対エージェント軸 vs_agents の導入時)
- **検知**: 2026-08-18 01:05 JST(凍結した同一ネット同士の再測が 0.617 / 0.373 と
  振れたことから調査)
- **復旧**: 2026-08-18 01:45 JST(自チームを毎戦引き直しに修正、再現性を実測確認)
- **影響**: 8/10〜8/18 の vs_agents 系列すべてと、8/17-18 の乖離解析のうち
  agents 軸を使った所見。**ベンチマーク軸・本判定(8/17)・昇格判定は無傷**
- **失われたもの**: なし(生データ・モデルは無傷)。無効になったのは
  vs_agents 系列の解釈と、それに基づいた一晩分の分析結論の一部

---

## 1. 前提: 2つの評価軸

学習の進捗は2軸で測っている。

| 軸 | 相手 | 導入 |
|---|---|---|
| ベンチマーク | 上位60構築 × ヒューリスティクス | 7月 |
| vs_agents | 上位60構築 × 過去の配布方策(_best 3性格巡回) | **2026-08-10** |

ベンチマーク軸には設計上の教訓が既に埋まっていた。かつて自チームを
「生成チーム1個を全戦使い回し」にしていたところ、**勝率がチームドローの
当たり外れで±0.2以上振動した**ため、「相手と同じ上位構築を毎戦引き直して
等条件にする」修正が入り、その経緯はコード内コメントに記録されていた。

## 2. 何が起きたか

自チームの構築は `opponent_kind` による分岐で決まる。

```python
if opponent_kind == "benchmark":
    own_teambuilder = RankedTeambuilder(top_n=60, ...)   # 毎戦引き直し
else:
    own_team = build_random_team_text(...)                # 1回生成して
    own_teambuilder = ConstantTeambuilder(own_team)       # 全戦使い回し
```

8/10 に追加された vs_agents 軸(`opponent_kind == "agents"`)は
**benchmark 分岐に入らず else 側へ落ち、過去に±0.2振動の実績がある
「1走行1チーム」の経路で8日間測定されていた。** 相手側は上位60構築を
毎戦引き直すため、条件も非対称だった(生成チーム1個 vs 上位構築群)。

### 検知の経緯

8/17 深夜の乖離解析で、同一条件のはずの測定が繰り返しごとに大きく
振れた(0.234 / 0.405 / 0.565)。当初は (a) 並列実行の歪み、(b) 方策の
短周期振動を疑い、**ネットを凍結して測定だけを繰り返す**切り分けを行った:

| 凍結ネット同士の同一測定(1,500戦・逐次) | 勝率 |
|---|---|
| 1回目 | 0.617 |
| 2回目 | 0.373 |
| 3回目 | 0.404 |
| 4回目(劣化カウンタ計装後) | 0.571 |
| 5回目(同) | 0.410 |

重みが完全に同一でも 0.24 動く = 測定自体の崩壊。計装の結果、
方策のフォールバック(劣化)はほぼゼロで、**走行間で平均ターン数が
25%違う**ことが決め手になった。1走行1チームなら、チームが変われば
勝率も試合の長さも走行単位で変わる。5走行の標準偏差 0.11 は
二項ノイズ(0.013)の8倍で、チーム品質の分散として整合する。

## 3. 被害の内訳

### 3-1. vs_agents 系列(8/11〜8/18)の解釈が全て無効

| 日付 | vs_agents | 実態 |
|---|---|---|
| 8/11〜8/12 | 0.472 / 0.4713 / 0.52 | 各点±0.1級のドロー運を含む |
| 8/13〜8/15 | 0.593 / 0.626 / 0.618 | **使用率DB汚染で生成チームが実質14種(メタ中核種)からしか引かれず、毎回「強いチーム」を引いていた** |
| 8/18 | 0.4093 | DB復旧で109種に散り、ドロー運が戻った |

「4点連続の上昇 → 飽和仮説」「2日で-0.17の崩落」という解釈は、
どちらも**自チーム抽選分布の変化**で説明される。皮肉なことに、
汚染期間の値が最も安定して見えた(引けるチームの分散が小さかったため)。

### 3-2. 乖離解析(8/17-18)の所見の一部が無効

- **「current は _best に頭打ち 0.405 で負けている」— 撤回。**
  1チームのドロー付き・非対称条件の測定だった。真の頭打ち関係は
  修正後の再測定で確定する
- 「並列評価が水準を歪める」— **未確認に格下げ。** 根拠だった
  0.234 vs 0.405 の差はチームドローで説明できる(凍結5走行は
  すべて逐次で、それでも振れた)。逐次規律は予防措置として残す
- 「vs_agents 軸の脆さ」— 軸自体の欠陥として確定(別の意味で正しかった)

### 3-3. 無傷だったもの

- **ベンチマーク軸**: 毎戦引き直しの修正済み経路。日次系列(0.57〜0.61)の
  安定はこの設計差の実証でもある
- **8/17 の本判定(arch_v7mlp 棄却)**: ベンチマーク軸のペア測定。影響なし
- **昇格判定(best_checkpoint)**: vs random / vs benchmark のみ使用。影響なし
- **8/14 の Set Encoder 無益性棄却**: 日次定点の arch_v7 列はベンチマーク軸
  (`opponent="benchmark"` 相当の matchup 測定)。影響なし
- vs_agents 単独を根拠にした不可逆な意思決定は無かった

## 4. なぜ防げなかったか

**過去の故障の教訓が、コメントとして残っているだけで構造化されていなかった。**
「1チーム使い回しは±0.2振動する」という実測済みの教訓は benchmark 分岐の
修正とコメントに封じ込められ、8/10 に新しい分岐(agents)を追加したとき、
その分岐は素通りして旧経路に落ちた。修正が「その分岐だけのパッチ」だと、
後から増えた分岐は保護されない — 使用率DB汚染(8/5)・watchdog 欠落(8/16)と
同じ「片側だけ塞ぐ」構造の3例目である。

気付けたはずのサイン: vs_agents は導入直後から日次で±0.05以上動いていた
(ベンチ軸は±0.02)。「動きの大きい軸」を「感度が高い」と好意的に解釈し、
分散の出どころを検算しなかった。

## 5. 復旧と恒久対策(2026-08-18 実装済み)

1. **agents 軸を benchmark と同じ毎戦引き直しに統一**
   (`opponent_kind in ("benchmark", "agents")`)。条件も対称になった
   (両陣営とも上位60構築)。修正後、凍結ネット同士の再測 2 回が
   二項ノイズの範囲で一致することを確認した(§6)
2. **方策の劣化カウンタ**(調査の副産物): BattlePolicy の
   masked / argmax_fallback / random_fallback / load_failed を計数し、
   評価結果に両陣営分を併記。モデル未ロードの静かな全戦ランダム化は
   警告+参照ロード失敗は即時エラーになった
3. **測定値の再基準化**: vs_agents / h2h の過去系列は比較不能として扱い、
   修正後の測定で基準を取り直す(P1 の事前登録判定のベースラインも再登録)

## 6. 教訓

1. **実測済みの教訓は、コメントではなく構造で残す。** 「使い回しは振動する」
   と分かっていたなら、既定を毎戦引き直しにして、使い回しを明示オプトインに
   すべきだった。パッチ+コメントは新しい分岐を保護しない
2. **分散が想定より大きい測定は、感度ではなく欠陥を疑う。**
   二項SEの何倍も動く時点で、走行単位の共通因子(この場合は1チーム抽選)を
   探すべきだった
3. **「ネットを凍結して測定だけ繰り返す」切り分けは強力。** 方策の振動と
   測定の分散を1実験で分離でき、今回の特定の決め手になった
