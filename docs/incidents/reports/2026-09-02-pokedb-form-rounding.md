# 2026-09-02 pokedbフォルム丸めによる使用率の誤集計

## 1. サマリ

- **発生**: 2026-07-17(pokedbオープンデータ統合の初回取り込み、snapshot 3)
- **検知**: 2026-09-02 未明。構築提案に「基本フォルムのロトム」が採用されたのを見た
  ユーザーが「基本ロトムは種族値が低くほぼ使われない。接続テストでも遭遇していない」と
  指摘し、調査で発覚
- **復旧**: 2026-09-02(名前解決の修正 + 過去20スナップショットの再集計)
- **影響範囲**: champions系スナップショット(3〜22、7/17〜8/31)の
  `pokemon_usage` / `teammate_usage`、および同じ関数を使う学習・評価用の
  相手構築(`ranked_teams`)。9系統・約70構築枠のフォルム違い種族が
  ベース種に誤計上されていた
- **生データの損失**: なし(pokedbアーカイブは全期間分保存されており、
  再集計で完全復元できた。snap8 の8/17分のみアーカイブ欠落で近傍日により近似)

## 2. 前提

環境の使用率データは2ソースから日次で取り込む:

- **championsbattledata.com** — ゲーム内バトルデータ由来の技/持ち物/特性/配分の
  採用率。**フォルム別に正しく分かれている**(rotomwash 等のページが個別に存在)
- **champs.pokedb.tokyo オープンデータ** — 上位ランカー構築(6体+持ち物)。
  ここから**ポケモン使用率%とチームメイト共起率**を集計する

pokedbの種族はJSONで `{"pokemon": "ロトム", "form": "ウォッシュロトム", ...}` の
形をとる。この (名前, フォルム) を showdown ID へ写すのが
`champions_agent/data/sources/pokedb_opendata.py: _species_id()` で、
その結果は (1) `pokemon_usage` / `teammate_usage` の集計キー、
(2) 学習・評価の相手構築を作る `champions_agent/env/ranked_teams.py` の
種族ID、の両方に流れる。

## 3. 何が起きたか

`_species_id` は form 引数を受け取りながら**一切使っていなかった**:

```python
def _species_id(ja_name: str, form: str = "") -> str:
    """日本語種族名 -> showdown ID。フォーム表記は暫定でベース種に丸める"""
    maps = _load_jp_maps()
    sid = maps["species"].get(ja_name)
    ...
```

docstringに「暫定でベース種に丸める」と明記された割り切りが、
影響を測定されないまま7週間本運用に残った。結果、
ウォッシュロトム(電気/水、S86)もヒートロトム(電気/炎)も
「rotom」(ゴースト/電気、S91、種族値合計440の基本形態)として集計された。

異常のサインは記録に残っていた:

1. 家電フォルム5種が**全スナップショットで一律0.1%**
   (pokedb未掲載種に与える擬似使用率の床値そのもの)
2. 基本ロトムが「8.5%で安定」— 種族値的に環境で戦えない種の値としては不自然
3. 実対戦ログ全件を走査してもロトム個体の認識記録は**0件**
   (使用率8.5%なら約12対戦に1回は遭遇するはず)

いずれも今回ユーザー指摘を受けるまで精査されなかった。

## 5. 失われたもの

- **生データ**: 損失なし。pokedbアーカイブ(`champions_agent/data/archive/`)から
  全スナップショットを再集計できた。唯一 8/17 分のアーカイブが欠落しており、
  snap8 は 8/18 のアーカイブで近似した(両日とも222構築で、
  8/16と8/18の集計値は全対象種で一致しており誤差は実測0.1%未満)
- **派生物**: 汚染期間中に使用率を参照した構築提案・診断の結論
  (再実行で復元可能)
- **時間**: 学習の相手構築が7週間、誤ったフォルム分布で生成されていた。
  この影響は分離測定不能(P1インシデントと同じ設計限界)

## 6. なぜ防げなかったか

- 「暫定でベース種に丸める」という割り切りが docstring に**書いてあった**のに、
  暫定のまま影響を測らず本運用に入った。割り切りを書くだけでは対策にならない
- 取り込みデータの妥当性検証が「取得できたか」だけで、
  「ドメイン的にあり得る分布か」(種族値の低い基本フォルムが8.5%で
  上位に居座る不自然さ)を見ていなかった
- 一律0.1%(床値)が5種も並ぶという分布の異常を検知する仕組みがなかった。
  セット回転検知(`META_SET_CHANGE_WARN`)は「変化」を見るが、
  「動かない不自然な値」は見ない
- 気付けたはずのサイン: 上記3点(§3)。特に「実対戦ログ遭遇0件 vs 使用率8.5%」は
  機械的に照合可能だった

## 8. 恒久対策

- `champions_agent/data/sources/pokedb_forms.json` — フォルム表記→showdown ID の
  対応表(種族固有/完全名/地方すがた接尾辞/ベース種扱いの4区分)
- `_species_id()` がこの表でフォルムを解決。**表にない未知のフォルムは
  警告を出してベース種に丸める**(黙って丸めない)
- 回帰テスト: `tests/test_pokedb_forms.py`(6件)。CIサブセット
  (`scripts/ci_tests.sh`)にも追加
- 過去分の修復ツール: `tools/repair_usage_forms.py`(dry-run既定、
  アーカイブから決定論的に再集計)

## 9. 教訓 / 未対応の課題

**教訓**:

- 「暫定」と書いた丸め・近似は、書いた時点で影響の上限を測るか、
  検知の仕掛けを添える。docstringの正直さは対策の代わりにならない
- 外部データの名寄せは「一律の床値が並ぶ」「値が長期間ピクリとも動かない」
  という分布の形も監視対象にする
- 使用率とゲーム内遭遇(対戦ログ)は突き合わせ可能な独立ソース。
  大きく食い違う種族は名寄せバグを疑う

**未対応(要観察)**:

- **floetteeternal の型データ欠落**: championsbattledata はフラエッテを
  フォルム分けしていないため、使用率は floetteeternal に付くが
  `meta_sets` は floette 名義のまま。診断・相手構築の型解決で
  この対応付けが必要(暫定: ベース名義の型を参照する運用)
- 図鑑(`advisor/data/dex.json` + patch)に basculegionf /
  taurospaldeacombat / taurospaldeablaze が未収録。`meta_top` は
  図鑑非収録種を診断から落とすため、これらは脅威リストに出ない
  (使用率0.5〜2.2%の低頻度種。ローカルShowdownは収録済みで対戦は可能)
- 汚染期間(7/17〜9/2)の学習への影響は分離測定不能。修復後の相手分布変更は
  セット回転と同様に評価軸を動かすため、`training_changes.json` に記録した
