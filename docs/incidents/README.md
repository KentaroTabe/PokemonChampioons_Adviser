# インシデント記録の規約

障害・データ汚染・測定の誤りなど、**気付くのが遅れた/再発すると痛い問題**を記録する場所。
「何を直したか」ではなく「なぜ気付けなかったか」を残すことを目的とする。

## ディレクトリ構成

| 場所 | 内容 | git |
|---|---|---|
| `reports/` | **正式なインシデントレポート**。外部の読者が前提知識なしで追える詳細版 | **追跡する(公開される)** |
| 直下の `YYYY-MM-DD-*.md` | 内部メモ。当時の判断や数値を短くまとめた備忘録 | 追跡しない(ローカル限定) |
| `INDEX.md` | 内部メモの分類別インデックスと横断的な教訓 | 追跡しない(ローカル限定) |

このリポジトリは public のため、`.gitignore` は**除外がデフォルト**で、
`reports/` と本ファイルだけを例外として追跡する。公開したくない詳細を含む記録は
直下の内部メモに置くこと。

## 命名規則

```
YYYY-MM-DD-<英小文字ハイフンのスラッグ>.md
```

日付は**発生日**(発生日が特定できない場合は発見日)。
2026-07-31以前の内部メモのうち、発生日を特定できなかったものは
問題史の編纂日 2026-07-31 を使っている。

## 正式レポートの書き方

参照実装: [reports/2026-08-05-usage-db-season-rollover.md](reports/2026-08-05-usage-db-season-rollover.md)

**インシデントが起きたら、このレポートと同じ方針で書く。** 章立ては以下に揃える。

1. **サマリ** — 発生 / 検知 / 復旧の日時、影響範囲、失われた生データの有無
2. **前提** — そのデータ・仕組みが何のために存在し、どこへ流れるか。
   このプロジェクトを知らない読者が2章以降を読めるだけの説明を置く
3. **何が起きたか** — 原因のコードを引用し、時系列で書く。
   異常のサインが記録に残っていたなら、それも明示する
4. **被害の内訳** — **必ず実測値で書く**。汚染前後の比較表を置き、
   **無傷だった範囲も同じ粒度で書く**(過大評価も過小評価も避ける)
5. **失われたもの** — 生データ / 派生物 / 時間のどれが失われ、どれが復元可能かを分ける
6. **なぜ防げなかったか** — 既存の対策がなぜ届かなかったか。
   「気付けたはずのサイン」を必ず1つは挙げる
7. **復旧手順** — 実際に叩いたコマンドと、復旧を確認した実測値
8. **恒久対策** — 変更したファイルと、追加した回帰テスト
9. **教訓 / 未対応の課題** — 一般化できる原則と、今回やらなかったこと

### 原則

- **推測を断定で書かない。** 確認していないことは「未確認」と明示する
- **数字は実測を載せる。** 「大幅に悪化」ではなく「48.9% → 96.5%」と書く
- **無傷だった範囲を書く。** どこまで信用してよいかが、読み手にとって最も重要
- **再発防止は回帰テストとセット。** テスト名をレポートに書く
- 学習に影響する変更を伴う場合は `champions_agent/train/training_changes.json`
  にも追記する(ベンチ推移の解釈に必要)
