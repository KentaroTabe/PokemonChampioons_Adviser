# 構築提案の設計と運用条件 (2026-08-20)

ユーザーのパーティに対する「選出助言」と「構築提案」を分離し、
それぞれの根拠と運用条件を定める。実装は `tools/team_proposal.py`
(ラッパー `scripts/team_proposal.sh`)。

## 1. 選出モデルは設計し直しが必要か → 「作り直し不要、役割の限定と3つの拡張」

実測済みの事実 (出典: `champions_agent/train/train_selection.py` 冒頭表 /
selection_features_v2.py / 2026-08-20 カバレッジ実測):

| 事実 | 含意 |
|---|---|
| 機能埋め込み (種族非依存) を使っても、未知チームの実戦選出は相性ベース同等 (0.34) まで落ちる。実際に使うチームのデータ収集 (+5000件) で 0.52 | アーキテクチャは汎化向きだが、**現状の学習分布では「任意の6体」への外挿は保証されない** |
| 未知チーム検証の改善は 60構築+1.4% → 272構築+7.3% と、**収集分布を広げるほど汎化は上がる** | ボトルネックは特徴量ではなく**収集分布と量** |
| 型情報を足した v2特徴量は事前登録ゲート不通過で棄却 (ペア順位精度 v1 0.642 / v2 0.631) | 手作り特徴の追加は現データ量では効かない |
| 埋め込みカバレッジは健全: 登録ボックス19/19種、メタ型プール235種中228種にベクトルあり | 「未収録種でゼロベクトル化」は現メタでは主因ではない |

結論:
- **構築提案のパーティ評価に選出モデルを使わない** (外挿の絶対値は未校正)。
  評価は実対戦 (ローカルShowdown、両サイド同一RL方策・共通乱数の相手列)。
  この評価器は `tools/evolve_teams.py` として実装・運用済み (日次13時)。
- 選出モデルの役割は (a) **採用後のパーティに対する選出助言**、
  (b) 将来、探索の枝刈り (汎化ゲート通過後)。
- 拡張は3点 (作り直しではない):
  1. **収集分布の拡大**: ランクド272構築に加え、ランダム合成構成と
     「現パーティ±2枠」の候補空間近傍を収集に混ぜる
     (`collect_selection` の対象チーム生成を広げる)。
  2. **汎化の常時計測**: train_selection が未知チーム検証の改善率を
     META (`selection_model_meta.json` の `val`) に記録するようにした
     (2026-08-20実装)。ゲート: 未知チーム分割で **+5%以上**。
  3. **チーム変更時の運用**: my_team 変更 → `collect_selection.sh 2 2500
     myteam` → `train_selection` (微調整)。これを構築提案の採用手順に固定。

## 2. 構築提案の2段階と評価器

| 段階 | 空間 | 探索 | 評価 |
|---|---|---|---|
| 1. 制約付き改善 | 現パーティから最大2枠入替 (±固定枠 `--locked`) | `evolve_teams --seed-myteam --max-changes 2` (種+変異で初期集団) | 実対戦 (現行メタ分布の相手列、共通乱数) |
| 2. 一般提案 | メタ型プール全体 (235種) | `evolve_teams` 世代ループ (+メタ遷移外挿 `--forecast-mix`、PSROアーカイブ `--archive-mix`) | 同上 + **受入検定** |

受入検定 (両段階、既定200戦×2): 提案チームと現行パーティを**同じ相手列**で
戦わせ、対応のある差の平均±2SEで「採用推奨 / 差は誤差の範囲 / 現行維持」を
判定する。探索時の上振れ (勝者の呪い) をそのまま提示しない。

## 3. 必要条件 (運用ゲート)

`bash scripts/team_proposal.sh --check` が毎回機械判定する。
必須(hard)未達なら `--propose` は実行を拒否 (`--force` で参考値実行)。

### 共通 (C1-C4, 必須)
| 条件 | 閾値 | 測定 |
|---|---|---|
| C1 使用率メタの鮮度 | 最新スナップショット ≤7日 | usage_snapshot.fetched_at |
| C2 ランクド構築プール量 | ≥100構築 (USAGE_MIN_RANKED_TEAMS) | build_ranked_teams |
| C3 評価用RL方策 | battle_policy_balance_best.zip 存在 | ファイル |
| C4 ローカルShowdown | 8100 LISTEN | socket接続 |

### 段階1 (S1-*, 必須)
| 条件 | 閾値 |
|---|---|
| S1-1 現パーティ6体の確定 | `current_team_entries()` が6体 (直近対戦ログ→技登録→登録順) |
| S1-2 登録完全性 | 6体全てに技4/性格/能力ポイント (種チームの忠実な再現) |
| S1-3 評価戦数 | `--battles ≥40` (SE≤0.08) |

### 段階2 (S2-*)
| 条件 | 種別 | 閾値 |
|---|---|---|
| S2-1 メタ型プール規模 | 必須 | ≥40種 |
| S2-2 受入検定の戦数 | 必須 | ≥100戦/側 (対応SE≤0.05) |
| S2-3 メタ遷移外挿 | 推奨 | 使用率履歴2ヶ月分 (無ければ現行メタのみで評価) |
| S2-4 PSROアーカイブ | 推奨 | ≥1件 (対策普及後への頑健性) |

### 選出モデル関連 (M-*, 推奨 = 提案自体は止めないが採用後の助言品質に関わる)
| 条件 | 閾値 |
|---|---|
| M1 構成汎化の実測 | META `val`: 未知チーム分割で改善 ≥+5% (train_selection が記録) |
| M2 現パーティが学習分布内 | `is_in_distribution` (分布外なら選出助言は参考値) |

実行時の追加チェック: 対戦中 (`check_battle_active`) と
`logs/PAUSE_TRAINING` 存在時は実行しない (測定系との競合回避)。

## 4. 採用フロー (提案を受け入れる場合)

1. 提案構築の型をゲーム内で組み、もっと見る画面で登録
   (config/my_team.json へ自動取込み)
2. `bash scripts/collect_selection.sh 2 2500 myteam` (新パーティの選出データ)
3. `python -m champions_agent.train.train_selection` (微調整 + val記録)
4. 接続テストで助言品質を確認

## 5. 使い方

```
bash scripts/team_proposal.sh --check
bash scripts/team_proposal.sh --propose --stage 1 --locked ミミッキュ
bash scripts/team_proposal.sh --propose --stage 2 --accept-battles 300
```

結果: `logs/team_proposal/proposal_<時刻>.json` (条件・提案・受入検定・採用手順)。

2026-08-20 時点の実測: 段階1/2とも必須条件は全て充足 (運用可能)。
未達は推奨条件のみ — M1 (未計測、次回 train_selection で自動記録)、
M2 (現パーティ分布外 → 採用フロー2-3で解消)、S2-3 (履歴1ヶ月分)。
