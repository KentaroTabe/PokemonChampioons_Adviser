## 1. 結論

外部成果の活用を続ける方針は維持する。今回の結果だけでMetamonへ切り替える根拠はない。
ただし、「Championsのfeatureがあるので、そのまま実用上の基準にできる」という期待は修正する。

## 2. B0-checkの不一致の扱い

現在の件数は、固定したShowdownとソース表・参照回数を比較した静的な調査結果である。
実際のダメージ・状態変化の不一致件数や、勝率への影響とは区別する。

- 技の内部表現には集約や近似がある。例えばpoke-engineのTriple Axelは威力40と複数回攻撃の処理を組み合わせている。表をShowdownの20に書き換えるだけでは正しい修正にならない。
- Foul Playには観測されたへんしんや、しめったいわ・ひかりのねんどに関する状態更新がある。観測後の追跡があることと、探索中の将来の効果を再現できることは別に試す。
- 特性名の参照がないことは実装欠落の有力な候補になるが、参照があることだけでも正しい効果実装の証明にはならない。
- 持ち物の6.5%、特性の7.2%、個体の8.5%は異なる集計値であり、足して「影響を受ける試合の割合」とはしない。
- ローカルShowdownの版と、稼働中サーバーの実体も一致させる。形式名の一致だけでは版を保証できない。

優先する動的ケースは、実際に使う構築・想定相手に出るメガ、主要技、壁・天候・地形の延長、へんしん、ばけのかわ等。
「正確に一致」「探索上の意図的な近似」「観測後だけ対応」「欠落／不具合」「参照側も未確定」に分ける。
近似を全廃することは採用条件にしないが、重要な局面を誤る近似を隠して基準にしない。

既存の延長効果・へんしんへの対応には、ここで利用候補が生まれた。
まず引き継ぐのは独立に確認できた仕様・境界ケース・回帰fixtureであり、旧Python実装をそのまま探索エンジンへ組み込む判断ではない。

## 3. 開発者向け4点の判断

### 1. Rust、外部取得、チーム、修正版の選択

Rustの導入とビルドを次の作業に含めることを勧める。対象cloneと依存・toolchainの版を記録し、既存の実行環境から分ける。
環境構築に必要な取得と、対戦中のデータ取得は分ける。
Rust公式はmacOSでrustupによる導入を案内している: https://rust-lang.org/tools/install/

実行時の4経路は次の方針とする。

| 経路 | 方針 |
|---|---|
| 公開Showdownのログイン | ローカル対戦ではローカル専用の接続・認証経路にする。変更を記録する |
| SmogonのChaos | 対象形式・月・cutoffを決めて取得したファイルを保存し、hashを固定 |
| data.foulplay.ccの型・技集合 | 対象形式の公開ファイルを必要な範囲で取得・検査して固定 |
| Showdownのサンプルセット | 同様に取得・検査して固定 |

測定中は保存ファイルを読む。取得できなかった必須データを黙って空にせず、取得不能／不足を結果に残す。
cutoff 0を手元の1500へ替える場合は条件変更として記録する。空データは接続の動作確認には使えても、元のFoul Playの判断能力の基準にはしない。

チームは既存登録から完全な6体セットを明示して用意し、修正後の書き出しと対象modのvalidatorを通す。
境界効果を試す診断用チームと、速度・完走を測るチームの目的を記録する。
未知の相手型まで試験対象へ渡さない。エンジン単体の完全情報ケースはルール検査に限定する。

無改変版は参照用として残す。対象ルールへの補正が必要と動的に確認されたら、最小限の修正版を別に固定する。
補正した外部版をB0にする前に修正範囲を凍結し、その後に旧部品Xとの比較へ進む。
今回の不一致リストを一括修正することや、旧スコア・旧修理を混ぜて改善することは、この段階の作業に含めない。
入力では「観測できていない情報」と「名前が判明しているのにエンジンが未対応」を区別する。
後者を別種・効果なしへ黙って置換する経路は検出し、未対応として記録する。前者は不完全情報として通常どおり扱う。

最初の打ち切り点は「ビルド、優先ケースの動的照合、少数対戦の完走、速度・メモリの測定が揃った時点」。
そこで修正規模を見積もる。多数の効果実装や状態表現の大改修が必要なら、全修復へ進まず別候補・別のシミュレーター接続と比較し直す。
確認できない効果を含む相手を成績から都合よく除外しない。範囲を限定した診断は限定結果として出す。

### 2. 本試験前の版固定

**現状の7行だけを正式比較の十分条件にはしない。** コード確認で次が残っている。

| 箇所 | 現状 | 必要な対応 |
|---|---|---|
| `tools/advice_mode.py::freeze_models` | RLのzipと選出のptだけをコピー | 選出の埋め込み・meta・特徴量版を一組として固定し、読み手もその写しを使う |
| `selection_model.py::_functional_store` | グローバルな `MODELS_DIR/selection_model_emb.json` を読む。無ければ通常の埋め込みへ退避 | 正式比較では指定bundleの埋め込みを必須にし、不足・不一致時に停止 |
| `selection_model.py::trained_teams` | グローバルなmetaを読む | 同じモデルbundleのmetaを参照。別の配備版の説明を付けない |
| `tools/advice_mode.py::freeze_data` | 使用率DBはコピーせずsnapshot番号を記録 | 必要なsnapshot／履歴範囲を不変のDBへ抽出し、その経路・hashを固定 |

snapshot番号が同じでも、その行の修復・更新があれば入力は変わり得る。
既存 `tools/inputs_pin.py` に選出3ファイルの検査と `export_bundle` があるので、必要な契約を再利用する。コピーだけして推論が元のパスを読み続ける状態を避ける。
登録チーム・コード・設定・Showdownの版も試験manifestで固定する。

最小受入は、固定後に元の埋め込み・meta・DBを変更しても固定入力が変わらず、bundle側を欠損・改変すると明確に止まること。
この確認を済ませてから、当該比較を始める直前に固定bundleを作り、必要なら起動し直す。
外部B0だけの調査のために、旧advisorの再起動を前提にしない。

### 3. GitHub CIのShowdown

**対象版のShowdownを用意する小さな統合試験jobを追加する方針を勧める。**
現在の軽いロジックjobは維持し、R1のvalidator経路を別jobで確実に実行する。
Showdownはブランチの最新ではなく検証対象のcommitに固定し、Node・依存・build条件を記録する。
取得・build・対象形式の準備に失敗したら、そのjobでは失敗にする。理由付きSKIPを合格の代わりにしない。
必要なのはチームの検証であり、常駐サーバーや大量対戦ではない。

ローカル171本がSKIP 0だったという報告と、GitHub側でvalidatorが動くことは別の証拠である。
今回、GitHubの実行結果や171本を再実行して検証したわけではない。

### 4. 固定した選出モデルの適用範囲

**登録構築専用のモデルは、別構築なら推論を止める。汎用モデルは、汎用として明示した範囲で複数構築に使える。**
ファイルを固定する契約と、そのモデルを適用できる入力の契約を分ける。
`source_id = pinned` は由来の表示であって適用範囲の検証にはならない。

- manifestにモデル種別、対応する構築、特徴量版・埋め込み、規制、学習時の型の前提を保存する。
- 構築専用なら6体だけでなく、学習が固定型を前提にした場合は型の内容も照合する。順番だけの変更と別構築を区別する。
- 選出画面で6体がまだ確定していなければ確認待ち。確定後の不一致では、その専用モデルを使わず理由を表示・記録する。別モデルへ黙って退避しない。
- 汎化性能を調べるため意図的に別構築へ適用する試験は、対象と条件を先に明示すれば別実験として可能。通常運用の適用許可とはしない。
- 固定時に元モデルの由来を保存し、後から配備先のファイルとの一致を探すことに依存しない。

## 4. 次の優先順位

1. 外部候補をビルドし、対象ルールでの動的な不一致と実用速度を確かめる。
2. 並行して、正式比較に使うモデルbundle・DBの固定を完成させる。新しい勝率比較はその後。
3. GitHubにvalidatorの統合試験を置き、固定モデルの適用範囲を明示する。
4. 外部版を固定できたら、候補Xを一つだけ加える比較へ進む。

修正の方向は妥当だが、CIの緑だけで正式比較の準備完了とは判定しない。
